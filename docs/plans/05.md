# 05 — Replace the demo fixture with the real Shree Vatika layout

**Tier 1.** Touches `fixtures/shree-vatika-2/` (the one shared demo colony both halves
depend on) and the local database seed. `/plan` before `/build`, `/review` before `/wrap`.

## 1. Context already true

- **Owner sent a real site-plan photo** and confirmed two decisions (this session, not
  written to disk elsewhere):
  1. This real layout **replaces** `fixtures/shree-vatika-2/` — the existing hand-authored
     demo (`colony.svg`/`colony.json`, `source.method: "hand-authored fixture"`) was always
     a placeholder ("Hand-authored demo. Not a real layout." — `colony.json`'s own note).
  2. **~8 interior plots are excluded** — their circled numbers were too small to read
     reliably in the photo (two unread columns inside the 33–36 row, two inside the
     32–23 row, two between 37 and 40). Left out of `colony.svg`, `colony.json`, and the
     seed CSV entirely, not stubbed with placeholder numbers.
- **Colony id/name kept as `shree-vatika-2` / "Shree Vatika Phase 2"** — the photo shows
  no project name; this is a stated assumption, not a confirmed fact. Flagged to the
  owner; easy to rename later since it's just two string fields.
- **The source plan has no lettered blocks** — every plot is a bare number (①, ③, ⑭, …
  ㊸). Contract requires `block` to match `^[A-Z]+$` and `svg_id` to be
  `plot-{BLOCK}-{NN}`. This build uses a single block, **`A`**, for every plot — a
  contract-shape necessity, not a fact read off the plan.
- **Two block sizes are explicitly labelled on the plan**: `30'0" X 60'0"` (plots
  48/51/54/47/44/41) and `35'0" X 55'0"` (26/24/22/15/18/21). A third label, `30'0" X
  55'0"`, sits next to plot 10 and is applied to the rest of that block (14/7/1/3/6).
  The remaining two blocks (37/40, and 33/36/32/23) have no legible size label — their
  dimensions are **estimated** from the plan's own tick marks (≈30×50 ft and ≈30×65 ft
  respectively) and must be marked as such, not presented as read facts.
- **Reuse by exact path:**
  - `apps/map/scripts/import-seed.ts` — the only import path. Refuses unless
    `colony.verified === true` (D-108) and fails loudly on any svg/manifest/csv id
    mismatch (`fail()` at lines ~77 and ~100). No changes needed to this script.
  - `contract/colony.schema.json` / `contract/SPEC.md` — the target shape. No schema
    changes; this task produces data that fits the existing contract, it doesn't extend
    it. Road-width text reuses the existing `feature-label` class rather than inventing
    a new one.
  - `fixtures/shree-vatika-2/colony.svg`'s existing `<symbol id="tree-canopy">` pattern —
    reused as-is if trees are added (see §4 non-goals: they are not, this plan skips
    trees).
- **`px_per_ft` stays `2.6667`**, matching the existing fixture's value — no reason to
  diverge, and D-110 already pins `viewBox` width at 1000 regardless.
- **The `verified: true` flag** — D-108 says no code path sets this true except a human
  verify-page pass, and `tools/pipeline`'s verify page doesn't exist yet (pre-M9). The
  existing fixture already bypasses this by hand-writing `verified: true` directly in
  `colony.json` (`method: "hand-authored fixture"`). This task does the same, using
  `method: "traced"` (schema enum already includes it) — the owner's own review of the
  rendered result in the running app over this session **is** the human verification
  pass D-108 requires; it just isn't happening through a UI that doesn't exist yet. This
  is a conscious, precedented bypass, not a silent one — call it out again in `/wrap`'s
  log entry.

## 2. The exact task

1. **`fixtures/shree-vatika-2/colony.svg`** — full rewrite. `viewBox="0 0 1000 1470"`
   (height grows because real plot proportions, at `px_per_ft=2.6667`, are much taller
   than the old demo's near-square plots — a 60 ft-deep plot is 160px tall vs. 80px
   wide). Contents, one compound `<path class="road">` (spec/00-rules.md: roads are
   negative space, one compound path), `site-boundary`, one `garden` feature (the green
   patch next to the 37/40 row — the only garden visible on the plan; no clubhouse/
   temple/tank, because none are visible on this plan and inventing them would be
   fabricated data), and 26 `plot` paths with `plot-label` text, all **touching** —
   adjacent plot edges share exact coordinates, zero gap (this session's explicit
   feedback). Road-width labels (`9.0 M W ROAD`, `7.5 M W ROAD`) as `feature-label`
   text, reusing the class rather than adding one.
2. **`fixtures/shree-vatika-2/colony.json`** — full rewrite matching the SVG's 26
   `svg_id`s exactly (the import script's orphan check fails loudly otherwise). Each
   plot: `block: "A"`, zero-padded `number`, `area_sqft` = `round(length_ft *
   breadth_ft)`, `centroid` in SVG px, `facing` inferred from which side of its block
   faces a road (row nearest a road above → that road's compass side; documented per
   block in the generator script, not hand-guessed per plot), `is_corner` true for the
   first/last column of every row (touches its row's road **and** a side road/spine),
   false for interior columns. `source.method: "traced"`, `source.file` naming the
   photo, `verified: true` (see §1). One `garden` feature.
3. **`seed/plot-status-seed.csv`** — full rewrite, 26 rows matching the manifest's
   `svg_id`s exactly, every row `status: available` with every optional field blank. No
   fabricated owners/brokers/bookings — this is real inventory; inventing sold plots
   would be actively misleading data in a tool D-006/D-007 treat as the record of truth.
4. **Re-seed the local database**: `supabase db reset` (already Claude-authorized per
   CLAUDE.md, confirmed no remote project linked), then `pnpm import:seed` from
   `apps/map/`.
5. **A short generator script** (scratch, not committed) builds the SVG/JSON/CSV from a
   block-spec table rather than hand-authoring 26 plot entries three times over — avoids
   the exact class of transcription bug that would silently mismatch one svg_id between
   the three files.

## 3. Pinned constraints

- **`px_per_ft = 2.6667`** — matches the existing fixture, no reason cited to change it.
- **Zero gap between adjacent plots** — this session's explicit correction to the earlier
  artifact mockups, which used a 4px gap. Adjacent plot rects/paths share exact boundary
  coordinates.
- **Single block `"A"`** for all 26 plots — the source plan has no letters; this is a
  contract-shape necessity (`block` must match `^[A-Z]+$`), stated once here so it isn't
  re-derived or second-guessed mid-build.
- **26 plots, exactly**: `01, 03, 06, 07, 10, 14, 15, 18, 21, 22, 23, 24, 26, 32, 33, 36,
  37, 40, 41, 44, 47, 48, 51, 54, 55, 56`. Nothing else — no LIG/EWS entries (unnumbered
  group allocation, not individually-numbered saleable plots on this plan) and none of
  the ~8 unread interior plots.
- **All 26 plots seed as `status: "available"`** — no fabricated booking data.
- **`verified: true`** in the manifest — see §1's D-108 reasoning. Do not leave it
  `false`; the import script refuses a `false` manifest outright, and this is a
  deliberate, documented bypass, not an oversight.

- **Clubhouse/temple/tank amenities.** Not visible on this plan. The existing demo had
  them; this real one doesn't get invented ones.
- **The ~8 unread interior plots and the LIG/EWS allocation.** Explicitly deferred by the
  owner's own choice this session (§1) — not this task's to guess at.
- **`tools/pipeline`.** Still doesn't exist (pre-M9, unrelated to this task). This
  fixture is hand-authored/traced exactly the way the demo fixture was, not
  pipeline-generated.
- **Renaming the colony id/name.** Kept as `shree-vatika-2` / "Shree Vatika Phase 2" per
  §1's stated assumption; a follow-up if the owner says this is actually a different
  property.

## 6. Failure modes (spec/00-rules.md checklist)

1. **Partial writes** — `import-seed.ts` already handles this: colony insert, then plots,
   then history, each failing loudly and naming exactly how far it got (see its own
   `fail()` messages). Nothing new to add. If `pnpm import:seed` fails partway, the fix
   is `supabase db reset` and retry, per the script's own error text — not a patch.
2. **Idempotency** — re-running `pnpm import:seed` against a non-empty DB will hit the
   `(colony_id, svg_id)` unique constraint and fail loudly (existing behaviour,
   untouched). Always reset first, same as every prior seed load in this repo's history.
3. **Concurrency** — N/A. This is a one-time offline load, not a live write path;
   `applyPlotTransition()` is untouched.
4. **Orphans** — the exact failure mode `import-seed.ts`'s own checks exist to catch
   (svg_id present in one file, absent from another). The generator script (§2.5) writes
   all three files from one shared plot table specifically so this can't happen by
   transcription slip.
5. **Dead computation** — N/A. `area_sqft`, `facing`, `is_corner` are computed once by
   the generator script and written into the static manifest, same "computed once, never
   recomputed" discipline tier-1.md requires of the (nonexistent) real pipeline.
