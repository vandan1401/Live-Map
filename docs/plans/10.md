## 2. The exact task

### 2.1 — New RPC: `bulk_set_initial_plot_data` (initial CSV/XLSX import)

New migration `apps/map/supabase/migrations/20260816000000_bulk_initial_plot_import.sql`:

- `create or replace function bulk_set_initial_plot_data(p_colony_id text, p_rows jsonb)
  returns jsonb`, `security definer`, `set search_path = public, pg_temp`. Guard `if
  auth.uid() is null then raise exception 'not authenticated'; end if;` (mirrors
  `apply_plot_transition`). Derive `v_actor` the same way (`app_metadata.display_name`
  coalesced with `email`).
- `p_rows` is a JSON array; unpack with `jsonb_to_recordset(p_rows) as x(svg_id text,
  status text, owner_name text, owner_phone text, broker_name text, rate_paise bigint,
  booking_amount_paise bigint, booking_date date, registry_date date, notes text)`.
- Loop over rows. For each: `select * into v_plot from plots where colony_id = p_colony_id
  and svg_id = r.svg_id for update`. In order:
  1. Not found → append `{svg_id, reason: 'unknown svg_id'}` to `skipped`, `continue`.
  2. `r.status not in ('available','booked','registered')` → append `{svg_id, reason:
     'invalid status'}` to `skipped`, `continue`.
  3. Ineligible — `exists (select 1 from plot_history where plot_id = v_plot.id and
     changed_by not in ('import', 'bulk_import'))` → append `{svg_id, reason: 'plot has
     real activity already'}` to `skipped`, `continue`.
  4. Otherwise: `update plots set status = r.status, owner_name = r.owner_name, owner_phone
     = r.owner_phone, broker_name = r.broker_name, rate_paise = r.rate_paise,
     booking_amount_paise = r.booking_amount_paise, booking_date = r.booking_date,
     registry_date = r.registry_date, notes = r.notes, version = version + 1, updated_by =
     'bulk_import', updated_at = now() where id = v_plot.id`; `insert into plot_history
     (plot_id, status, changed_by, note) values (v_plot.id, r.status, 'bulk_import', 'Bulk
     initial import by ' || v_actor)`; append `svg_id` to `applied`.
- An unexpected error inside the loop (anything other than the three named skip
  conditions, which are checked, never raised) propagates and rolls back the **whole**
  call — no partial-batch commit (§3, §6).
- Return `jsonb_build_object('applied', v_applied, 'skipped', v_skipped)`.
- `revoke execute on function bulk_set_initial_plot_data(text, jsonb) from public; grant
  execute ... to authenticated;` — same belt-and-suspenders pattern as
  `apply_plot_transition`.

## 3. Pinned constraints

- **`bulk_set_initial_plot_data` is a second, narrowly-scoped write path for `plots` —
  deliberately, not an accidental violation of invariant 4.** Invariant 4 ("plot status
  changes through exactly one function") governs the *operational* transition path used by
  the map and the table view (§2.3), which stays `applyPlotTransition()`-only with no
  exception. This RPC exists only for the one-time initial-data event `spec/00-rules.md`
  already names as an allowed exception to "no spreadsheet as the live data store." It
  never runs `isLegalTransition()` and can jump straight to any of the three status words —
  that is intentional (a plot already sold before the family started using this app is not
  a "transition" from `available`, it is a fact being recorded for the first time) and must
  not be "fixed" to route through `applyPlotTransition()`.
- **Eligibility is `changed_by not in ('import', 'bulk_import')`, not "zero history rows"
  and not "only ever run once."** A plot stays eligible for repeated bulk-import
  correction — re-uploading a fixed CSV before anyone has made a real edit — for exactly as
  long as its only history is the pipeline seed and/or prior bulk-imports. The instant a
  real transition happens (`applyPlotTransition`, which always writes the real
  `display_name`/email, never these two literal strings), the plot is permanently locked
  out of bulk-import — future changes must go through the table view or the map. This is
  the deliberate "onboarding correction window" design; do not narrow it to single-shot
  without discussing the UX regression first (a typo in row 200 of a 300-row file would
  otherwise require a full `supabase db reset`).
- **`updated_by`/`changed_by` for a bulk-imported row is the literal string
  `'bulk_import'`, not the real uploader's display name** — mirrors `'import'`'s existing
  precedent (`scripts/import-seed.ts`). The real uploader's name is still recorded, in
  `plot_history.note` (`'Bulk initial import by ' || v_actor`), for audit purposes — but is
  not the eligibility-check value, so `formatActorName` needs the new case (§2.2) or the
  UI will literally show "bulk_import" as an editor's name.
- **An unexpected error mid-batch rolls back the entire `bulk_set_initial_plot_data` call**
  — no partial commit of, say, rows 1–150 of a 300-row file with no record of which
  succeeded. The three *expected* skip conditions (unknown `svg_id`, invalid status,
  ineligible plot) are outcomes recorded in the returned `skipped` array, never raised
  exceptions — only a genuinely unexpected DB error aborts the transaction.
- **No new write path for `owner_phone`, `broker_name`, `rate_paise`,
  `booking_amount_paise`, `booking_date`, `registry_date`, `notes` from the table view.**
  These remain writable only via `bulk_set_initial_plot_data` (§2.1, initial-data event
  only) — the table view (§2.3) displays them read-only. Money fields especially: opening
  an ongoing edit path for `rate_paise`/`booking_amount_paise` from a table cell is exactly
  the "own write-path decision" `PROGRESS.md`'s Deferred section already flagged as
  out-of-scope for a quick follow-up (D-010's paise discipline plus a UI numeric-input
  path is real, separate scope).
- **The table view never submits more than one row's transition per `applyPlotTransition`
  call.** No "save all" batching — every row edit is independent, so the existing
  version-conflict/legal-transition guarantees extend to the table with zero new
  concurrency surface.

## 4. Non-goals

- Real Google Sheets integration (OAuth, live sync) — explicitly rejected by the owner this
  session, see §1.
- A write path for `owner_phone`/`broker_name`/`rate_paise`/`booking_amount_paise`/
  `booking_date`/`registry_date`/`notes` from the table view or any path other than the
  bulk-import RPC. Still an open, separate feature gap (`PROGRESS.md` → `## Deferred`).
- Column-mapping UI (dragging/renaming CSV columns to match). The header row must match
  the fixed contract exactly; a mismatched header is a parse error, not a mapping prompt.
- Filtering, sorting, or searching within the table view. Lists all of a colony's plots,
  order as returned by `fetchPlotsByColony` (manifest order). Reusing `searchPlots.ts` here
  is a reasonable follow-up, not required by this plan.
- Editing geometry, `block`/`number`/`area_sqft`/`facing`/`is_corner`/`svg_id` from either
  feature — those come from the pipeline manifest and stay read-only everywhere in
  `apps/map`.
- Undo/redo inside the table view beyond what `applyPlotTransition`'s existing per-plot
  Undo already provides via the plot detail sheet — not duplicated here.
- Creating a colony or plot rows that don't already exist. `bulk_set_initial_plot_data`
  only ever updates existing `plots` rows matched by `(colony_id, svg_id)` — it is not a
  replacement for `pnpm import:seed`, which still owns colony/plot creation from a
  pipeline manifest.
- Storing the uploaded filename or a client-supplied import label in the database. The
  confirmation screen (§2.2) can show it locally; `plot_history.note` only carries the
  server-derived actor name.

## 6. Failure modes (spec/00-rules.md checklist)

### `bulk_set_initial_plot_data` (§2.1)

1. **Partial writes** — each eligible row's `plots` update and `plot_history` insert are
   adjacent statements inside the same function-body transaction as the whole call; an
   unexpected error anywhere in the loop rolls back the entire batch, not just the row that
   failed (§3) — a 300-row file either fully applies (modulo expected skips) or none of it
   does.
2. **Idempotency** — deliberately *not* strict single-shot idempotency (§3's "correction
   window"): a byte-identical re-upload before any real edit re-applies and appends another
   `plot_history` row per plot (visible, not silent). After a real edit, the same re-upload
   is a true no-op for that plot (shows up in `skipped`). Both behaviors are intentional and
   covered by acceptance criterion 2.
3. **Concurrency** — `select ... for update` per row, same lock pattern as
   `apply_plot_transition`; two overlapping bulk-imports (or a bulk-import racing a live
   table/map edit) on the same plot serialize through the lock rather than racing.
4. **Orphans** — an `svg_id` in the uploaded file with no matching `plots` row is reported
   in `skipped` with reason `'unknown svg_id'`, never silently dropped and never inserted
   as a new row (this RPC only updates existing rows).
5. **Dead computation** — N/A. Never touches `facing`/`is_corner`/`area_sqft`.

### Table view (§2.3)

1. **Partial writes** — inherited unchanged from `applyPlotTransition()`'s existing
   transaction; the table view adds no new write statement, only a new caller.
2. **Idempotency** — inherited unchanged: a double-submit on the same row fails the
   existing version check on the second call, identical to the map's Save button.
3. **Concurrency** — inherited unchanged, plus: each row edits independently (§3), so a
   stale version on row 5 cannot block or corrupt a save on row 6 — no shared batch state.
4. **Orphans** — N/A; the table only ever lists plots already validated at import-time
   join checks (`fetchPlotsByColony`), no new join.
5. **Dead computation** — N/A; `facing`/`is_corner` render read-only, never recomputed.
