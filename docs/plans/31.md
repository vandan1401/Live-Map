# Plan 31 — Backdrop step moves into the colony-upload flow; the per-row picker button is removed

Owner direction (2026-09-12, same session, second correction on this feature): "the backdrop
should lie in upload colony where we upload json and svg because i want different backdrop
for every colony" — then, on being asked whether the per-row "Backdrop" button
(docs/plans/30.md) should also stay for editing an existing colony's backdrop later, chose
**"Upload flow only"**: remove that button entirely. From now on, setting or changing a
colony's backdrop happens as a step immediately after uploading or replacing that colony
(re-attaching its svg+json is the way back into the backdrop editor, same as any other
correction in this app — D-118's philosophy, applied here).

Nothing about *how* a backdrop is stored or written changes — `colonyBackdrop.ts`'s two
functions, the Storage bucket, the 11 `colonies.backdrop_*` columns, and
docs/plans/30.md's RLS/grant migration are all reused exactly as they are. This plan is
pure UI re-sequencing: move `ColonyBackdropScreen.tsx` from being opened by a `ColonyPicker`
row button to being the automatic next step after `ColonyUploadScreen.tsx`'s own upload/
replace succeeds, and delete the row-button entry point.

## 1. Context already true

- **`ColonyBackdropScreen.tsx` (docs/plans/30.md) already does everything needed** — file
  input, 8 alignment fields, calls `uploadColonyBackdropImage`/`updateColonyBackdropTransform`
  with the authenticated `client`. It takes `{ client, colony: ColonyRow, onClose }`. Nothing
  in its internals needs to change except adding one new optional prop (task B).
- **`ColonyUploadScreen.tsx`'s `upload()` function** (currently 152 lines) already knows the
  exact moment a colony exists: `result.ok === true` inside `createColonyFromManifest(...)`'s
  `.then()`, both for a fresh create and a confirmed replace — the RPC returns only
  `{ colonyId }`, not a full row, so reaching the backdrop screen from here needs one new
  fetch (`fetchColonyById`, `lib/db/colonies.ts`, already exists, already used elsewhere —
  the layer-boundary table in NAVIGATION.md lists `lib/db/*` as importable from any feature).
- **`ColonyUploadStageView.tsx`'s `Stage` union's `"done"` case becomes unreachable** once
  the success branch below routes to a `"backdrop"` stage instead — the only place `"done"`
  was ever set. Dead code, not a fallback to keep "just in case" (this repo's own working
  style: note gaps, don't hedge with unused branches).
- **What this plan undoes from docs/plans/30.md, precisely:** `ColonyPicker.tsx`'s
  `onBackdrop` prop and per-row "Backdrop" button; `App.tsx`'s `backdropColonyId` state and
  its `ColonyBackdropScreen` render branch. `docs/plans/30.md`'s migration
  (`20260912020000_colony_backdrop_authenticated_write.sql`), `colonyBackdrop.ts`'s two
  functions, and `ColonyBackdropScreen.tsx` itself are **not** undone — only the entry point
  into that screen moves.
- **Risk tier:** `ColonyUploadScreen.tsx`/`ColonyUploadStageView.tsx` are Tier 1
  (`apps/map/src/features/colony-upload/**`). `ColonyPicker.tsx`, `App.tsx`,
  `ColonyBackdropScreen.tsx` are Tier 2. No migration, no RLS, no RPC change in this plan —
  the Tier-1 surface here is UI sequencing only, but the directory still calls for
  `/plan`/`/review`.

## 2. The exact task

**A. `ColonyUploadStageView.tsx`** — delete the `"done"` variant from the `Stage` union, its
render branch, and the `onDone` prop from `Props`/the destructure. No replacement needed —
task D handles what used to happen at that stage.

**B. `ColonyBackdropScreen.tsx`** — add one new optional prop:

```ts
introMessage?: string;
```

Rendered as a `<p className="colony-upload-summary">{introMessage}</p>` immediately above
the existing `.colony-upload-hint` paragraph, only when provided (`undefined` renders
nothing extra — no behavior change for any future direct use of this component).

**C. `ColonyUploadScreen.tsx`** — the exact task:

- `upload()`'s success branch becomes `setStage({ kind: "backdrop", colonyId: result.colonyId })`
  in place of `{ kind: "done", colonyId: result.colonyId }`.
- New `Stage` member (declared in `ColonyUploadStageView.tsx` alongside the others, even
  though `ColonyUploadScreen.tsx` is the only place that renders it — keeps the `Stage` type
  in one place): `{ kind: "backdrop"; colonyId: string }`.
- New local state, `const [backdropColony, setBackdropColony] = useState<ColonyRow | null>(null)`.
  A `useEffect` keyed on `stage.kind === "backdrop"` (same shape as the existing preview
  effect above it) calls `fetchColonyById(client, stage.colonyId)` and stores the result;
  reset to `null` whenever `stage.kind` is not `"backdrop"` (so a later, different colony's
  upload never briefly shows a stale row).
- Top-level return gets a new branch **before** the normal overlay/panel/StageView JSX:
  when `stage.kind === "backdrop"`, render `backdropColony` loaded → `<ColonyBackdropScreen
  client={client} colony={backdropColony} introMessage={\`Colony "${stage.colonyId}" is
  live. Optionally set its backdrop below.\`} onClose={onClose} />`; not yet loaded → a
  minimal `.colony-upload-overlay`/`.colony-upload-panel` with a single "Loading…" paragraph
  (matches this screen's own existing `.colony-upload-summary` class, no new CSS). `onClose`
  here is the **same** `onClose` prop `ColonyUploadScreen` already receives from `App.tsx` —
  closing the backdrop step closes the whole upload flow, same as clicking "×" ever did.

**D. `ColonyPicker.tsx`** — remove the `onBackdrop` prop from `Props`, the destructure, and
the "Backdrop" `<button>` per row (keep `ShareLinkButton` as the row's only remaining
action besides opening the colony).

**E. `App.tsx`** — remove the `ColonyBackdropScreen` import, the `backdropColonyId` state and
its render branch, and the `onBackdrop={...}` prop passed to `<ColonyPicker>`.

**F. Tests:**
- `ColonyUploadScreen.test.tsx`: `createFakeSupabaseClient()` gains a `.from("colonies")`
  stub returning a fake row (`maybeSingle()` resolving `{ data: <ColonyRow-shaped
  object with backdrop_* defaults>, error: null }`) so the new post-upload fetch resolves in
  tests. New test: after a full successful upload (choose files → Continue → tick the
  checkbox → click Upload), the backdrop screen's own heading (`"Backdrop — Test Colony"`)
  appears, and `onClose` is **not** called automatically (only once the backdrop screen's own
  close button fires) — the concrete proof this plan's whole point (chaining, not skipping,
  the backdrop step) actually happened.
- `ColonyPicker.test.tsx`: remove the `onBackdrop`-specific test and the `onBackdrop={vi.fn()}`
  prop from every other render call (added by docs/plans/30.md, now reverted).

## 3. Pinned constraints

- **`onClose` for the backdrop stage is the same prop `ColonyUploadScreen` already receives**
  — do not thread a second "finish" callback; the backdrop step's own close IS the upload
  flow's close, by design (one less click, no redundant confirmation screen).
- **`introMessage` is optional and additive** — `ColonyBackdropScreen.tsx` must render
  identically to its docs/plans/30.md shape when the prop is omitted.
- **No migration, no RPC, no RLS change in this plan** — if implementing this surfaces a need
  for one, stop and report rather than improvising it inline.

## 4. Non-goals

- Any change to `colonyBackdrop.ts`, the Storage bucket, the `backdrop_*` columns, or
  `20260912020000_colony_backdrop_authenticated_write.sql` — all reused exactly as shipped.
- A way to edit an existing colony's backdrop without re-uploading its svg+json — the
  owner's own explicit choice this session ("Upload flow only").
- `contract/`, `create_colony_from_manifest()`, `tools/pipeline` — untouched, as in
  docs/plans/30.md.

## 5. Acceptance criteria

- `mingw32-make gate` — same documented baseline (pre-existing anon-grant drift ± the
  `subscribePlots` flake, nothing new); `tools/pipeline` byte-identical.
- `ColonyUploadScreen.test.tsx`'s new case actually completes a real successful upload
  (through the Upload button, not just reaching the "ready" stage) and asserts the backdrop
  screen's own content is what's on screen afterward — confirm by reading the test, not
  assuming the mock shape is enough.
- `pnpm typecheck`/`lint`/`build` clean; `dist/` clean of `admin-portal`.
- Not achievable from here: opening the real chained flow in a browser. Flag as
  owner-verification-needed.

## 6. Failure modes

N/A — no new state writes. The write paths (`colonyBackdrop.ts`'s two functions,
`create_colony_from_manifest()`) are unchanged from docs/plans/29.md/30.md, already covered
by their own failure-mode analysis. This plan only changes when the existing backdrop screen
appears, not what it does.
