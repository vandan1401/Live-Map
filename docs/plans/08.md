## 1. Context already true

- **The gap**: `PlotStatusActions.tsx` offers a plain "Mark Booked" button with no input
  for the buyer's name. `PlotDetailContent.tsx` only ever *displays* `plot.owner_name`
  while `status === "booked"` — nothing in the app writes it. The only write of
  `owner_name` today is `scripts/import-seed.ts`'s one-off CSV import
  (`apps/map/src/scripts/import-seed.ts:143`, via `PlotInsert.owner_name`).
- **The one write path**: `apply_plot_transition()`
  (`apps/map/supabase/migrations/20260813000000_m4_apply_plot_transition.sql`) is the only
  function that writes `plots.status` (D-006, D-013, CLAUDE.md invariant 4). Its current
  signature is `(p_plot_id uuid, p_expected_version integer, p_new_status text, p_actor
  text, p_note text default null)` — no owner-name parameter exists. TypeScript callers
  reach it through exactly two layers, in order:
  `apps/map/src/lib/plot-status/applyPlotTransition.ts` (business-outcome typing) →
  `apps/map/src/lib/db/plotTransitions.ts`'s `callApplyPlotTransition` (the only place
  `.rpc("apply_plot_transition", ...)` is called).
- **Legal transitions** (`apps/map/src/lib/plot-status/transitions.ts`): `available` is
  the *only* predecessor of `booked` — `available: ["booked"]`, `booked: ["registered",
  "available"]`, `registered: ["available"]`. There is exactly one transition that ever
  enters `booked`: `available → booked`. No other transition needs an owner name.
- **`plot_history` has no `owner_name` column** (only `status`, `changed_by`,
  `changed_at`, `note` — M2 schema). This matters for Undo: `PlotStatusActions.tsx`'s
  `canUndo`/`onUndo` can walk `available → booked` back into `booked` via
  `history[1].status` when undoing an accidental un-book. That call must land on the
  correct prior buyer name with **no new UI** — see §3's "never clear" rule, which is
  precisely what makes this work for free.
- **D-016** (provisional): actor is a client-supplied string until M8 — unaffected here.
  `owner_name` is a different field (who was sold the plot), not `updated_by`/`changed_by`
  (who made the edit).
- **Reuse by exact path:**
  - `apps/map/src/lib/plot-status/applyPlotTransition.ts`'s `ApplyPlotTransitionInput` —
    gains one new optional field, `ownerName`. Do not add a second exported function.
  - `apps/map/src/lib/db/plotTransitions.ts`'s `callApplyPlotTransition` — gains one new
    optional arg passed straight through to the RPC's new parameter. Still the only
    `.rpc()` call site (NAVIGATION.md layer rule).
  - `apps/map/src/features/plot-detail/PlotStatusActions.tsx`'s existing
    `plot-status-button`/`plot-status-buttons` CSS classes
    (`apps/map/src/styles/plot-detail-sheet.css`) — the new input sits inside the existing
    `.plot-status-actions` block, no new stylesheet file.

## 3. Pinned constraints

- **`owner_name` is only ever written when `p_owner_name` is non-null, and the write is a
  coalesce, never an overwrite-with-null.** This is the one interface rule with real blast
  radius: get it backwards and every non-booking transition (registered, undo, un-book)
  silently blanks the buyer's name — exactly the "evidence that settles a commission
  dispute" invariant (CLAUDE.md #5) applied to a field `plot_history` doesn't separately
  track.
- **The owner-name field is required in the UI for a fresh booking** (`available →
  booked`), enforced by disabling the Save button — not enforced in the database. The
  column stays nullable (existing schema, unchanged); a null is still valid for rows that
  predate this change or for `registered`/`available` states where the field isn't shown.
- **No new write path.** The text field's value only ever reaches the database through
  `applyPlotTransition()` → `callApplyPlotTransition()` → `apply_plot_transition()`. No
  direct `.update()` on `plots` from `PlotStatusActions.tsx` or `PlotDetailSheet.tsx`.
- **Undo never supplies an owner name**, by construction (§2.5 unchanged call site) — this
  is what makes an undo-into-booked restore the prior buyer for free, per §1's
  `plot_history`-has-no-owner_name observation. Do not "fix" this by having Undo look up
  and pass the old name explicitly; that would require a new column or a history read
  this plan does not add, and the coalesce already gets the right answer without it.

## 4. Non-goals

- **`owner_phone`, `broker_name`, `rate_paise`, `booking_amount_paise`, `booking_date`** —
  none of these get a write path in this plan. Only the one field the owner explicitly
  flagged (`owner_name`). A fuller "booking details" form is a separate, larger decision
  (probably its own spec entry) — not scoped here.
- **Clearing `owner_name` on `booked → available` or `registered → available`.** Explicitly
  rejected in §3 — the field is sticky by design so Undo works, and no acceptance
  criterion asks for scrubbing it.
- **Editing `owner_name` on an already-booked plot without a status change.** Out of
  scope — this plan only wires the field into the transition that creates a booking.
- **Retroactively backfilling `owner_name` on the 26 real Shree Vatika rows** — those were
  set (or left null) by `import-seed.ts`'s CSV at M2/M6 and are untouched by this plan.

## 6. Failure modes (spec/00-rules.md checklist)

1. **Partial writes** — unchanged from the existing `apply_plot_transition()` body: the
   `owner_name` column is set in the same `update plots ...` statement as `status` and
   `version`, inside the same transaction as the `plot_history` insert. No new partial-write
   surface — one more column in an existing atomic statement, not a second statement.
2. **Idempotency** — a double-tap on "Mark Booked" sends the same `p_owner_name` twice;
   the second call fails on the existing version check (`version_conflict`) before it ever
   reaches the `update`, same as today's double-tap protection. No new idempotency risk.
3. **Concurrency** — unchanged; the existing `select ... for update` row lock covers the
   whole row, including the new column write. Two concurrent bookings with different buyer
   names on the same plot: one wins with its name, one gets a named conflict and must
   retry — same shape as the existing concurrent-write test, extended to assert on
   `owner_name` too.
4. **Orphans** — N/A; no new referenced entity, `owner_name` is a plain text column with
   no join.
5. **Dead computation** — N/A; nothing is derived from `owner_name`, it is stored verbatim
   from what the user typed, same as `updated_by`/`changed_by` already are.
