# 07 — M7: PWA install and offline reads

**Tier 1** (`spec/07-map-pwa.md`, `CLAUDE.md`'s risk table lists `apps/map/src/pwa/**` and
`apps/map/public/sw.js` explicitly). `/plan` then `/review`. A bad service worker serves
stale data indefinitely and is painful to un-deploy.

## 1. Context already true

- **Goal (`spec/07-map-pwa.md`)**: installable on an iPhone home screen; opens and shows
  last-known colony state with no network. Acceptance criteria 1, 2, 4 are manual/real-device;
  criterion 3 is DevTools-verified across two builds; criterion 5 explicitly says "not a
  unit test." This plan builds the automatable substrate and states plainly which
  criteria stay manual — it does not fake device verification.
- **D-001** (accepted): PWA on Cloudflare Pages, not a native app — this is the milestone
  that makes that decision real.
- **D-008** (provisional): read-only offline; writes require connectivity. This plan does
  not add offline writes, queueing, or background sync — reads only, per D-008.
- **D-011** (accepted): no auth until M8, app must not be deployed to a public URL before
  then. Unaffected by this plan; noted so the offline cache is not mistaken for a security
  boundary — it caches whatever the anon key could already read.
- **No PWA scaffolding exists yet**: no `apps/map/src/pwa/`, no `public/manifest.*`, no
  `public/sw.js`, no icons beyond `public/favicon.svg` (a decorative multi-filter SVG, not
  icon-shaped — new square icons are needed for `apple-touch-icon`/manifest `icons`, iOS
  ignores SVG icons in the manifest). `index.html` currently has no manifest link, no
  `apple-mobile-web-app-capable`, no SW registration.
- **Vite serves `public/` unprocessed at the build root** — `apps/map/public/favicon.svg`
  → `/favicon.svg` in `dist/`. A hand-authored `public/sw.js` becomes `/sw.js` with no
  bundler plugin, matching CLAUDE.md's risk-table path exactly. **No `vite-plugin-pwa` or
  Workbox dependency is added** — the service worker is one hand-written, reviewable file,
  consistent with D-014's pinned stack (pnpm + Vite + Vitest + Wrangler, no extra build
  tooling) and easier to reason about at Tier 1 than a generated precache manifest.
- **Colony SVG geometry is already inlined, not fetched** — `ColonyMap.tsx:6` does
  `import colonySvgRaw from "…/colony.svg?raw"`, so it ships inside the hashed JS bundle.
  "colony SVGs cached aggressively" (spec/07) is satisfied by app-shell caching of that
  bundle — no separate SVG fetch/cache path is needed. Do not add one (see §4).
- **Reuse by exact path:**
  - `apps/map/src/lib/sync/freshness.ts`'s `formatFreshnessLabel(lastSyncedAt, now, online)`
    — already produces the exact "Offline — last synced Xh ago" string spec/07 asks for.
    The offline-cache code must call this, not reimplement duration formatting.
  - `apps/map/src/components/FreshnessIndicator.tsx` — already renders `{label, offline}`,
    presentational, no changes needed; the offline-read path just needs to feed it the
    right label/offline values.
  - `apps/map/src/lib/sync/attachSync.ts` — owns the initial `loadPlotStatuses` call and
    the online/offline signal (`navigator.onLine`, channel status). This is the one place
    that needs a fallback branch: when the initial fetch fails while offline, read from
    the new IndexedDB cache instead of leaving the map blank.
  - `apps/map/src/lib/colony/plotStatus.ts`'s `loadPlotStatuses(client, colonyId)` — the
    online path stays exactly as-is; the cache module wraps it, it does not replace it.
  - `apps/map/src/lib/colony/listColonies.ts`'s `loadVerifiedColonies` — `App.tsx` calls
    this on mount; it also needs an offline fallback (see §2.3) so the colony picker isn't
    empty on a cold, offline open.

## 2. The exact task

1. **Icons** — generate a square app icon (reuse the existing brand mark's colour/shape
   language from `favicon.svg`, redrawn as a simple square glyph; do not attempt to
   auto-crop the existing multi-filter SVG, it isn't square or icon-safe). Produce
   `apps/map/public/icons/icon-192.png` and `icon-512.png` (the two sizes both the web
   manifest and iOS `apple-touch-icon` need) plus one `apple-touch-icon.png` (180×180, the
   iOS home-screen size) via a one-off script (`apps/map/scripts/generate-icons.ts` using
   an SVG-to-PNG approach already reachable from `devDependencies`, or a static hand-drawn
   SVG rasterised once and committed — do not add a new image-processing dependency for a
   one-time task; if nothing in the current toolchain rasterises SVG, draw the PNGs
   directly and commit them, no script). Commit the output PNGs; the script (if any) is
   not part of the build.
2. **`apps/map/public/manifest.webmanifest`** (new) — `name`, `short_name`, `start_url: "/"`,
   `display: "standalone"`, `background_color`, `theme_color` (reuse the brand purple
   `#863bff` from `favicon.svg`), and an `icons` array pointing at the 192/512 PNGs.
3. **`apps/map/index.html`** — add `<link rel="manifest" href="/manifest.webmanifest">`,
   `<link rel="apple-touch-icon" href="/icons/apple-touch-icon.png">`,
   `<meta name="apple-mobile-web-app-capable" content="yes">`,
   `<meta name="apple-mobile-web-app-status-bar-style" content="default">`,
   `<meta name="theme-color" content="#863bff">`. No splash-screen `<link
   rel="apple-touch-startup-image">` entries — iOS auto-generates a splash from the
   manifest icon + theme colour on modern versions; hand-crafted per-device-size splash
   images are a maintenance burden with no acceptance criterion requiring them (see §4).
4. **`apps/map/public/sw.js`** (new, hand-written, under the 250-line cap) —
   - `CACHE_NAME = "colony-map-v1"` (a literal version string baked into the file, see
     §3 pinned constraint on bumping it).
   - `install`: precache the app shell — `/`, `/index.html`, `/manifest.webmanifest`, the
     icon files. Cannot precache hashed `/assets/*.js`/`.css` (names change per build,
     unknown at SW-authoring time) — those are cached at runtime instead (below). Call
     `self.skipWaiting()` so a new SW activates without waiting for all tabs to close —
     paired with the versioned cache name so an old SW's cache is deleted on activate, not
     kept around indefinitely (spec/07's "clear upgrade path").
   - `activate`: delete any cache whose name isn't `CACHE_NAME`, then `self.clients.claim()`.
   - `fetch`: two strategies —
     - Navigation requests (`event.request.mode === "navigate"`): network-first, falling
       back to the cached `/index.html` on failure (offline app shell).
     - Same-origin `GET` requests under `/assets/` (Vite's hashed build output directory):
       cache-first, populate the cache on first successful fetch. Hashed filenames mean a
       cache-first strategy is safe — a changed asset gets a new URL, never a stale hit.
     - Everything else (cross-origin, Supabase API calls, non-GET): pass through to the
       network untouched, no caching. Offline reads come from IndexedDB (below), not from
       caching Supabase responses in the SW — the SW's cache is for static build output
       only.
5. **`apps/map/src/pwa/registerServiceWorker.ts`** (new) — `if ("serviceWorker" in
   navigator)`, registers `/sw.js` on `window.load`. Called once from `main.tsx`.
6. **`apps/map/src/pwa/offlineCache.ts`** (new) — thin wrapper over the native
   `indexedDB` API (no new dependency — see §3), one object store `plot-snapshots` keyed
   by `colonyId`, storing `{ statuses: Record<string, PlotStatus>, colonies: ColonyRow[],
   savedAt: string }`. Two functions: `saveSnapshot(colonyId, statuses, colonies)` and
   `loadSnapshot(colonyId): Promise<Snapshot | null>`. DOM-free, matches the
   `lib/colony/*` domain-module shape even though it lives under `src/pwa/` (it's PWA-specific
   persistence, not general domain logic — kept out of `lib/colony` on purpose, see §3).
7. **`apps/map/src/lib/sync/attachSync.ts`** — on the initial `loadPlotStatuses` call, on
   success call `saveSnapshot`; on failure, check `navigator.onLine === false` and if so
   call `loadSnapshot`, apply its statuses via the existing `applyStatuses` callback, and
   set the freshness label from its `savedAt` via `formatFreshnessLabel(new
   Date(savedAt), new Date(), false)` — reusing the exact function named in §1, not a new
   one.
8. **`apps/map/src/App.tsx`** — same fallback shape for the colony list: if
   `loadVerifiedColonies` rejects and `navigator.onLine === false`, read a cached colony
   list from `offlineCache` (extend the snapshot to also be saved keyed by a fixed
   `"__colonies__"` key, or a second tiny store — implementer's call, not pinned) instead
   of immediately showing the `loadError` message. Online failures keep showing
   `loadError` unchanged (that's a real problem, not an offline state).
9. **`apps/map/src/features/pwa-install/InstallInstructions.tsx`** (new) — one-time
   screen: a short sentence-case explanation ("Add Colony Map to your home screen") plus
   the exact iOS steps (Share → Add to Home Screen), and one screenshot image (reuse or
   crop an existing app screenshot if one exists in the repo; otherwise a simple annotated
   static image is acceptable — this is UI content, not logic). Shown once, gated by a
   `localStorage` flag (`colony-map:install-instructions-seen`, same pattern as
   `lib/identity/actor.ts`'s `ACTOR_STORAGE_KEY`), dismissible. Wire into `App.tsx` after
   the actor gate, before the colony picker — matches where `NamePrompt` already sits in
   the flow.
10. **Tests** (new):
    - `apps/map/src/pwa/offlineCache.test.ts` — save then load round-trips a snapshot;
      loading a colony with no saved snapshot returns `null`. Requires `fake-indexeddb`
      as a new devDependency (jsdom does not implement `indexedDB`; the project has no
      existing polyfill for it) — add it, install it in `src/test/setup.ts` alongside the
      existing jsdom setup.
    - `apps/map/src/features/pwa-install/InstallInstructions.tsx` test — renders once,
      dismiss sets the localStorage flag and calls its close callback (same pattern as
      `NamePrompt.test.tsx` if one exists, else `ColonyPicker.test.tsx`'s presentational
      style).
    - No test drives `public/sw.js` itself — service worker execution isn't reachable from
      Vitest/jsdom. Its correctness is criteria 1–5 in §5, all manual/DevTools, matching
      what spec/07 itself states.

## 3. Pinned constraints

- **Cache name is a literal string bumped on every SW change that must invalidate old
  caches**: `colony-map-v1`. Any future edit to `sw.js`'s caching behaviour bumps this to
  `-v2`, etc. — the `activate` handler's delete-other-caches logic is what makes an old
  version replaceable (spec/07 criterion 3's whole point). Do not make this dynamic
  (build hash, timestamp) — a human-readable literal is what makes "did the SW update"
  answerable by reading the file.
- **Offline is read-only** (D-008). No mutation queue, no retry-on-reconnect for writes.
  `PlotStatusActions.tsx`'s Save/Undo path is untouched by this plan — if a write is
  attempted offline it fails exactly as it does today (network error surfaces to the
  user), not silently queued.
- **No new runtime dependency for IndexedDB** — hand-write against the native `indexedDB`
  API in `offlineCache.ts`. `fake-indexeddb` is a *dev*-only test dependency, never
  imported outside `*.test.ts`/`setup.ts`.
- **The SW never caches Supabase API responses.** Plot/colony data offline comes only from
  the explicit IndexedDB snapshot written by `attachSync.ts`/`App.tsx`, never from the
  service worker intercepting `fetch` to the Supabase REST/Realtime endpoints. Mixing the
  two would let a SW-cached stale API response bypass the freshness label entirely —
  exactly the "cached data must never render without its age" rule spec/07 states.
- **`offlineCache.ts` lives under `src/pwa/`, not `src/lib/colony/`** even though it's
  DOM-free like the other domain modules — it's PWA-specific persistence (a cache), not
  a read of the source of truth, and NAVIGATION.md's Feature index should list it under a
  new PWA row, not folded into the M2/M6 colony rows.
- **`apple-touch-startup-image` splash screens are out of scope** (§4) — do not add
  per-device splash image files or the associated `<link>` tags.

## 4. Non-goals

- **Splash screen images.** iOS 15+ synthesizes one from the manifest; hand-authoring the
  historical per-device-resolution `<link rel="apple-touch-startup-image">` set is real
  effort with no acceptance criterion asking for it.
- **Offline writes / background sync / write queueing.** D-008 pins reads-only; adding a
  queue is a separate, larger decision this plan does not make.
- **Caching the colony SVG as a separate network resource.** It's already inlined in the
  JS bundle (§1) — do not add a `fetch`/cache path for `fixtures/**/colony.svg`, that
  would be caching something that was never fetched at runtime in the first place.
- **`vite-plugin-pwa`, Workbox, or any SW-generation tooling.** Hand-written `sw.js` only
  (§1, §3).
- **Push notifications, background fetch, periodic sync, or any other SW capability beyond
  install/offline-shell/offline-read.** Not asked for by spec/07.
- **Android-specific install-prompt handling (`beforeinstallprompt`).** The owner's fleet
  is iPhones (`spec/07`'s framing, "Safari not Chrome"); Android's native install banner
  needs no code from this app to work and isn't tested here.

## 6. Failure modes (spec/00-rules.md checklist)

1. **Partial writes** — N/A for the SW/manifest/install-screen work; no state writes.
   For `offlineCache.ts`: an IndexedDB `put` either commits or the transaction aborts —
   no partial snapshot (statuses without colonies or vice versa) is ever written, since
   both are written in one object per `saveSnapshot` call, not two separate calls.
2. **Idempotency** — `saveSnapshot` overwrites the prior snapshot for that `colonyId`
   wholesale; calling it twice in a row is safe. SW `install`/`activate` are themselves
   idempotent by the Cache API's own contract (re-adding an already-cached URL is a
   no-op).
3. **Concurrency** — N/A. No two writers ever race on the same IndexedDB key; only the
   single sync-attach path writes snapshots, one colony at a time, one tab at a time (no
   cross-tab coordination attempted or needed — a second tab just overwrites with its own
   equally-valid snapshot).
4. **Orphans** — an old cache left behind by a stale `CACHE_NAME` after a version bump
   would leak storage forever; the `activate` handler's delete-other-caches step (§2.4)
   exists specifically to prevent this. If a future SW edit forgets to bump `CACHE_NAME`,
   old and new assets would collide silently — this is why §3 pins the bump as a rule, not
   a suggestion.
5. **Dead computation** — offline snapshots are only ever read on a demonstrated fetch
   failure while `navigator.onLine === false`; the online path never touches
   `offlineCache.ts` at all, so there's no wasted read/write on the common path beyond one
   `saveSnapshot` call per successful sync (already necessary — that's what makes offline
   possible next time).
