# 04 — M5: Realtime and the freshness indicator

**Tier 1.** Touches a migration and `apps/map/src/lib/sync/` (both on the tier-1 path
list). `/plan` before `/build`, `/review` before `/wrap`.

## 1. Context already true

- **Goal (spec/05-map-realtime.md):** when one person marks a plot sold, the other four
  see it change on the map within ~1s without refreshing, and a freshness indicator is
  always visible so nobody trusts stale data. Full acceptance table is spec/05's, cited
  again in §5 below.
- **`plots.status` is written by exactly one function**, `applyPlotTransition()`
  (`apps/map/src/lib/plot-status/applyPlotTransition.ts`) — unchanged by this task. M5
  adds a **read/subscribe** path only, no new writer.
- **`data-status` is a runtime DOM attribute, never written into the SVG** (D-004).
  `ColonyMap.tsx` already has the exact pattern to extend: `loadPlotStatuses()` on mount
  sets `data-status` on each `.plot` node directly
  (`apps/map/src/components/ColonyMap.tsx:72-78`), and `handlePlotStatusChange()`
  (`ColonyMap.tsx:109-111`) does the same single-node update after the local actor's own
  save. The realtime handler in this task is a **third call site of the same pattern** —
  `svgEl.querySelector(\`#${svgId}\`)?.setAttribute("data-status", newStatus)` — not a new
  mechanism.
- **Reuse by exact path:**
  - `getBrowserDbClient()` (`apps/map/src/lib/db/browserClient.ts`) — the same client
    `ColonyMap.tsx` already holds in `clientRef`. The realtime channel is opened on this
    same client instance, not a second connection.
  - `loadPlotStatuses(client, colonyId)` (`apps/map/src/lib/colony/plotStatus.ts`) — the
    reconnect refetch (spec/05 "refetch rather than trusting no events were missed")
    calls this exact function again, the same one the initial mount already uses.
  - `PlotStatus` type (`apps/map/src/lib/db/types.ts`) — three values now
    (`available`/`booked`/`registered`, D-013 amended). Nothing about the type changes.
  - **Not** `formatRelativeTime` (`apps/map/src/shared/format.ts`) — it renders an
    absolute clock time with day context ("2:40 pm today"), which is right for
    `plot_history` attribution but wrong for spec/05's genuinely relative "Updated 2 min
    ago" / "3h ago" style. This task adds a new, separate pure formatter (§2) rather than
    repurposing that one — do not try to make one function serve both call shapes.
- **Layer boundary (NAVIGATION.md):** `lib/sync/` may import `lib/db`, may not import
  `src/components`. In practice `ColonyMap.tsx` already imports directly from `lib/db`
  and `lib/colony` despite the layer table's stricter "Components may not import
  lib/db" line — a pre-existing gap, not this task's to fix (see §4). `lib/sync/` itself
  stays framework-free (plain functions, callback-based), matching how `lib/colony/
  plotStatus.ts` stays DOM-free and lets `ColonyMap.tsx` own the `useEffect`/DOM-write
  side. The new freshness-indicator UI is a small presentational component under
  `apps/map/src/components/`, owned and driven by `ColonyMap.tsx`'s state, the same
  relationship `ColonyMap.tsx` already has with `PlotDetailSheet`.
- **`plots` is not yet in the `supabase_realtime` publication.** Grepped both existing
  migrations — no `alter publication` statement anywhere. Without it, `postgres_changes`
  subscriptions silently receive nothing; this is the one schema change this task needs.
- **`--colony-status-hold` is already the established generic warning-accent token**
  (`apps/map/src/styles/colony-theme.css:25`, `#c0392b`), reused by
  `plot-detail-sheet.css` for the conflict banner and warning text (docs/plans/03.md §2
  task 14 pinned this reuse explicitly). The offline state of the freshness indicator
  reuses the same token — do not introduce a second warning colour.
- **D-008 (offline writes) is provisional but currently enforced**: writes require
  connectivity. This task does not touch the write path or Save-button disabling — that
  is already true today because `applyPlotTransition` simply fails over a dead
  connection; spec/05's "Save control is disabled and says why" line is **not** in this
  task's build list (see §4 non-goals) unless acceptance criterion 3/4 turn out to need
  it, which they don't — they only test the indicator and reconnect refetch.

## 2. The exact task

1. **New migration** `apps/map/supabase/migrations/20260815000000_m5_realtime_publication.sql`:
   ```sql
   alter publication supabase_realtime add table plots;
   ```
   with a one-line comment citing spec/05 and noting `plot_history` is deliberately not
   added (§4 non-goals). No RLS/grant change needed — Realtime authorizes through the
   same anon key and existing permissive `plots_permissive_all` policy (D-011).

2. **`apps/map/src/lib/sync/freshness.ts`** (new) — pure, DOM-free, unit-tested:
   - `formatFreshnessLabel(lastSyncedAt: Date, now: Date, online: boolean): string`.
   - Thresholds (named constants, each with a one-line comment — tier-2/tier-1 numbers
     rule): under 60s → `"just now"`; under 3600s → `` `${floor(s/60)} min ago` ``;
     3600s and over → `` `${floor(s/3600)}h ago` ``.
   - `online: true` → `` `Updated ${duration}` `` (e.g. "Updated 2 min ago", "Updated
     just now"). `online: false` → `` `Offline — last synced ${duration}` `` (matches
     spec/05's literal example string).

3. **`apps/map/src/lib/sync/subscribePlots.ts`** (new):
   - `export type SyncConnectionStatus = "connected" | "disconnected"`.
   - `subscribePlotChanges(client, colonyId, handlers): () => void` where `handlers =
     { onChange: (svgId: string, status: PlotStatus) => void; onStatusChange: (status:
     SyncConnectionStatus) => void }`.
   - Opens exactly one channel: `client.channel(\`plots-changes-${colonyId}\`).on(
     "postgres_changes", { event: "UPDATE", schema: "public", table: "plots", filter:
     \`colony_id=eq.${colonyId}\` }, (payload) => handlers.onChange(payload.new.svg_id,
     payload.new.status)).subscribe((status) => handlers.onStatusChange(status ===
     "SUBSCRIBED" ? "connected" : "disconnected"))`.
   - Returns an unsubscribe function that calls `client.removeChannel(channel)` — the
     caller's `useEffect` cleanup calls this, same discipline as the existing `cancelled`
     flag pattern in `ColonyMap.tsx`'s mount effect.
   - `event: "UPDATE"` only — no INSERT/DELETE (§4 non-goals; plots are only ever
     inserted by the one-off seed import, never during normal use).

4. **`apps/map/src/components/FreshnessIndicator.tsx`** (new) — presentational only:
   `{ label: string; offline: boolean }` props, renders one `<p>` with
   `.colony-freshness-indicator` (+ `.is-offline` when `offline`). No state, no effects.

5. **`apps/map/src/components/ColonyMap.tsx`** — extend the existing mount effect and add
   state:
   - New state: `lastSyncedAt` (Date, set on initial `loadPlotStatuses` success, on every
     realtime `onChange`, and on every successful reconnect refetch — never on a failed
     fetch), `browserOnline` (`navigator.onLine`, updated via `window` `online`/`offline`
     listeners), `channelStatus` (`SyncConnectionStatus`, from `onStatusChange`),
     `freshnessLabel` (string, recomputed on a tick — see below).
   - `offline` displayed state = `!browserOnline || channelStatus === "disconnected"`.
   - After the initial `loadPlotStatuses` promise resolves, call `subscribePlotChanges`
     on the same client; in `onChange`, `setLastSyncedAt(new Date())` and apply
     `data-status` directly via `querySelector` (same one-liner as
     `handlePlotStatusChange`).
   - Reconnect refetch: track "was offline" via a ref; when the derived `offline` value
     transitions `true → false`, call `loadPlotStatuses` again, reapply `data-status` to
     every plot (full reapply, not just the changed one — "refetch rather than trusting
     no events were missed", spec/05), then `setLastSyncedAt(new Date())`.
   - A `setInterval` tick (named constant, see §3) recomputes `freshnessLabel` from
     `lastSyncedAt`/`now`/`offline` via `formatFreshnessLabel` — this is what makes
     acceptance criterion 2 ("age is real, not a fixed string") true; without a tick the
     label would freeze at whatever it was computed at.
   - Effect cleanup: remove `window` listeners, call the `subscribePlotChanges`
     unsubscribe function, clear the interval — mirrors the existing `cancelled`/`map.
     remove()` cleanup already in this effect.
   - Render `<FreshnessIndicator label={freshnessLabel} offline={offline} />` inside the
     existing `colony-map-container` div, alongside `colony-scale-note`.

6. **`apps/map/src/styles/colony-theme.css`**:
   - `.plot { transition: fill 150ms ease-out; }` → `400ms` (spec/05: "Fill transitions
     over ~400ms on a realtime change... worth the effort"). This is the same rule that
     already fires for the local actor's own save (`handlePlotStatusChange`) — one rule,
     applies to both origins of a `data-status` write, not two code paths.
   - New `.colony-freshness-indicator` rule, positioned top-left (mirrors
     `.colony-scale-note`'s bottom-left placement, `.colony-dev-click-badge`'s top-right —
     the fourth corner is free), quiet/neutral styling by default.
   - `.colony-freshness-indicator.is-offline` — `color: var(--colony-status-hold)` (the
     established warning-accent reuse, see §1), matching how `plot-detail-sheet.css`
     already uses that token for its conflict banner.

7. **Tests:**
   - `apps/map/src/lib/sync/freshness.test.ts` (new) — pure unit tests: under-60s →
     "just now" (both online/offline phrasing), minute boundary, hour boundary, spec's
     literal "Offline — last synced 3h ago" example reproduced exactly.
   - `apps/map/src/lib/sync/subscribePlots.test.ts` (new) — live integration test against
     the local Supabase instance, same two-independent-client pattern already
     established in `applyPlotTransition.test.ts:64-176` (`getBrowserDbClient()` called
     twice, a scratch colony/plot created via `insertColony`/`insertPlots`). One client
     subscribes via `subscribePlotChanges`; the other calls `applyPlotTransition` (the
     real write path) on the scratch plot. Assert the subscriber's `onChange` fires with
     the new status within a generous test timeout — pin **5000ms** (spec's own
     acceptance bar is "under 2s" over a real network between two browsers; 5s leaves
     headroom for CI/local Docker jitter while still catching a genuinely broken
     subscription). Use a `Promise` + `setTimeout` reject, not a fixed `sleep`.
   - Baseline test count going into this task: **35** (per `PROGRESS.md`'s last verified
     gate run). Report the new total after `/build`.

## 3. Pinned constraints

- **Fill transition: 400ms**, spec's own number, applies via the existing shared `.plot`
  rule (not a new class).
- **Freshness tick interval: 15000ms (15s).** Not specified by spec/05; chosen so a human
  watching for 5 minutes (acceptance criterion 2) sees the label visibly advance multiple
  times without a wasteful sub-second re-render loop. Named constant in `ColonyMap.tsx` or
  `lib/sync/freshness.ts` (whichever the label-recompute code lives in) with a comment
  citing this reasoning.
- **Freshness label thresholds: <60s "just now", <3600s "N min ago", ≥3600s "Nh ago"**,
  floor-rounded. These produce spec's own literal examples ("Updated 2 min ago", "Offline
  — last synced 3h ago") — do not change the abbreviation style (`h`, not `hr`/`hours`).
- **Subscription scope: `UPDATE` events on `plots`, filtered to one `colony_id`.** Not all
  colonies, not INSERT/DELETE, not `plot_history`.
- **Connection status is the AND of two signals**: `navigator.onLine` (via `window`
  `online`/`offline` events — this is what DevTools' offline mode toggles, and it fires
  synchronously, which is why acceptance criterion 3's 10s bar is trivially met) and the
  realtime channel's own `SUBSCRIBED`/non-`SUBSCRIBED` status (catches a server-side drop
  that leaves the browser's own network up). Offline if either says disconnected.
- **Reconnect always does a full `loadPlotStatuses` refetch**, never a partial catch-up —
  pinned directly by spec/05 ("refetch rather than trusting that no events were missed").
- **No new write path.** `applyPlotTransition()`'s signature, the RPC, and the
  atomicity/concurrency mechanism are untouched by this task.

## 4. Non-goals

- Offline write queue or disabling the Save button — D-008 already blocks offline writes
  by simply failing the request; spec/05's "Save control is disabled and says why" line
  is not required by any of this milestone's acceptance criteria and is not built here.
  If a future session wants it, it is a small, separate Tier 1 change to
  `PlotStatusActions.tsx`.
- Offline **reads** from a cache (service worker) — explicitly M7 per spec/05's own
  non-goals section.
- Auto-refreshing an already-open `PlotDetailSheet` when its plot changes via someone
  else's realtime write. Spec/05's acceptance criteria only test the map's fill and the
  freshness indicator; the sheet already has its own manual "Refresh" affordance for the
  conflict case. Wiring the sheet into the realtime stream is a reasonable follow-up, not
  part of this task.
- Fixing the pre-existing `ColonyMap.tsx` → `lib/db`/`lib/colony` direct-import gap
  against NAVIGATION.md's stated Components-layer boundary — noted, not fixed (note, don't
  fix — `PROGRESS.md` → Deferred).
- `plot_history` realtime, or adding it to the publication.
- Any change to `applyPlotTransition()`, the migration from M4, or `PlotStatusActions.tsx`.

## 6. Failure modes (spec/00-rules.md checklist)

This task adds no new write path — `applyPlotTransition()` is untouched — so most of the
five don't apply directly. Walking them anyway, as tier-1.md requires:

1. **Partial writes** — N/A. No new writer; realtime only observes writes
   `applyPlotTransition()` already makes atomically.
2. **Idempotency** — a realtime `UPDATE` event and the local actor's own optimistic
   `onPlotStatusChange` call can both fire for the same write (the actor sees their own
   change twice: once locally, once echoed back over the subscription). Both set the same
   final `data-status` value from the same source of truth, so a duplicate write is a
   no-op, not a bug — but the effect's cleanup must still properly unsubscribe/resubscribe
   exactly once per mount (React 18 strict-mode double-invoke in dev is the concrete risk;
   reuse the existing `cancelled`-flag discipline from the mount effect to guard it).
3. **Concurrency** — N/A to this task's write path (unchanged). The realtime channel
   itself has no concurrency hazard — it is read-only fan-out from Postgres's WAL.
4. **Orphans** — a realtime payload's `svg_id` could in principle match no `.plot` node if
   data ever drifted from the SVG; the existing `querySelector(...)?.setAttribute(...)`
   pattern already degrades to a harmless no-op rather than a crash, same as the initial
   load path. No new validation needed — import-time validation (M2) is what actually
   prevents this from happening with real data.
5. **Dead computation** — N/A. No derived fields touched.
