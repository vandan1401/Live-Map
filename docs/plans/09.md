# 09 — M8: auth (username/password) + RLS lockdown (spec/08-map-auth.md)

**Tier 1.** Touches `apps/map/supabase/migrations/**` and `apps/map/src/lib/{plot-status,
sync,auth}/**` — both in CLAUDE.md's risk table. `/plan → /build → /review`.

This is `spec/08-map-auth.md`'s M8, "the milestone that makes the app safe to deploy."
Plan numbering on disk stays sequential (`docs/plans/09.md`), not milestone-aligned — see
`docs/plans/08.md`'s own note on this.

**Two decisions were pinned by the user before this plan was written** (asked directly,
since they are genuine product/business calls, not implementation detail):

1. **Auth is username + password, not magic links** — explicit, deliberate override of
   D-003 ("Supabase Auth magic links... no passwords, no reset flow to build"). The user's
   own words: "we do auth a little different — usernames and passwords no email needed."
   Approved technique: each username maps to a synthetic, invisible internal email
   (`{username}@colony.local`) so Supabase Auth's session/JWT/`auth.uid()`/RLS machinery
   keeps working unmodified — the user is never shown or asked for an email address.
2. **Session length 24h, offline cache TTL 24h** (same number, deliberately — a revoked
   user's cached data goes stale on the same clock their session would have expired on
   anyway). **Backfill: stamp to a system user** — already true today (see §1) — this
   plan's job is to make the UI say so, not to write a migration.
3. **No real usernames/passwords yet** — the user will add them later. This plan ships
   with exactly one placeholder/demo account (created via a new documented script) and
   never invents real family credentials.

## 1. Context already true

- **Current RLS (`20260812120000_m2_schema.sql`)**: `for all using (true)` on `colonies`,
  `plots`, `plot_history`; broad grants to `anon`/`authenticated` including `insert`/
  `update` on `colonies`/`plots` and `insert` on `plot_history`. Permissive per D-011,
  comment-tagged "tighten at M8" on all three policies — this plan is that tightening.
- **`apply_plot_transition()`** (currently 6-arg, from `docs/plans/08.md`'s
  `20260815010000_apply_plot_transition_owner_name.sql`) takes `p_actor text` as a

  claim, not a verified identity... never from a client-supplied field." D-016's own
  blast-radius note already predicted this change: "M8 swapping the source of that string
  from a `localStorage` value to a server-derived session id changes nothing about the
  schema or `applyPlotTransition()`'s signature" — `updated_by`/`changed_by` stay plain
  `text` columns, not a foreign key, at every layer.
- **Actor threading today**: `App.tsx` shows `NamePrompt` until `lib/identity/actor.ts`'s
  `localStorage` value exists → prop-drilled `actor: string` through `ColonyMap.tsx` →
  `PlotDetailSheet.tsx` → `PlotStatusActions.tsx` (UI-only: `canUndo`'s
  `history[0].changed_by === actor`, the "recently edited" warning's
  `plot.updated_by !== actor`) and separately → `applyPlotTransition.ts` →
  `plotTransitions.ts`'s `p_actor` → the RPC.
- **`import-seed.ts` uses the anon key** (`process.env.VITE_SUPABASE_ANON_KEY`) for
  `insertColony`/`insertPlots`/`insertPlotHistory` — works only because RLS is currently
  permissive. Locking down `anon`/`authenticated` grants breaks `pnpm import:seed` the
  moment this ships, unless it switches keys.
- **Seed backfill is already the "system user" pattern the user asked for**:
  `import-seed.ts:143` writes `updated_by: "import"` and `:172` writes
  `changed_by: "import"` literally, already. `lib/db/plotHistory.ts`'s
  `fetchRecentHistoryForPlots` already excludes `changed_by: "import"` rows from the
  share-summary text (invariant 5). **The one real gap**: `PlotDetailContent.tsx:9-11`
  renders `plot.updated_by`/`row.changed_by` verbatim — a never-touched plot's detail
  sheet and history list literally read "updated by import" today. Nothing writes a
  migration for this; it's a display fix.
- **Offline machinery to build on, not replace**: `pwa/offlineCache.ts`
  (`saveSnapshot`/`loadSnapshot`/`saveColonyList`/`loadColonyList`, IndexedDB, every
  snapshot already carries `savedAt`), `lib/sync/attachSync.ts` (owns the plot-status
  offline fallback, two `loadSnapshot(colonyId)` call sites), `App.tsx` (owns the
  colony-list offline fallback, one `loadColonyList()` call site).
- **`.env`/`.env.example`** define only `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` today.
  No service-role key exists anywhere in this repo yet.
- **`supabase/config.toml`'s `[auth]` block is a stub** — `enabled = true`, `site_url`
  only, comment: "this section exists because the CLI requires it, not because sign-in is
  wired up yet." Confirmed running for real against the installed CLI, 2.114.0
  (`npx -y supabase --version`).
- **Reuse by exact path**:
  - `apps/map/src/lib/db/client.ts`'s `createDbClient(url, key)` — already
    key-agnostic (anon or service-role), reused unchanged by both the browser client and
    the new admin scripts.
  - `apps/map/src/pwa/offlineCache.ts` — extend with the TTL constant/helper, do not fork
    a parallel cache mechanism.
  - `apps/map/src/lib/plot-status/transitions.ts`'s `isLegalTransition` — unchanged,

  - The existing scratch-colony/scratch-row live-integration test pattern

## 2. The exact task

**A. Migration** — new file
`apps/map/supabase/migrations/20260815020000_m8_auth_rls_lockdown.sql`:

1. `drop function apply_plot_transition(uuid, integer, text, text, text, text);` (today's
   6-arg signature).
2. Recreate as **5-arg**: `(p_plot_id uuid, p_expected_version integer, p_new_status text,
   p_note text default null, p_owner_name text default null)` — `p_actor` is gone
   entirely, not defaulted, not ignored. `security definer`, `set search_path = public,
   pg_temp`. Body: same row-lock (`select ... for update`) / version-check / update /
   history-insert shape as today, with two changes:
   - First statement in the body: `if auth.uid() is null then raise exception 'not
     authenticated'; end if;` — fail loudly rather than ever falling back to a placeholder
     string (see Pinned Constraints — this is the exact class of bug a past `/review`
     already caught once: `getStoredActor() ?? "unknown"`).
   - `v_actor := coalesce(auth.jwt() -> 'user_metadata' ->> 'display_name', auth.jwt() ->>
     'email')` — used everywhere `p_actor` used to be (`updated_by`, `changed_by`).
3. `comment on function` (same convention as the M2/M4/owner-name migrations) explaining
   why it's `security definer` — see Pinned Constraints.
4. `grant execute on function apply_plot_transition(uuid, integer, text, text, text) to
   authenticated;` — **not** `anon`.
5. `drop policy "colonies_permissive_all" on colonies;` (and the `plots`/`plot_history`
   equivalents).
6. New policies, `select`-only, on all three tables:
   `create policy "<table>_authenticated_select" on <table> for select using
   (auth.role() = 'authenticated');`
7. `revoke insert, update on colonies, plots from anon, authenticated; revoke insert on
   plot_history from anon, authenticated;` — leave the existing `select` grants on all
   three tables untouched (see Pinned Constraints on why anon keeps `select` but is
   filtered to zero rows by RLS, not denied at the grant layer).

**B. `apps/map/supabase/config.toml`** — under `[auth]`:
- `enable_signup = false` — no public self-registration; an admin-created `auth.users` row
  **is** the allowlist, no separate table needed.
- `[auth.email]` block: `enable_confirmations = false` — accounts are created
  pre-confirmed via the admin API (`email_confirm: true` at creation), synthetic addresses
  never receive real mail.
- `[auth.sessions]` block: `timebox = "24h"`. **Verify this exact key against the
  installed CLI (2.114.0) during `/build`** — `supabase start`/`db reset` will error
  loudly on an unrecognized key, same as this file's own existing disclaimer about being
  hand-written. If the key doesn't exist in this CLI version, the 24h absolute-session
  rule must still be enforced — client-side, by recording the session's issued-at time at
  sign-in and forcing a sign-out once 24h has elapsed, checked on the same tick that
  already drives the freshness indicators. Do not silently drop the requirement either
  way.

**C. New `apps/map/src/lib/auth/`**:
- `username.ts` — pure. `usernameToEmail(username: string): string`: lowercase, trim,
  validate `^[a-z0-9_-]{2,32}$`; throw a typed/message error on an invalid username rather
  than silently producing a malformed email. Reused by both the login form and
  `create-user.ts` (§H) so validation never drifts between the two.
- `session.ts` — `signIn(client, username, password)` →
  `client.auth.signInWithPassword({ email: usernameToEmail(username), password })`,
  mapping GoTrue's error into one generic "Incorrect username or password" message (no
  user enumeration between "unknown username" and "wrong password"). `signOut(client)`.
  `getDisplayName(session): string` → `session.user.user_metadata.display_name ??
  session.user.email` — **must mirror the migration's own coalesce exactly** (display_name
  then email, nothing else), so the name a user sees for themselves in the UI never
  disagrees with what the database just wrote to `plot_history` for the same write.
- Unit-tested (`username.test.ts`): valid/invalid usernames, case-folding.

## 3. Pinned constraints

- **Synthetic email**: `{username}@colony.local`, username validated
  `^[a-z0-9_-]{2,32}$` (case-folded to lowercase) in exactly one place
  (`lib/auth/username.ts`), reused by the login form and `create-user.ts`. Never let a
  second, slightly-different validation rule exist anywhere else.
- **Session timebox: 24 hours**, via `[auth.sessions] timebox = "24h"` if the installed
  CLI supports the key; otherwise an explicit client-side 24h absolute-session
  enforcement, never silently dropped (see §B).
- **Offline cache max age: 24 hours** (`OFFLINE_CACHE_MAX_AGE_MS`), the single source of
  truth reused by both `attachSync.ts`'s plot-status fallback and `App.tsx`'s colony-list
  fallback. Expiring a snapshot means: don't render it, **and** call
  `client.auth.signOut()` — that `signOut` call is the literal mechanism that satisfies
  "forces re-auth after the pinned age" (criterion 5); a TTL check that merely hides stale
  data without invalidating the session does not satisfy the criterion.
- **`apply_plot_transition()` drops `p_actor` entirely** — no code path, tampered payload
  or otherwise, can supply a client-chosen attribution string anymore. The function raises
  loudly (`not authenticated`) rather than ever falling back to a placeholder string like
  `"unknown"` — that exact mistake (`getStoredActor() ?? "unknown"`) was already a real
  `/review` finding once (M3 log entry) and must not be reintroduced here.
- **`apply_plot_transition()` is `security definer` on purpose**, so `plots`/
  `plot_history` never need direct `insert`/`update` grants for any client role. This is
  what keeps invariant 4 ("exactly one function writes `plots.status`") true at the
  privilege layer, not just by convention. Spec/08's prose — "authenticated users read and
  write plots" — describes the *effective* capability delivered through this RPC, not a
  literal grant; granting `authenticated` raw `update` on `plots` or raw `insert` on
  `plot_history` would open a second write path, which spec/00-rules.md and tier-1.md both
  forbid. Do not add those grants even though the spec prose reads that way in isolation.
- **RLS policies are `select`-only** on all three tables, `using (auth.role() =
  'authenticated')`. `anon` keeps its existing `select` **grant** — the policy, not a
  grant denial, is what filters an anon query to `[]`, matching criterion 2's literal
  wording ("returns zero rows") rather than a permission-denied error.
- **`import-seed.ts` and `create-user.ts` both require `SUPABASE_SERVICE_ROLE_KEY`** —
  never the anon key, since both must bypass the now-locked-down RLS/grants. This key must
  never reach `import.meta.env`/the browser bundle — no `VITE_` prefix, `process.env`
  only, Node-context scripts and tests only.
- **Historical seed rows are untouched** — no migration backfills `updated_by`/
  `changed_by`. They already read the literal `"import"` (§1); only the display layer
  changes (§I).
- **D-011 is not touched by this plan.** `.claude/hooks/guard.sh` keeps blocking
  `wrangler pages deploy`/`wrangler deploy` after this ships — see Non-goals.

## 4. Non-goals

- **Real family usernames/passwords** — deferred by the user; this plan ships one
  placeholder/demo account only.
- **Removing the deploy guard / flipping D-011 to superseded** — spec/08's own "After this
  ships" section is a separate, later, manual action gated on the user live-verifying all
  six acceptance criteria for real. Not done here.
- **A password-reset UI or self-service flow** — the admin script is the only mechanism;
  extending it to also reset a password is a trivial follow-up, not required by any
  acceptance criterion, not built here.
- **Enforcing `colonies.verified = true` via RLS** — stays an app-level check (D-108,
  unrelated to this milestone).
- **Any change to the append-only trigger, the `(colony_id, svg_id)` uniqueness
  constraint, or `docs/plans/08.md`'s owner-name coalesce logic** — untouched beyond the
  signature edit needed to drop `p_actor`.
- **Rate limiting or brute-force protection on the login form** — five or six trusted
  family members, not a public signup surface; Supabase Auth's own built-in limits are
  relied on as-is.
- **A `family_members`-shaped allowlist table** — considered and rejected; an
  admin-created `auth.users` row with `enable_signup = false` already **is** the
  allowlist, and a second table would be an orphaned duplicate of what `auth.users`
  already tracks.

## 6. Failure modes (spec/00-rules.md checklist)

This plan writes state (a migration: RLS policies, grants, the RPC signature), so all
five apply:

1. **Partial writes** — unchanged from today's function body: still one Postgres
   transaction covering the `plots` update and the `plot_history` insert. The new
   `auth.uid() is null` guard runs *before* the row lock, so a rejected unauthenticated
   call never touches any row — no new partial-write surface.
2. **Idempotency** — unchanged; still gated by the existing `version` check. Dropping
   `p_actor` removes a parameter, not the conflict-detection logic.
3. **Concurrency** — unchanged row lock (`select ... for update`). New consideration: two
   different authenticated users racing the same plot now derive their names from two
   real sessions instead of two client-typed strings — same conflict shape, more
   trustworthy inputs; the existing concurrent-write test's assertions still hold.
4. **Orphans** — N/A. No new referenced entity — deliberately no `app_users`/allowlist
   table (see Non-goals); the allowlist is "an admin-created `auth.users` row exists."
5. **Dead computation** — N/A. `auth.jwt() -> 'user_metadata' ->> 'display_name'` is read
   once per call inside the function, not cached or duplicated anywhere else;
   `getDisplayName()` on the client mirrors the same coalesce so the two never disagree,
   but each computes it independently rather than one reading a value the other wrote.
