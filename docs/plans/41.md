# Plan 41 — Buyer details survive Registry done and Sold to investors (Tier 1)

Owner ask (2026-10-30): "when a plot is marked as registry done, the owner should still show, the person
who brought the plot also; if I want to mark the plot as sold to investors the owner should still be the
one whom the plot was marked booked for." Tier 1 (`lib/plot-status/**`) — `/review` after build.
Vocabulary (`spec/00-rules.md`): **Owner** = the buyer named on the plot record (`owner_name`);
Confirmed with the owner (2026-10-31): "the person who brought the plot" means the person who *bought* it,
the same person as the Owner — so **no Broker row is added** (an earlier draft added one; removed).

## 1. Context already true

- `plots.owner_name` is sticky (D-018): written only by `apply_plot_transition`'s `p_owner_name`
  through `coalesce(p_owner_name, owner_name)`, never cleared by any transition. `broker_name` is never
  touched by a transition. **The database already keeps both through registered and sold_to_investors.
  No migration is needed.** (`20261027000000_colony_statuses.sql` L155-157.)
- The *display* hides them: `features/plot-detail/PlotDetailContent.tsx` L46 shows Owner only when
  `status === "booked"` and never shows the broker; `lib/colony/searchPlots.ts` L23 gates `ownerName`
  on `status === "booked"` (D-018's stale-name guard, added by `/review`).
  `features/plot-table/PlotTableRow.tsx` already prints owner and broker for every status — unchanged.
- The *rule* blocks the move: `lib/plot-status/transitions.ts` `isLegalTransition` lets a custom status
  move only to/from `available` and between customs (plan 40 §3, flagged "owner should confirm").
  `booked -> sold_to_investors` and `registered -> sold_to_investors` are refused today.
- `isLegalTransition` is the single legality function (D-006, D-013); `applyPlotTransition()` calls it.
  Reuse: `legalNextStatuses`, `shared/format.ts` `formatStatusLabel`.
- `PlotStatusActions.tsx` derives `canBook = nextStatuses.includes("booked")` — true for *every* plot that
  may move to booked, and shows the mandatory "Buyer name" box. Once a custom status can move to booked,
  this would demand a new buyer name on `sold_to_investors -> booked` and overwrite the owner.
- `canUndo` in the same file uses `isLegalTransition(plot.status, history[1].status)`: Undo of
  `booked -> sold_to_investors` works only if the reverse edge is legal.
- Must not be reverted: D-018 stickiness and the stale-name search gate for **available** plots;
  `plot_history` append-only; the version check; the buyer-name prompt on `available -> booked`.
- Public link (`get_public_colony`) never returns owner/broker/PII — untouched (D-038 family).

## 3. Pinned constraints

- **Owner shown for every status except `available`** (booked, registered, sold_to_investors, any custom).
  Reason: a name only ever exists once a booking happened, and D-018's danger is the *un-booked* plot.
- **Reverse edges are legal** (`sold_to_investors -> booked | registered`). Reason: Undo, and fixing a
  mis-tap, would otherwise force a trip via `available` and a retyped buyer name. Costs, accepted and
  flagged: (a) a plot that went `available -> sold_to_investors` (never booked, so no owner) can now
  reach `booked`/`registered` with no buyer name; it shows "—". Bulk import can already create a booked
  plot with no owner, so this is not a new class. (b) **A stale name can show.** `owner_name` is never
  cleared (D-018), so a plot booked for X, un-booked to `available`, then moved to `sold_to_investors`
  shows "Owner: X" (search finds it by X), and its "Mark Booked" button re-books it for X with no
  prompt. Before this plan the booked-only gate hid X. Closing it needs a database or history-based
  rule, outside this plan. **Owner to confirm both.**
- `owner_name` is never cleared or rewritten by these edges: the client sends no `ownerName`, the RPC
  coalesces. **No migration, no RPC change, no new column, no new history field.** (`plot_history`
  still has no owner column — a different "owner at that time" question is out of scope, D-018.)
- Transition legality stays in TypeScript only; the DB still guards status *membership* only.
- Money fields, `version`/concurrency semantics, RLS: untouched.
- Tier 1 files touched: `lib/plot-status/**` only. Everything else is Tier 2/3.

## 6. Failure modes (writes plot state — `spec/00-rules.md`)

1. **Partial writes** — unchanged: status update + history row stay one transaction inside
   `apply_plot_transition`. No new write path.
2. **Idempotency** — double-tap still fails on the `version` check. Existing test must still pass with a
   `booked -> sold_to_investors` move.
3. **Concurrency** — unchanged semantics; the live test already races two clients on a custom status.
4. **Orphans** — no new orphan class. Two accepted risks (§3): an *owner-less* booked/registered plot
   reached via a custom status renders "—"; and a *stale* owner (booked, un-booked, then moved to a
   custom status) renders the old buyer. `buyerVisibility.test.ts` pins both.
5. **Dead computation** — `facing`/`is_corner` untouched; the show-buyer rule is one function
   (`statusShowsBuyer`), not re-derived per component.
- Also: **stale name on an un-booked plot** (D-018's original hazard) — covered by keeping `available`
  hidden in both the sheet and search, with a test for each.
