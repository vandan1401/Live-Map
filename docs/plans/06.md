# 06 — Multi-colony home screen (colony picker)

**Tier 1.** Touches `apps/map/src/lib/colony/**` and `apps/map/src/lib/db/**` (the Domain
and Data-access layers per `NAVIGATION.md`'s layer table) and changes how `ColonyMap`
receives its colony id — a shape change other code depends on. `/plan` before `/build`,
`/review` before `/wrap`.

## 1. Context already true

- **Owner's original design**: a list of colonies on open; tapping one opens its map. The
  app currently skips straight from the name prompt to the map — `App.tsx` renders
  `<ColonyMap actor={actor} />` unconditionally once an actor is set (`App.tsx:20`), and
  `ColonyMap.tsx` hardcodes `const COLONY_ID = "shree-vatika-2"` at module scope
  (`ColonyMap.tsx:18`), used in 5 places (`ColonyMap.tsx:116,156,198,205,211`).
- **The `colonies.verified` render-time gate just closed this session** — `loadPlotStatuses`
  and `loadPlotDetail` (`apps/map/src/lib/colony/{plotStatus,plotDetail}.ts`) now check
  `colonies.verified` via `fetchColonyById` and return `{}`/`null` for an unverified
  colony, matching D-108's "no code path sets it true / the app refuses `false`"
  invariant. The picker being built here must apply the **same rule at the list level**:
  an unverified colony must never appear in the list at all, not just be blocked once
  opened.
- **Only one real colony exists** (`shree-vatika-2`, `fixtures/shree-vatika-2/`). Per
  CLAUDE.md: *"`fixtures/shree-vatika-2/` is one shared demo colony... One copy,
  deliberately — two would drift."* This plan does **not** create a second real fixture,
  second `seed/*.csv`, or fabricated colony data. Proof that the picker correctly lists
  multiple colonies and filters unverified ones comes from **scratch DB rows**, the same
  pattern already used by `applyPlotTransition.test.ts` and this session's
  `plotStatus.test.ts`/`plotDetail.test.ts` (insert via `insertColony`/`insertPlots` with a
  random-suffixed id, never cleaned up — harmless residue cleared on the next
  `supabase db reset`).
- **`ColonyMap.tsx` statically imports the one real SVG at module scope**:
  `import colonySvgRaw from "../../../../fixtures/shree-vatika-2/colony.svg?raw"`
  (`ColonyMap.tsx:6`). This does not change in this plan — see §4 non-goals. The picker
  only needs `colonyId` to reach `ColonyMap` as a prop so its **data queries** (status,
  detail, sync, search, share summary) key off the selected colony; the SVG geometry
  itself stays whatever fixture is compiled in.
- **Reuse by exact path:**
  - `apps/map/src/lib/db/colonies.ts` — already has `insertColony`, `fetchColonyById`.
    Add `fetchVerifiedColonies` here (the only place `supabase.from()` may appear —
    `NAVIGATION.md`'s layer rule).
  - `apps/map/src/lib/colony/plotStatus.ts` / `plotDetail.ts` — the exact pattern to
    follow for the new `apps/map/src/lib/colony/listColonies.ts`: a thin, DOM-free
    wrapper around one `lib/db` call, unit-proven against the live local DB.
  - `apps/map/src/features/identity/NamePrompt.tsx` — the exact pattern for a new
    `apps/map/src/features/colony-picker/ColonyPicker.tsx`: presentational, takes
    callback props, no direct `lib/db` import (features may import `all src/lib/*` per
    the layer table, but this component doesn't need to — it receives the list as a
    prop, `App.tsx` owns the fetch, matching how `App.tsx` already owns `actor` state
    rather than pushing it into a feature component).
  - `apps/map/src/lib/db/browserClient.ts`'s `getBrowserDbClient()` — same client factory
    every other feature uses, no new one needed.
  - `ColonyRow` (`apps/map/src/lib/db/types.ts:24`) already has `id`, `name`, `verified` —
    everything the picker needs to render and filter. No type changes required.

## 2. The exact task

1. **`apps/map/src/lib/db/colonies.ts`** — add:
   ```ts
   export async function fetchVerifiedColonies(client: SupabaseClient): Promise<ColonyRow[]> {
     const { data, error } = await client.from("colonies").select("*").eq("verified", true);
     if (error) throw new Error(`fetchVerifiedColonies failed: ${error.message}`);
     return (data as ColonyRow[] | null) ?? [];
   }
   ```
2. **`apps/map/src/lib/colony/listColonies.ts`** (new) — `loadVerifiedColonies(client)`,
   DOM-free, calls `fetchVerifiedColonies` directly (same one-line-body pattern as
   `plotStatus.ts`'s pre-D-108-fix shape). Comment states the D-108 tie: this is the
   list-level half of the same rule `plotStatus.ts`/`plotDetail.ts` enforce at the
   single-colony level.
3. **`apps/map/src/features/colony-picker/ColonyPicker.tsx`** (new) — props:
   `{ colonies: ColonyRow[]; onSelect: (colonyId: string) => void }`. Renders a plain list
   (button per colony, name + nothing else — no plot counts, no thumbnails, see §4).
   Empty state: a sentence-case message ("No colonies yet.") if the list is empty — not a
   blank screen (Tier 3 copy rule: sentence case, plain language).
4. **`apps/map/src/App.tsx`** — new state `colonies: ColonyRow[] | null` (null = not yet
   fetched) and `selectedColonyId: string | null`. Flow after the existing actor gate:
   fetch `loadVerifiedColonies` once (on mount, after actor is set); while `colonies` is
   `null`, render nothing extra (existing loading pattern, no new spinner component —
   see `ColonyMap.tsx`'s own `client === null` handling for the precedent, if any exists;
   otherwise a bare `null` return is fine, matches this app's minimal-chrome style); once
   loaded, render `<ColonyPicker colonies={colonies} onSelect={setSelectedColonyId} />`
   if `selectedColonyId` is null, else `<ColonyMap actor={actor} colonyId={selectedColonyId} />`.
5. **`apps/map/src/components/ColonyMap.tsx`** — remove the module-level
   `const COLONY_ID = "shree-vatika-2"` (line 18). Add `colonyId: string` to `Props`
   (alongside the existing `actor: string`, same comment style). Replace all 5 remaining
   `COLONY_ID` usages (lines 116, 156, 198, 205, 211) with the prop.
6. **Tests** (new):
   - `apps/map/src/lib/colony/listColonies.test.ts` — live-integration, same scratch
     pattern as `plotStatus.test.ts`: insert one scratch colony `verified: true`, one
     `verified: false`; assert the verified one appears in `loadVerifiedColonies`'s
     result and the unverified one does not. Also assert the real `shree-vatika-2` row
     is present (proves the query isn't scoped to only scratch data).
   - `apps/map/src/features/colony-picker/ColonyPicker.test.tsx` — pure component test
     (no live DB, matches `PlotStatusActions.test.tsx`'s style): renders a list of 2
     fixture `ColonyRow`s, clicking one calls `onSelect` with that colony's `id`; renders
     the empty-state message when given `[]`.
7. **Styling** — add picker styles to a Tier 3 CSS file. Reuse `colony-theme.css` if it
   has headroom under 250 lines (check first — it was already split once this session for
   exactly this reason); otherwise a new `colony-picker.css`, same pattern as
   `plot-selection.css`'s earlier split.

## 3. Pinned constraints

- **The picker lists only `colonies.verified = true` rows.** This is D-108 applied at the
  list level — an unverified colony must be invisible here, not just refused once opened.
  Non-negotiable, same invariant the render-time gate fix (this session, earlier) already
  established for single-colony reads.
- **`ColonyMap` takes `colonyId` as a required prop, not a module constant.** Every one of
  its 5 existing `COLONY_ID` usages moves to the prop; no usage is left reading the old
  constant (a partial migration would silently query one colony while displaying another).
- **No second real fixture, no second `seed/*.csv`, no new `fixtures/` subdirectory.**
  Multi-colony proof is scratch DB rows only, inserted the same way
  `applyPlotTransition.test.ts` already does it (random suffix, no delete grant, cleared
  by the next `supabase db reset`) — never committed to the repo.
- **No colony-selection persistence** (no `localStorage` key for "last opened colony").
  Every fresh load shows the picker after the name prompt. Reversible and simple; adding
  persistence later is a small, isolated change if the owner asks for it once there's more
  than one colony to actually get tired of re-selecting.
- **The picker shows name only** — no plot counts, no thumbnail, no last-updated time.
  Those all require an extra query per colony (or a bigger one), and nothing in the
  owner's stated design asked for them. Easy to add later; not guessed at now (see §4).

## 4. Non-goals

- **Dynamic per-colony SVG geometry loading.** `ColonyMap.tsx` keeps its static import of
  `fixtures/shree-vatika-2/colony.svg`. Making the SVG source vary by `colonyId` needs
  either a second real colony's traced geometry (none exists) or `tools/pipeline` emitting
  per-colony output (pre-M9, doesn't exist). If a second real colony is ever added, wiring
  its SVG in is a follow-up task gated on that fixture existing — not this plan's job.
- **Colony creation, editing, or deletion UI.** The picker is read-only — it lists what
  `import-seed.ts` already put in the database.
- **Persisting the selected colony across reloads.** See §3.
- **Plot counts, thumbnails, or any per-colony summary data in the picker list.** See §3.
- **Changing `import-seed.ts` or any seed/fixture file.** This plan only adds a read path
  (`fetchVerifiedColonies`) and a UI layer on top of existing data.

## 6. Failure modes (spec/00-rules.md checklist)

1. **Partial writes** — N/A. This plan adds no write path; `fetchVerifiedColonies` and
   `loadVerifiedColonies` are both read-only.
2. **Idempotency** — N/A, same reason. Re-fetching the colony list is always safe.
3. **Concurrency** — N/A. No writes, no locking, no `version` field involved.
4. **Orphans** — the one real failure mode that applies: an unverified colony must never
   leak into the picker's list. This is exactly what acceptance criterion 1 proves against
   a real unverified scratch row, not just by reading the query code.
5. **Dead computation** — N/A. Nothing here is computed once and cached; the list is
   fetched fresh each app load, which is correct for a handful of colonies with no
   performance concern at this scale.
