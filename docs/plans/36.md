## 3. Pinned constraints

**Authentication / authorization**
- Every `/api/*` request except `POST /api/login` requires `Authorization: Bearer <access
  token>`. The server validates it with `client.auth.getUser(token)` using the
  service-role client (GoTrue validates signature + expiry + banned state; do not hand-roll
  JWT verification) **and** requires `user.app_metadata.role === 'super_admin'`.
  Missing/invalid token -> 401; valid token without the role -> 403 and a `denied` audit row.
- The server's own service-role client is **never signed in** as a user (login uses a
  separate throw-away anon client), so it cannot silently change role.
- Static files stay unauthenticated (they contain no data); all data is behind `/api`.
- `POST /api/login {username, password}`: throw-away anon client (`persistSession:false`),
  `signInWithPassword(usernameToEmail(username), password)`; returns `{accessToken,
  expiresAt}` only if the user has the role; otherwise 401/403 with a generic message. The
  refresh token is never sent to the browser.
- Login throttle: **5 failed attempts per 15 minutes per source IP**, then 429 for the rest
  of the window; in-memory. The attempt is **counted before** the sign-in call (so parallel
  requests cannot all pass the check); a success clears the counter.
- Source IP = `req.socket.remoteAddress` **only**. `X-Forwarded-For` is never trusted.
- No bypass flag or "dev mode" without auth, in any mode. SaaS mode requires the same login.
- The caller may not delete, deactivate, or change the org of **themself**, and may not
  touch any other `super_admin` user via these routes (403). Role is never accepted in a body.

**Binding / config**
- Listens on `ADMIN_HOST` (default `127.0.0.1`) : `ADMIN_PORT` (default `5002`; self-host
  uses `3001`). Never defaults to `0.0.0.0`. C5 sets the host to `0.0.0.0` *inside* the
  container and publishes the port bound to the Tailscale IP only.
- `SUPABASE_URL` falling back to `VITE_SUPABASE_URL`; `SUPABASE_ANON_KEY` falling back to
  `VITE_SUPABASE_ANON_KEY`; `SUPABASE_SERVICE_ROLE_KEY` (no fallback). Fail to start with a
  clear message if any is missing.

**Audit log semantics (the evidence)**
- Fail-closed, write-ahead: before any mutating action, insert an `attempt` row; if that
  insert fails, **abort and do not perform the action** (500). After the action insert an
  `ok` or `error` row; if *that* insert fails, the action stands and the response is a 500
  stating the action happened but its result row failed; print to stderr. **No response is
  sent before the result row is written** (handlers do the work; `app.ts` answers).
- An action that *reports* failure by returning (not throwing) must be turned into a throw
  inside the audited step, so it is recorded as `error`, not `ok`.
- Only methods a route actually owns are audited; a request for a route/method that does not
  exist writes no audit row and gets 404.
- Audited actions: `login` (ok/denied/throttled, single result row; if it cannot be written no
  token is issued), `create_user`, `reset_password`, `deactivate_user`, `reactivate_user`,
  `delete_user`, `reassign_user_org`, `create_org`, `regenerate_public_link`,
  `revoke_public_link`, `upload_backdrop_image`, `update_backdrop`, and `api_access` (denied).
  Pure reads are not audited; reading the audit log is not audited.
- `detail` never contains passwords, tokens or keys.
- `GET /api/audit-log?limit=&before_id=`: newest first, `limit` default **50**, max **200**,
  keyset pagination on `id`.

**User actions**
- Minimum password length **8**, enforced for create **and** reset, server-side, before any
  audit `attempt` row.
- Deactivate = GoTrue ban (`ban_duration: "876000h"`); reactivate = `"none"`. Existing access
  tokens stay valid until their normal expiry — documented limitation.
- Delete = `auth.admin.deleteUser(id)`, requires `{confirmUsername}` matching the user.
- Reset password = `updateUserById(id, {password})`; no SMTP, no email sent.

**Security boundaries**
- The service-role key must not appear in shipped code: no reference under `src/` (outside
  test infrastructure), `public/`, or in `dist/` after `pnpm build`.
- Mutating routes keep the JSON content-type check and the error-as-sentence posture.
- Nothing here changes RLS on existing tables, any RPC, or app code under `src/`.

## 6. Failure modes (`spec/00-rules.md`, "writing state")

1. **Partial writes** — an admin action touches Auth (GoTrue) and the audit table, which
   cannot share a transaction. Resolved by write-ahead `attempt` + result row: an unaudited
   mutation cannot happen; a mutation with a missing result row is detectable.
2. **Idempotency** — reset is naturally idempotent (both audited); delete of an
   already-deleted user is a 404 recorded as `error`; create of an existing username fails at
   GoTrue and is recorded as `error`. Tested.
3. **Concurrency** — two super admins on the same user: last write wins at GoTrue, both
   attempts are in the log with actor and timestamp. `plots` are not touched (D-006 unaffected).
   Parallel login attempts are counted before sign-in, so the throttle cannot be bypassed.
4. **Orphans** — deleting a user leaves `plot_history.changed_by` text untouched (no FK).
   Audit rows keep `actor_id` after the actor is deleted (no FK) so the evidence outlives the
   account.
5. **Dead computation** — none; role is a stored claim set only by `grant-super-admin`.
