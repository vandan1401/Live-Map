# Plan 26 — Public colony link: apply the owner-drawn zoom reference

**Tier 1** (`apps/map/supabase/migrations/**`; `get_public_colony` is a security-relevant,
anon-facing RPC — same designation as docs/plans/25.md). Narrow follow-on to the Leaflet+
canvas UI rework (owner ask, 2026-09-01, prior session): the public link now has real
fly-to-plot zoom on selection (`useFlyToSelectedPlot.ts`), but it falls back to the fixed
`SELECT_ZOOM` constant for every colony, because `get_public_colony()` never returned the
per-colony `COL-ZOOM-REF` extent the owner draws in AutoCAD (docs/plans/20.md, D-033).
Owner's ask, verbatim: "the public link does not follow the zoom we decided in .json."

## 1. Context already true

- `colonies.select_zoom_ref_width_px`/`select_zoom_ref_height_px` (docs/plans/20.md,
  `20260829000000_select_zoom_ref.sql`) already hold the owner-drawn rectangle's SVG-viewBox
  extent for every colony that has one — nullable, permanently, for one that doesn't.
- The authenticated map already reads these two columns straight off `ColonyRow` (no
  separate fetch, `App.tsx` → `ColonyMap.tsx` → `useFlyToSelectedPlot`) and passes them to
  `view.ts`'s `computeSelectZoom`, which falls back to the fixed `SELECT_ZOOM = 3.4` when
  either is null — the exact fallback path a public colony currently always takes, because
  `get_public_colony()`'s `colony` object is `{id, name, svg}` only.
- `usePublicColonyCanvas.ts` already calls `useFlyToSelectedPlot(mapRef, modelRef,
  selectedId, null, null)` — the two `null`s are the only thing that needs to change; the
  fly-to-zoom mechanism itself is already correct and unit-tested (`view.test.ts`).
- Same class-of-fact reasoning M19 (docs/plans/25.md) already established for
  block/number/area_sqft/length_ft/breadth_ft: these two columns are pure geometry (a
  rectangle's pixel extent), never listed among the PII/money columns `get_public_colony()`
  withholds, and already visible to anyone who can see the SVG at all (the map's own framing
  reveals its rough proportions regardless).

## 2. The exact task

**A. New migration,
`apps/map/supabase/migrations/<timestamp>_m20_public_link_zoom_ref.sql`:**
`create or replace function get_public_colony(p_token uuid)` — same signature, same grants.
The `colony` object in the returned jsonb gains `'select_zoom_ref_width_px',
v_colony.select_zoom_ref_width_px, 'select_zoom_ref_height_px',
v_colony.select_zoom_ref_height_px` alongside `id`/`name`/`svg`. The initial `select ... into
v_colony` gains these two columns. Update `comment on function` to name them explicitly,
carrying forward the two rationale comments M19 already preserved from M17 (verified/svg-not-
null check, no org_id check). No other statement in this migration.

**B. `apps/map/src/lib/db/types.ts`:** `PublicColonyResult`'s `colony` object gains
`select_zoom_ref_width_px: number | null; select_zoom_ref_height_px: number | null` — same
nullable-numeric type `ColonyRow` already uses for these columns, not re-derived.

**C. `apps/map/src/features/public-colony/PublicColonyView.tsx`:** pass
`found.colony.select_zoom_ref_width_px`/`_height_px` through to `usePublicColonyCanvas`
instead of the hook synthesizing `null`/`null` itself.

**D. `apps/map/src/components/map/usePublicColonyCanvas.ts`:** accept
`selectZoomRefWidthPx`/`selectZoomRefHeightPx` as args (mirroring `useColonyCanvas.ts`'s own
prop names exactly) and pass them into `useFlyToSelectedPlot` instead of the hardcoded
`null, null`.

**E. Tests:** `publicColony.test.ts`'s existing "no PII/money column anywhere" scratch-colony
test gains a non-null `select_zoom_ref_width_px`/`_height_px` on the scratch colony insert and
asserts both come back unchanged through `loadPublicColony`; the existing forbidden-column
loop stays unmodified. `PublicColonyView.test.tsx`'s chrome-smoke stub gains the two fields
(nullable is fine, matching most real colonies) so the type stays honest end to end.

## 3. Pinned constraints

- The RPC's column list stays explicit and hand-written — same discipline M17/M19 already
  established; grep the new migration for every PII/money column name as part of review.
- No new grants, no RLS change — pure return-shape addition to an existing `security
  definer` function, same as M19.
- `useFlyToSelectedPlot`'s own fallback-to-`SELECT_ZOOM`-when-null behavior is unchanged and
  untouched (`view.ts`'s `computeSelectZoom`) — a colony with no `COL-ZOOM-REF` rectangle
  keeps behaving on the public link exactly as it does on the authenticated map today.

## 4. Non-goals

- Any change to the authenticated map's own zoom-ref handling — already correct, already
  shipped (docs/plans/20.md, D-033).
- Applying this migration to production as part of this plan's own acceptance — same posture
  as every prior migration: the owner's own explicit go-ahead, a separate step.

## 5. Acceptance criteria

- `mingw32-make verify-map` clean except the already-documented baseline drift.
- `publicColony.test.ts`'s new zoom-ref assertions pass against a live local scratch colony.
- A colony with a real `COL-ZOOM-REF` rectangle, opened via its public link, fly-to-zooms a
  tapped plot to the same framing the authenticated map would use for it — not live-verifiable
  by Claude, needs the owner's own pass once deployed (same posture as every prior visual
  session).

## 6. Failure modes

- **Partial writes / concurrency / orphans.** N/A — read-only RPC, no new write path.
- **Idempotency.** N/A — `create or replace function`, same one-time-forward shape as every
  prior migration here.
- **Dead computation.** The two new fields must actually reach `useFlyToSelectedPlot` (task
  D) — a field returned by task A but never read by the public view would be a real finding.

**Status:** complete
