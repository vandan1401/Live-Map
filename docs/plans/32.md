# Plan 32 — Backdrop alignment declared in colony.json, applied on upload

Owner direction (2026-09-12, this session, final decision after looking at the running
app): backdrop alignment (x/y/scale/rotate_deg/darken_alpha/enabled_on_admin/
enabled_on_public/attribution) should be declarable in `colony.json` itself, alongside
`select_zoom` and everything else — "good practice for future... if we add more
configuration and details" — rather than only entered through `ColonyBackdropScreen.tsx`'s
form. The image file stays a separate upload (JSON cannot carry binary data).

This supersedes the reversion logged in `PROGRESS.md`'s `## Deferred` entry from earlier
this session, with the two real problems that entry named now resolved on purpose, not
papered over:

1. **`tools/pipeline` cannot *derive* `backdrop` from a DXF — a manually aligned aerial
   photo has no geometric source — but it now *propagates* it, the same way it propagates
   every other hand-maintained field in a colony config.** Owner (2026-09-13, this session,
   immediately after the JSON-authoritative decision above): "also make changes in pipeline
   which creates json to enter map details and everything to enter the required values in
   json." `tools/pipeline/colonies/<id>.json` (the `ColonyConfig` input file
   `load_colony_config()` reads — never regenerated by a run, unlike the `colony.json`
   manifest it produces) gains an optional `backdrop` block; `build_manifest()` copies it
   verbatim into the exported `colony.json`, mirroring exactly how `select_zoom` already
   passes through. This resolves the original "hand-maintain the raw exported JSON forever"
   burden for real: the operator maintains ONE file, the `ColonyConfig` input, once, and
   every future `make export` carries it through automatically instead of silently dropping
   it. See task H below.
2. **A replace must not silently revert a freshly-tuned alignment to a stale JSON value —
   except now it's explicitly allowed to, by design, when the manifest declares
   `backdrop`.** The rule is now: **JSON is authoritative whenever it declares `backdrop`,
   on every create and every replace, no exceptions.** An operator who wants a colony's
   existing (UI-tuned) alignment left alone on a routine geometry-fix replace must simply
   not include `backdrop` in that upload's manifest — omission is the only way to say
   "leave it".

## 1. Context already true

- **Everything in `lib/colony/colonyBackdrop.ts`, the `colony-backdrops` Storage bucket,
  the 11 `colonies.backdrop_*` columns, and `20260912020000_colony_backdrop_authenticated_
  write.sql`'s RLS/grants (docs/plans/29.md/30.md) are reused exactly as they are.** This
  plan only adds a second way to call `updateColonyBackdropTransform` — automatically, from
  a parsed manifest — alongside the existing manual form in `ColonyBackdropScreen.tsx`
  (unchanged, still there for entering/adjusting values without editing JSON, and the only
  way to attach the image).
- **`select_zoom` is the precedent to mirror for the schema/type/SPEC shape** — optional
  object, present only when relevant, documented with a worked example in
  `contract/SPEC.md`. `colony`'s own schema object has no `additionalProperties: false`, so
  this is a pure addition, not a breaking one.
- **`ColonyUploadScreen.tsx`'s `upload()` function** already reaches the exact moment a
  colony's `colonyId` is known (`result.ok` inside `createColonyFromManifest(...)`'s
  `.then()`) and already transitions to a `{kind: "backdrop", colonyId, intro}` stage there
  (docs/plans/31.md) — this plan adds one more step in that same branch: apply the
  manifest's `backdrop`, if present, before setting that stage.
- **A previous attempt at this exact feature, same session, was built then reverted.**
  `/review` found five real issues: no `contract/` producer (above), the replace-overwrite
  question (resolved above), `attribution ?? ""` silently blanking the ODbL credit when
  omitted, a fetch-error path with no way to close the screen, and zero test coverage of
  the actual write. All five are pinned constraints or tasks below — this is not a second
  guess at the same design, it is the same design with every finding closed.
- **The fetch-error-path fix from that reversion stays** — `ColonyUploadScreen.tsx`'s
  post-upload `fetchColonyById` call already routes a `null` row or a thrown error to the
  closable `"failed"` stage (not a dead "Loading…" panel). Nothing here changes that.

## 2. The exact task

**A. `contract/colony.schema.json`** — add optional `colony.backdrop`, sibling to
`select_zoom`:

```json
"backdrop": {
  "type": "object",
  "required": ["transform", "darken_alpha", "enabled_on_admin", "enabled_on_public", "attribution"],
  "properties": {
    "transform": {
      "type": "object",
      "required": ["x", "y", "scale", "rotate_deg"],
      "properties": {
        "x": { "type": "number" },
        "y": { "type": "number" },
        "scale": { "type": "number", "exclusiveMinimum": 0 },
        "rotate_deg": { "type": "number" }
      }
    },
    "darken_alpha": { "type": "number", "minimum": 0, "maximum": 1 },
    "enabled_on_admin": { "type": "boolean" },
    "enabled_on_public": { "type": "boolean" },
    "attribution": { "type": "string" }
  },
  "description": "Optional. When present, this is the AUTHORITATIVE alignment for this colony's synthetic-aerial backdrop (D-036/D-047/D-048/D-049), applied on every upload/replace, overwriting whatever the colony currently has -- omit this key entirely to leave an existing backdrop untouched. A backdrop has no DXF source, so tools/pipeline cannot derive it -- but it does propagate it: declare it once in tools/pipeline/colonies/<id>.json (the hand-maintained ColonyConfig input, never regenerated by a run) and every make export carries it through into the exported colony.json verbatim -- unlike select_zoom, which is genuinely derived from COL-ZOOM-REF, this is a plain passthrough of whatever the config declares, with nothing in the drawing to compute, constrain or validate it against. Once that config file declares backdrop, IT is the value's home, not the database. attribution is required, not optional, specifically so an omitted credit is a validation error, not a silently blanked column."
}
```

`attribution` is now **required** — an intentionally empty credit is still expressible
(`"attribution": ""`), but it must be a deliberate, present value, never an accidental
omission (the exact bug the previous attempt shipped and `/review` caught).

Note: task A's schema edit was already applied earlier this session with the prior
("must be hand-maintained... indefinitely") wording — update the `description` string to
the text above as part of task H, since the propagation mechanism changes what it should
say, not what it validates.

**B. `contract/SPEC.md`** — worked example (mirrors `select_zoom`'s own paragraph
immediately below it) plus a **prominent, explicit statement of the hand-maintenance

"backdrop": { "transform": { "x": 864, "y": 283, "scale": 0.105, "rotate_deg": 0 },
              "darken_alpha": 0.65, "enabled_on_admin": true, "enabled_on_public": true,

```md
**`backdrop` is optional and, when present, authoritative** — applied on every
upload/replace that includes it, overwriting the colony's current alignment. Omit the key
entirely on a routine geometry-fix replace to leave an existing backdrop untouched.
**`tools/pipeline` cannot derive this block** — a backdrop is a manually aligned aerial

`tools/pipeline/colonies/<id>.json` (the hand-maintained per-colony config `make export`
reads) and every future export carries it through into `colony.json` verbatim, the same way
`select_zoom` is. A fresh export whose config has no `backdrop` block omits the key too,
which means this upload does not touch the colony's existing alignment, not that it gets
cleared.
```

**D. `ColonyUploadScreen.tsx`** — in `upload()`'s `result.ok` branch, before setting the

- `backdrop` present, the update call threw: `Colony "<id>" is live. Could not apply
  colony.json's backdrop alignment (<error message>) — set it manually below.` — still

## 3. Pinned constraints

- **`attribution` is required in the schema — no `?? ""` fallback anywhere in the code
  that reads it.** This is the exact fix for the previous attempt's blanking bug; do not
  reintroduce optionality here.
- **Applied on both create and replace, unconditionally, whenever `backdrop` is present —
  no "only on first upload" special case.** This is the owner's explicit, repeated choice,
  not an oversight to "fix" back to preserve-on-replace.
- **Omitting `backdrop` from the manifest must never call `updateColonyBackdropTransform`
  at all** — this is what makes "leave untouched" actually true; task E's second new test
  is the proof.
- **Never routed through `create_colony_from_manifest()`** — a separate call, same
  authenticated client, after the RPC succeeds. The RPC's own signature and `contract/`'s
  `plots`/`features` sections stay untouched (`tools/pipeline` is touched, deliberately —
  task H).
- **A failed manifest-driven apply must still land the user on the backdrop stage**, with
  the failure named in `intro`, never a dead end (same posture as the existing
  `fetchColonyById` error handling this plan reuses unchanged).

## 4. Non-goals

- **Deriving `backdrop` values from DXF geometry** — still explicitly impossible, a manually
  aligned aerial photo has no geometric source. Task H only makes the pipeline *propagate*
  a hand-declared value through re-exports; it never computes one.
- Any other new field, config option, or general-purpose "hand-authored extras" mechanism
  in `ColonyConfig` — task H adds exactly one field, `backdrop`, mirroring `select_zoom`'s
  existing shape. Not a generic passthrough facility.
- Removing or changing `ColonyBackdropScreen.tsx`'s manual form — it stays exactly as is,
  now pre-filled with whatever the manifest just applied (or the colony's existing values,
  if the manifest declared none) and still the only way to attach the actual image file.
- A "diff" or "confirm before overwrite" UI when JSON and the database disagree — the
  owner's rule is unconditional JSON-wins-when-present; adding a confirmation step is
  unrequested scope.
- `create_colony_from_manifest()`, any other manifest field — untouched. (`tools/pipeline`
  is in scope via task H, narrowly — see that task and its own non-goals above.)

## 6. Failure modes

1. **Partial writes** — the RPC (colony + plots) and the manifest-driven backdrop update are
   two separate calls, same accepted shape as every other backdrop write this session
   (Postgres cannot transact across them anyway). If the RPC succeeds and the backdrop apply
   fails, the colony is fully live with its previous (or default) backdrop — never a
   half-written colony row.
2. **Idempotency** — re-uploading the exact same manifest twice applies the exact same
   values twice; no counter, no accumulation, naturally idempotent.
3. **Concurrency** — same low-stakes last-write-wins already accepted for this data
   (docs/plans/29.md/30.md's own reasoning, unchanged).
4. **Orphans** — N/A, no new geometry/identity relationship introduced.
5. **Dead computation** — N/A, nothing here is derived; it is copied verbatim from the
   manifest into the matching columns.
