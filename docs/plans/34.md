# Plan 34 — Backdrop upload accepts any image format, not JPEG-only

## 1. Context already true

Plan 33 (same session) put the backdrop image upload directly on `ColonyUploadScreen.tsx`'s
picking stage. It inherited the project's original JPEG-only convention end to end:
`colonyBackdrop.ts::isJpegBuffer` (magic-number check), a fixed `${colonyId}.jpg` storage
path with `contentType: "image/jpeg"` hardcoded in `uploadColonyBackdropImage`, and
`accept="image/jpeg"` on both the new inline picker and admin-portal's own upload form
(`admin-portal/static/backdropEditor.js`). Owner, mid-session: "one more thing .png is not
allowed please allow every image format."

## 2. The exact task

- `colonyBackdrop.ts`: replace `isJpegBuffer(bytes): boolean` with
  `detectImageFormat(bytes): {ext, contentType} | null`, magic-number detection for JPEG,
  PNG, WebP, and GIF (87a/89a). `uploadColonyBackdropImage` takes a `format: ImageFormat`
  arg, storage path becomes `${colonyId}.${format.ext}`, upload `contentType` uses
  `format.contentType`.
- Orphan cleanup: a re-upload in a *different* format changes the storage path (e.g.
  `.jpg` -> `.png`), so `uploadColonyBackdropImage` reads the colony's existing
  `backdrop_storage_path` first and removes the old object after the new one lands, if the
  path changed.
- `backdropImageFile.ts::readBackdropImageFile` uses `detectImageFormat` instead of
  `isJpegBuffer`, reads 12 bytes (WebP's magic number needs it, up from 3), returns
  `format` alongside bytes/dimensions.
- `ColonyUploadStageView.tsx`'s backdrop input: `accept="image/*"`, label "Backdrop image
  (optional)" (was "... (JPEG, optional)").
- `admin-portal/backdropRoutes.ts` + `admin-portal/static/backdropEditor.js`: same
  generalization (own upload path, shares `colonyBackdrop.ts`).

## 3. Pinned constraints

- Detection stays magic-number-only — never file extension or the browser's `File.type`
  (both trivially wrong/spoofable), same principle the old `isJpegBuffer` comment stated.
- `colonies.backdrop_storage_path` has no format assumption baked into the schema — a
  plain text column, no migration needed.
- The orphan-removal call is best-effort after the row update succeeds — its own failure
  must not throw (a `.remove()` error would otherwise mask the fact that the real upload
  already succeeded).

## 4. Non-goals

- No new bucket-level MIME allowlist (the `colony-backdrops` bucket has none today either).
- No image transcoding/normalization to one canonical format — whatever format is
  uploaded is what's served.

## 5. Acceptance criteria

- `pnpm typecheck` / `pnpm lint` clean.
- `colonyBackdrop.test.ts`'s `detectImageFormat` describe block (JPEG/PNG/WebP/GIF/
  invalid/empty) passes.
- `backdropImageFile.test.ts` updated for the renamed rejection message, passes.
- Live-integration: `colonyBackdrop.test.ts` + `colonyBackdropRls.test.ts` against the
  local Docker Supabase, including a new test proving a format-changing re-upload deletes
  the old Storage object.

## 6. Failure modes

- **Orphans**: the one real risk — addressed directly by the old-path removal above.
- Partial writes/concurrency/idempotency/dead computation: unchanged from plan 33's
  analysis — this plan only changes what bytes are accepted and where they're stored, not
  the write sequencing.
