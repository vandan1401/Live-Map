# Plan 19: Feature/road-annotation labels, road inner stroke, plot-corner gap fix

Three owner asks in one message (2026-08-24), bundled because all three are road-rendering
related and were requested together:

1. Pipeline must emit text for road/pathway width annotations ("9m wide road", "road to
   Sailana") **and** for classified garden/amenity features including "Future planning"/
   reserved — both wanted now (Tier 1, `tools/pipeline/pipeline/{matching,export}/**`).
2. Map renderer: a 1-unit-wide, tiled, light-grey inner stroke on roads (Tier 3,
   `apps/map/src/components/map/**`).
3. Bug fix: rounded plot corners leave a gap (exposed ground texture) between a plot and the
   road that should be adjacent to it (Tier 3, `apps/map/src/components/map/drawColony.ts`).

## 1. Context already true

- **The pipeline never emits any `.feature-label`/`.entrance-label` text today.**
  `tools/pipeline/pipeline/export/svg.py::build_svg` only ever emits `plot-label` text (one
  per matched plot, at the plot ring's own centroid). `PROGRESS.md` (~line 1151) already
  documents this gap and the owner's 2026-08-22 ask for road texts; that entry also records a
  now-superseded owner rule to suppress "Future planning"/reserved labels — **this plan
  reverses that:** the owner now wants text for both categories, so `build_svg` emits every
  `COL-FEATURE-NO` label unconditionally, with no keyword-based suppression.
- **`docs/cad-layer-standard.md:22`** already specs `COL-FEATURE-NO` (`TEXT`/`MTEXT`, "1 per
  feature, insertion point inside its own feature"). That wording only covers labels that
  fall inside a garden/amenity/water ring. Road-width texts ("9.0 M W ROAD") sit over the
  derived road area, which has no ring at all (D-104: roads are computed by subtraction, a
  road layer is ignored) — so under the current strict rule, a real DXF with road-width
  `COL-FEATURE-NO` text would make `pipeline.matching.classify.classify_features` raise
  `MatchingError: ... is inside no feature` via the shared
  `pipeline.matching.match_labels_to_rings` (`tools/pipeline/pipeline/matching/__init__.py`)
  and reject the whole export. This plan adds the missing case: a `COL-FEATURE-NO` label that
  matches no ring is not an error, it is a free-floating road/pathway annotation.
- **`match_labels_to_rings` is shared by `assign.py` (plots) and `classify.py` (features).**
  Plot-number matching must stay exactly as strict as it is today (tier-1.md, "Matching is
  identity" — a plot label outside every plot is still a hard error, unchanged, still tested
  by `test_matching.py::test_label_outside_every_plot_is_an_error_naming_its_handle`). Only
  the feature path gains the new "unmatched is allowed" behaviour.
- **`fixtures/shree-vatika-2/colony.svg`** (hand-authored, not pipeline output) already shows
  the target shape: `<text class="feature-label" x=".." y="..">9.0 M W ROAD</text>`, some with
  `transform="rotate(-90 ..)"`, sitting at arbitrary points with no ring association at all —
  and, separately, plot-dimension strings using the same class, which are out of scope here
  (fixture-only decoration, not something the pipeline generates).
- **The app side already renders `.feature-label` text with no changes needed.**
  `apps/map/src/components/map/colonyModel.ts::parseColonyModel` reads every `<text>` whose
  class is in `LABEL_KINDS` (includes `feature-label`), plus `data-rotation`/
  `data-label-height` when present, falling back to a literal `transform="rotate(..)"` (the
  fixture's own convention) when they are absent. `drawLabels.ts` draws whatever `model.labels`
  contains. **No apps/map change is required for part 1** — confirmed by reading both files.
- **`build_svg`'s existing plot-label emission is the pattern to copy** (`svg.py:86-105`):
  `data-rotation` is `-label.rotation_deg` (Y-flip mirrors rotation direction, tier-1.md, and
  is regression-tested in `tools/pipeline/tests/test_svg_labels.py`), `data-label-height` is
  `label.height * t.scale` when `label.height is not None`, omitted otherwise.
- **The manifest schema does not need to change.** `contract/colony.schema.json`'s `features`
  array shape (`svg_id`/`class`/`kind`/`label`/`centroid`/`area_sqft`) is unaffected — road
  annotations are never rings, so they can never be manifest features, the same way roads and
  trees never appear in the manifest today (`contract/SPEC.md`: "Roads and trees never appear
  here. Both are derived... storing a derived value creates a second source of truth"). No
  `run_qa` check ties feature-label **text** count to manifest **feature** count (verified by
  reading `tools/pipeline/pipeline/export/qa.py` — its only feature-adjacent checks are
  `svg_id` dedup/missing across plots+features).
- **The road/plot-corner gap (part 3) is a rendering-only artifact, not a geometry bug.**
  `apps/map/src/components/map/plotPath.ts::roundedPlotPath` (D-028, 2026-08-22) softens
  every plot's corners by insetting the path with `arcTo`, except plots in `state.cornerPlots`
  (drawn from their raw `d`). `drawColony.ts` paints in this order: ground fill (whole
  viewport) → `fillDecor` (road, from the **true/unrounded** plot geometry the pipeline
  derived via `site − union(plots ∪ ...)`, D-104) → per-plot opaque `plotBase` + status tint,
  using the **rounded** path (D-028) → strokes → labels → selected plot. Because the road
  polygon was subtracted using each plot's true (straight-corner) footprint, but the plot is
  then painted with a smaller, corner-inset rounded path, the sliver between the rounded edge
  and the true corner is covered by **neither** the road fill (road's own geometry excludes
  it — it's inside the true plot footprint) **nor** the plot fill (rounded path excludes it)
  — so the ground/grass fill from the very first paint call shows through instead. That is
  the "small empty spaces" the owner is describing. Fix is entirely in `drawColony.ts`; no
  pipeline change.
- **No separate "pathway" rendering exists anywhere in the codebase today.** `contract/
  SPEC.md` has exactly one road-ish class, `road` ("negative space, one compound path") — a
  pathway is geometrically just a narrower stretch of the same derived road polygon; "6.0 M W
  PATHWAY" is a label, not a distinct feature class. So "like pathway" (part 2) is read as: an
  inner border/curb trim that reads as a light, tiled strip along every road edge — applied
  uniformly to the one `road` path, since the data has no way to single out which stretch is
  "a pathway" versus "a road." `theme.road` fill (`--colony-road: #2c2924`, dark asphalt) and
  `canvasPatterns.ts::buildRoadPattern` (the existing flecked-asphalt tile) are the closest
  existing precedent for how a canvas-pattern road treatment is wired end to end (built once
  in `colonyCanvasLayer.ts::onAdd`, threaded through `DrawState`, consumed in `drawColony.ts`).

## 2. The exact task

### Part 1 — pipeline: emit feature-label text for both classified features and road/pathway annotations

- `tools/pipeline/pipeline/matching/__init__.py::match_labels_to_rings`: add a keyword-only
  parameter `allow_unmatched_labels: bool = False`. When `True`, a label matching **zero**
  rings is skipped (excluded from the returned pairs) instead of raising. Every other
  behaviour is unchanged: a label matching 2+ rings still raises; a ring with 0 or 2+
  matching labels still raises. Callers that don't pass the new parameter (i.e.
  `assign_plot_numbers`) get the exact same behaviour as today — do not change that call site.
- `tools/pipeline/pipeline/matching/classify.py::classify_features`: pass
  `allow_unmatched_labels=True` to `match_labels_to_rings`. No other change — `_resolve_kind`
  and its keyword table still apply only to labels that matched a ring (an unmatched label
  never goes through keyword classification, so "ROAD"/"PATHWAY" do not need to be, and must
  not be, added to `_KEYWORD_TABLE`).
- `tools/pipeline/pipeline/export/run.py::orchestrate_export`: it already builds
  `feature_labels = [lbl for lbl in result.labels if lbl.layer == _FEATURE_LABEL_LAYER]`
  (line 50) before calling `classify_features`. Pass that same `feature_labels` list straight
  into `build_svg` as a new argument (see below) — it already contains every `COL-FEATURE-NO`
  label, matched or not; nothing about `classify_features`'s return type needs to change.
- `tools/pipeline/pipeline/export/svg.py::build_svg`: add a new parameter
  `feature_labels: Sequence[Label]` (import `Label` from `pipeline.extract.types`, already
  imported for `Point`). After the existing feature `<path>` loop, emit one
  `<text class="feature-label">` per label in `sorted(feature_labels, key=lambda l: l.handle)`
  (deterministic ordering — mirrors `sorted(features, key=feature_svg_id)` just above it),
  positioned at `apply_transform(t, label.point)` — **the label's own DXF insertion point**,
  not a ring centroid (there may be no ring at all for a road annotation, and using the
  label's own point is simpler and correct for both cases; unlike plot-label, there is no
  existing convention here to preserve). Carry `data-rotation`/`data-label-height` with the
  exact same expression `build_svg` already uses for plot labels (`-label.rotation_deg`,
  `label.height * t.scale` when not `None`). No `data-kind` and no `data-feature`/`data-ring`
  attribute — the app reads none for `feature-label` (confirmed above) and the SVG contract
  places no such requirement on this class.
- Update every existing `build_svg(...)` call site to pass the new argument (positional or
  keyword, match the existing style): `tools/pipeline/pipeline/export/run.py`,
  `tools/pipeline/tests/test_export.py` (3 call sites), `tools/pipeline/tests/
  test_svg_labels.py` (5 call sites). Passing `[]` where a test has no feature labels to
  assert on is fine.
- `docs/cad-layer-standard.md`: extend the existing "Feature labels" section (around line 96)
  to document the new case in one short paragraph: a `COL-FEATURE-NO` label whose insertion
  point falls inside no `COL-GARDEN`/`COL-AMENITY`/`COL-WATER` ring is a free-floating
  road/pathway annotation — rendered as-is, with no keyword matching required (so "9.0 M W
  ROAD", "ROAD TO SAILANA", "6.0 M W PATHWAY" are all valid without being added to the
  keyword table). Keep the existing keyword-table paragraph and its "a label matching nothing
  is rejected" sentence scoped to labels that **do** fall inside a ring — that hard-error
  behaviour is unchanged and still real (tier-1.md, D-118: ambiguity/misclassification inside
  a real feature ring is still a loud failure, never a guess).

### Part 3 — apps/map: fix the plot-corner/road gap

- `apps/map/src/components/map/drawColony.ts`: in the main per-plot loop (currently lines
  163-185) and in the selected-plot block (currently lines 204-238), immediately before the
  existing `ctx.fillStyle = theme.plotBase; ctx.fill(path)` line, add a road-coloured pre-fill
  of the plot's **true, unrounded** footprint for every plot **not** in `state.cornerPlots`
  (a corner plot's raw `d` path already exactly matches its true footprint — `plotPathFor`
  returns the same path either way for it, so a pre-fill there is a wasted no-op draw call,
  skip it):
  ```ts
  if (!state.cornerPlots.has(plot.id)) {
    ctx.globalAlpha = 1; // road-coloured backdrop is never dimmed/filtered — see below
    ctx.fillStyle = state.road ?? theme.road;
    ctx.fill(pathFor(plot)); // the raw, un-rounded path — already cached by pathFor()
  }
  ```
  Then continue exactly as today (set `ctx.globalAlpha = alpha` — or, in the selected-plot
  block, no alpha changes needed there since it doesn't use `plotAlpha` at all — and paint
  `plotBase`/status tint with the **rounded** `path` as before). **The pre-fill must always be
  drawn at `globalAlpha = 1`, regardless of the plot's own dim/select/filter alpha** — it
  represents permanent road background, not the plot's own status visualisation, so a
  dimmed-out or filtered-out plot must not show a dimmed sliver of "road" in its rounded
  corner (that would look like a rendering bug in its own right). In the main loop this means
  setting `ctx.globalAlpha = 1` for the pre-fill and only then computing/assigning `alpha` for
  the subsequent `plotBase`/status fills, rather than computing `alpha` once up front and
  reusing it for both.
  This closes every rounded plot's exposed-corner gap by guaranteeing road colour sits
  underneath before the rounded fill is painted on top, without touching pipeline geometry.

## 3. Pinned constraints

- `allow_unmatched_labels` (part 1) defaults to `False` and `assign_plot_numbers`/plot
  matching must not pass `True` — plot-number matching stays exactly as strict as it is today.
  This is the one interface change with real blast radius in this plan; get the default right
  so no existing call site's behaviour shifts silently.
- Feature-label text position is the **label's own transformed insertion point**
  (`apply_transform(t, label.point)`), not a ring centroid — deliberate, and different from
  how `plot-label` positions itself (ring centroid). Do not copy the plot-label centroid
  pattern here; there is no ring at all for a road annotation, so centroid isn't available in
  the general case, and using the operator's own placement point is correct for both the
  matched and unmatched cases uniformly.
- `feature_labels` are emitted in `sorted(..., key=lambda l: l.handle)` order — deterministic
  output, same principle `build_svg` already applies to `features`/`plots`.
- Road-edge stroke width is exactly `1` (SVG user units, i.e. `ctx.lineWidth = 1` — grows with
  zoom like every other size in `drawColony.ts`/`drawLabels.ts`), per the owner's literal "1
  unit" ask. Do not convert to a fixed screen-pixel width.
- `--colony-road-edge: #c7c2b6` is a first-pass placeholder value, not a confirmed final
  colour — flag this in the PR/wrap notes as "owner should eyeball live and retune," don't
  present it as settled.
- The corner-gap pre-fill (part 3) is always drawn at `globalAlpha = 1`, independent of
  `plotAlpha(plot, state)` — pin this explicitly, it is the one easy way to get this fix
  subtly wrong (a dimmed corner sliver would be its own visible bug).
- Corner plots (`state.cornerPlots`) are skipped in the pre-fill — their raw path already
  equals their true footprint, so the fill would be a same-shape no-op paid for on every
  frame across up to ~675 plots (Jai Dev Residency's real count, per `NAVIGATION.md`).

## 6. Failure modes

This plan writes no database state and touches no `plots`/`plot_history`/RLS/auth surface —
`spec/00-rules.md`'s five failure modes, walked for what does change:

- **Partial writes**: `orchestrate_export` still only writes `colony.svg`/`colony.json` after
  `run_qa` passes, both or neither (unchanged code path, not touched by this plan).
- **Idempotency**: `feature_labels` are sorted by `label.handle` before emission — two clean
  runs against the same DXF produce byte-identical label ordering, same principle as
  `sorted(features, key=feature_svg_id)`/`ordered_plots` already in this file. No new
  randomness or clock/hash-of-process-state is introduced.
- **Concurrency**: N/A — pure local file generation, no shared/concurrent writer.
- **Orphans**: N/A — no new foreign-key-shaped relationship is introduced; a road annotation
  is deliberately not tied to any ring/manifest row, so there is nothing to orphan.
- **Dead computation**: the new `allow_unmatched_labels=True` path in `classify_features`
  means an unmatched label's text is carried straight through to `build_svg` with no
  transformation beyond position/rotation — nothing is computed and discarded.
