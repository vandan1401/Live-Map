## 3. Pinned constraints

- **Shape.** `statuses[i] = { key, label, colour }`. `key`: `^[a-z][a-z0-9_]{0,31}$`, unique. `label`: 1–32
  chars, trimmed. `colour`: `^#[0-9a-f]{6}$` lowercase. Unknown extra fields rejected
  (`additionalProperties: false`), like the rest of the schema.
- **Must contain `available`** (the initial/default status of every new plot). `booked` and `registered` are
  optional — a colony that omits them simply never offers them. Order in the array = legend order.
- **`MAX_STATUSES = 8`.** Why 8: the legend/toolbar is one row on a phone, and ≥9 colours stop being
  distinguishable on the map. Enforced in schema (`maxItems: 8`), pipeline QA and the app.
- **Default when absent**: `available #e8b84b "Available"`, `booked #3b82f6 "Booked"`,
  `registered #ff145a "Registry done"` — identical to today, so every existing colony is byte-unchanged.
- **Colour precedence (highest first):** `colony.json statuses` > `presentation.json` per-colony override
  (only for the three built-in keys) > default. Labels follow the same order.
- **Transitions.** Built-ins unchanged: `available -> booked`; `booked -> registered | available`;
  `registered -> available`. A custom key `c`: `available <-> c`, and `c <-> c'` for any other custom `c'`.
  **A custom status never moves directly to or from `booked`/`registered`** — go via `available`. Reason:
  `booked` requires a buyer name on entry (D-018); a direct edge would bypass it. *This is the plan's reading
  of "new ones are free"; relaxing it is a one-line change in `isLegalTransition` and the owner should confirm
  it.* Self-transitions stay illegal (UI no-op).
- **Validation lives in three places on purpose** — schema (shape), pipeline QA (before a human sees it),
  database (`unknown_status` / `status_in_use`). Removing any one is a regression.
- **Removing a status in use is refused**, never silently remapped: `status_in_use:<key>:<count>`.
- **`plot_history` is untouched** except dropping the closed-list check; still append-only, no new columns.
- **Migration order:** apply to hosted Supabase **before** the Cloudflare deploy; on the box,
  `update.sh` runs the migrator before restarting containers (already the order). Old app + new DB must work
  (new column ignored, new RPC param defaulted). New app + old DB does **not** — so ordering is mandatory.
- **No new money fields; no change to `version`/concurrency semantics.**
- Tier 1 files touched: `contract/**`, `supabase/migrations/**`, `lib/plot-status/**`, `features/colony-upload/**`
  (it passes `statuses` to the RPC), pipeline `export/**`.

## 6. Failure modes (writes plot state — `spec/00-rules.md`)

1. **Partial writes** — status update + `plot_history` insert remain one transaction inside
   `apply_plot_transition`; the membership check runs *before* either write. The colony replace writes
   `colonies.statuses` and plots in one RPC transaction — the `status_in_use` rejection rolls both back.
2. **Idempotency** — double-tap still fails on the `version` check (unchanged); needs no new path, but the
   existing test must still pass with a custom status.
3. **Concurrency** — unchanged semantics. A new live test changes a plot to a custom status from two clients;
   exactly one wins with the named conflict.
4. **Orphans** — new orphan class: a plot holding a status its colony no longer lists. Prevented at write
   (`unknown_status`) and at replace (`status_in_use`); the renderer's fallback is defence in depth, logged.
5. **Dead computation** — `facing`/`is_corner` untouched. Resolved status colours/labels are computed in one
   function (`resolveColonyStatuses`) and never re-derived per component.
- Also: **old-client/new-DB skew** (Cloudflare app deployed before the migration) — the ordering rule in §3
  is the control; record it in `PROGRESS.md` and the v1.0.2 `CHANGELOG.md` entry, which must call the
  migration out explicitly like v1.0.1's predecessors did.
