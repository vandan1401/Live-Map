# Plan 16 — Disambiguate plot-label text for mixed blockless/lettered colonies

**No spec file** — this is a `PROGRESS.md` → `## Deferred` item, not a pre-written milestone.
Flagged by `/review` during plan 15 (blockless plot IDs, 2026-08-21) and explicitly deferred
as needing its own plan. **Tier 1** — `tools/pipeline/pipeline/export/**` is Tier 1 per
`CLAUDE.md`'s risk table.

## 1. Context already true

- **The bug, exact location**: `tools/pipeline/pipeline/export/svg.py:82-87` — the loop that
  emits each plot's visible `<text class="plot-label">` renders `{int(plot.number)}` only.
  It never reads `plot.block` at all. This means **every** plot's on-map label is bare
  digits today, for every colony, not only blockless ones — a pre-existing gap that plan 15
  made concretely harmful: a colony with bare `1`–`6` (blockless) and explicit `A-1`–`A-6`
  (lettered) as genuinely distinct plots (Jai Dev Residency's real shape, `PROGRESS.md` →
  `## Current`) would render the visible text "1" for *both* `plot-01` and `plot-A-01` —
  indistinguishable on the map a family member is actually looking at, even though
  `svg_id`s never collide (`assign.py`'s `seen` dict already guards that, unaffected by this
  plan).
- **`MatchedPlot`** (`tools/pipeline/pipeline/matching/assign.py:27-34`) already carries both
  `block: str` (empty string for a blockless plot, per plan 15) and `number: str`
  (zero-padded, e.g. `"01"`) — no new field needed, `build_svg` just isn't using `block`.
- **The app's own equivalent formatter**, `formatPlotLabel` (`apps/map/src/shared/format.ts:74-76`):
  `plot.block ? \`${plot.block}-${plot.number}\` : plot.number` — zero-padded, no digit-
  stripping. This plan's pipeline-side fix is **not** required to match that convention
  exactly (see §3 — deliberately not, to keep the fixture-facing diff minimal); the
  divergence between the SVG's on-map label style and the table/detail-sheet's label style
  already exists today (SVG always drops the leading zero; the table/detail sheet never
  does) and is out of scope here.
- **No test today asserts on exact plot-label text.** `tools/pipeline/tests/test_export.py`'s
  `_svg()` helper (line 72-75) calls `build_svg` with a single `MatchedPlot` (`block="A"`,
  `number="01"`), and every existing test using it (`test_svg_has_zero_styling_attributes`,
  `test_two_clean_runs_are_byte_identical`, the `run_qa`/`orchestrate_export` tests) checks
  structural properties, never the literal label string. This plan's change breaks none of
  them.
- **`tools/pipeline/tests/test_export.py` is already 304 lines — over the 250-line cap**
  (`.claude/hooks/filesize.sh`, CLAUDE.md invariant 7), a pre-existing breach independent of
  this plan (confirmed via `wc -l`, no edit made). **Do not add to this file** — it would
  push an already-tracked breach further, exactly the mistake plan 15's `/review` caught
  once already (`.claude/agent-memory/adversarial-reviewer/review-line-cap-breaches.md`).
  New tests for this plan go in a new file, `tools/pipeline/tests/test_svg_labels.py`,
  following the same split-file precedent plan 15 set with
  `test_colony_config.py`/`test_matching_blockless.py`.
- **`fixtures/shree-vatika-2/colony.svg` is hand-traced, not pipeline-generated**
  (`test_export.py`'s own module docstring, D-017) — its `plot-label` text (`fixtures/
  shree-vatika-2/colony.svg:32-36`, e.g. `<text ...>1</text>` for `plot-A-01`) is committed
  by hand, and nothing in the repo regenerates it today. `test_golden.py` (the one test that
  would compare pipeline output against this fixture) is skipped — `fixtures/
  shree-vatika-2/colony.dxf` still doesn't exist (same blocker recorded throughout
  `PROGRESS.md` for M10–M13). This plan's `svg.py` change is therefore **not** exercised
  against the real fixture and cannot desync anything that currently passes.

## 2. The exact task

1. `tools/pipeline/pipeline/export/svg.py`, the plot-label emission loop (currently lines
   82-87): change the text content from `{int(plot.number)}` to include the block prefix
   when present:
   - `plot.block` non-empty → `f"{plot.block}-{int(plot.number)}"` (e.g. `"A-1"` — keeps
     today's existing digit-stripping style, now just also carrying the block, see §3 for
     why the number stays unpadded here).
   - `plot.block` empty (blockless, plan 15) → `str(int(plot.number))` (unchanged from
     today's output for a blockless plot — there is nothing to disambiguate it from within
     its own block, only across blocks).
   - **Prefix only when the colony actually mixes more than one distinct `block` value**
     (computed once per `build_svg` call: `len({p.block for p in ordered_plots}) > 1`).
     This is the corrected scope after `/review` (round 1) flagged the first draft for
     prefixing unconditionally, which would have changed every already-shipped single-block
     colony's map label (e.g. `shree-vatika-2`'s 26 plots, `1`→ nothing needed changing there
     at all) with no owner ask on record for that. A single-block colony has nothing to
     disambiguate, so its labels are provably unaffected.
2. `tools/pipeline/tests/test_svg_labels.py` (new file): unit-level tests calling
   `pipeline.export.svg.build_svg` directly (same inline-construction convention as
   `test_export.py`'s `_PLOT`/`_SITE`/`_GARDEN_RING`, `Ring`/`Label`/`MatchedPlot`/
   `ClassifiedFeature` imports, `compute_transform`/`derive_road` for the required
   `Transform`/road args — no DXF, no `ColonyConfig` needed since this is purely an SVG-
   string-shape test):
   - A single lettered plot alone (`block="A"`, `number="01"`) renders `>1<` — no
     prefix, since one block gives nothing to disambiguate (this is the case that covers
     every already-shipped colony, e.g. `shree-vatika-2`).
   - Two lettered plots in different blocks (`A`/`B`) each render prefixed (`>A-1<`,
     `>B-1<`).
   - A blockless plot (`block=""`, `number="07"`) renders `>7<` (unchanged behavior).
   - A synthetic colony with a blockless and a lettered plot in the same `build_svg` call
     (mirrors the real Jai Dev Residency shape) renders two distinct label texts (`>1<` and
     `>A-1<`) even when their zero-padded `number` happens to collide (e.g. both
     `number="01"`) — this is the actual disambiguation the bug report is about; assert both
     texts are present and unequal.

## 3. Pinned constraints

- **Number stays unpadded (`int(plot.number)`) in both branches — do not zero-pad to match
  `formatPlotLabel`.** Reasoning: the fixture's existing hand-traced labels (`fixtures/
  shree-vatika-2/colony.svg`) already use the unpadded style (`"1"`, not `"01"`) for every
  plot; matching that convention going forward, rather than switching to zero-padded, keeps
  today's single-block fixture's *number* rendering exactly reproducible once a real DXF
  eventually drives `test_golden.py` (only the block-prefix addition would then be a real
  diff, not also a padding change). Converging the SVG's label style with
  `formatPlotLabel`'s (table/detail-sheet) style is a separate, pre-existing divergence
  (§1) and is not this plan's job.
- **`svg_id` construction (`assign.py`) is untouched.** This plan only changes the *visible*
  `<text>` content, never the `id`/`data-plot` attribute, which is already collision-safe.
- **No change to `contract/` or `apps/map`.** The visible label text lives entirely inside
  the SVG the pipeline emits; the app renders whatever text is already in the markup and
  has no separate label-formatting code path for the map itself (only `formatPlotLabel`,
  used by the table/detail sheet/search/share-summary, is untouched — confirmed no caller
  of it reads or duplicates `build_svg`'s output).
- **`fixtures/shree-vatika-2/colony.svg` is not touched by this plan, and needs no future
  update either.** It is hand-traced (D-017), single-block, and the golden test that would
  compare it against pipeline output is still skipped (no `colony.dxf`). Because the
  prefix only fires for a colony that mixes more than one distinct block (§2), a real DXF
  for this single-block colony would reproduce today's unprefixed labels unchanged —
  there is no future desync to flag here, unlike the first draft of this plan assumed.

## 4. Non-goals

- Zero-padding the number, or otherwise converging the SVG label style with
  `formatPlotLabel`'s.
- Any change to `assign.py`'s `svg_id`/`block`/`number` resolution (plan 15's territory,
  already correct and untouched here).
- Updating `fixtures/shree-vatika-2/colony.svg` — no DXF exists yet to drive that
  comparison (§3).
- Touching `tools/pipeline/tests/test_export.py` in any way, including to fix its
  pre-existing 304-line cap breach — out of scope for this plan, a separate cleanup.
- Any change to `tools/pipeline/verify/` (the local preview page) — it reads whatever
  `colony.svg` already contains; no code there formats a label independently.
