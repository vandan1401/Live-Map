# 03 — Three-status vocabulary + plot dimensions (D-013/D-012 revision)

**Tier 1.** Touches `contract/`, a migration, and `apps/map/src/lib/plot-status/**`.
`/plan` before `/build`, `/review` before `/wrap`.

## 1. Context already true

- **User decision this session, replacing D-013's four-word vocabulary:** three statuses
  — `available`, `booked`, `registered` (displayed as **"Registry done"**, stored value
  unchanged — same D-010-style separation of storage word from display label already used
  for money). `hold` is removed entirely, confirmed explicitly by the user rather than
  assumed. Legal transitions (D-006/D-013 pattern preserved, just fewer nodes):
  ```
  available  → booked
  booked     → registered, available
  registered → available
  ```
- **User decision this session, replacing D-012's field list on the plot detail sheet:**
  show only **Length (ft)** and **Breadth (ft)**, plus **Owner name — only when
  `status === "booked"`**, literally as stated (not `registered`, confirmed explicitly
  when asked). The attribution line ("Booked — updated by Vikas, 2:40pm") and the
  `plot_history` list stay — confirmed explicitly, they answer "who changed this and
  when" (D-007/D-006), a different question than "what does this plot look like."
  Everything else currently in `PlotDetailContent.tsx`'s field list (facing, area, owner
  phone, broker, rate, booking amount, booking date, registry date, notes) is removed
  from **display** only. The underlying DB columns are **not** dropped — spec/00-rules.md
  already permits storing `booking_amount_paise` "as a plain number," and no other part
  of this change depends on deleting them. Only new columns (`length_ft`, `breadth_ft`)
  are additive.
- **What's actually live right now:** local Supabase has the M2+M4 schema applied, 45
  plots imported (4 of them `status = 'hold'`: `plot-A-06`, `plot-A-10`, `plot-A-16`,
  `plot-B-12`) — this session's next `supabase db reset` + `pnpm import:seed` will be the
  first real exercise of the new CHECK constraint and remapped seed data.
- **Reuse by exact path, unchanged:** `applyPlotTransition()`
  (`apps/map/src/lib/plot-status/applyPlotTransition.ts`) — its signature doesn't change,
  only the `PlotStatus` union it's generic over shrinks. `formatRupees`/`formatDate`/
  `formatRelativeTime` (`shared/format.ts`) — unaffected, dimensions aren't money or
  dates.
- **Why the CHECK-constraint change is safe even outside this session's `db reset`
  workflow:** `plots.status` can be `UPDATE`d in place (defensive `UPDATE ... SET status
  = 'available' WHERE status = 'hold'` before the constraint swap), but `plot_history` is
  append-only by trigger — any historical `'hold'` row there is permanent and **must not**
  be touched. That's correct, not a bug: `plot_history` is evidence of what actually
  happened, and a CHECK constraint only validates rows being written now, not rewrite
  history. Nothing in this migration attempts to touch `plot_history`'s existing rows.

## 3. Pinned constraints

- **The new transition table** (supersedes the M4 plan's, which had `hold`):
  ```
  available  → booked
  booked     → registered, available
  registered → available
  ```
- **`length_ft`/`breadth_ft` are `numeric not null`, no default.** Every plot has a real
  frontage and depth; there's no meaningful placeholder the way `notes` can be null.
- **Owner name visibility is exactly `status === "booked"`** — not `registered`, not
  "has an owner_name value." Confirmed explicitly this session; do not generalize to
  "any status with an owner" without asking again, that was the one place two reasonable
  readings existed and the narrower one was chosen on purpose.
- **`plot_history`'s historical `'hold'` rows are never touched.** The CHECK constraint
  change only affects rows written after this migration; append-only holds.
- **Display label vs stored value stay separate** (D-010 precedent): the stored word is
  still `registered`; only `formatStatusLabel` changes what's shown. No migration, no CSV,
  no test outside `format.ts`/`format.test.ts` should say `"Registry done"` — that string
  belongs in exactly one place.

## 4. Non-goals

- No pipeline changes — `tools/pipeline/` doesn't exist yet (pre-M9); `length_ft`/
  `breadth_ft` are added by hand to the one hand-authored fixture manifest, the same way
  `area_sqft`/`facing`/`is_corner` already are.
- No change to which DB columns exist for owner_phone/broker_name/rate_paise/
  booking_amount_paise/booking_date/registry_date/notes — display-only removal, per §1.
- No change to `applyPlotTransition()`'s signature, the migration from M4
  (`apply_plot_transition()`), or the concurrency/atomicity mechanism — only the set of
  legal `PlotStatus` values shrinks.
- No renaming of the `--colony-status-hold` CSS variable — still used as a generic
  warning-accent token elsewhere (§2 task 14).

## 6. Failure modes (spec/00-rules.md checklist, applied to this task)

1. **Partial writes** — N/A to this task's own change (no new write path); the existing
   `apply_plot_transition()` atomicity is untouched.
2. **Idempotency** — the `update plots set status = 'available' where status = 'hold'`
   step is naturally idempotent (a second run touches zero rows).
3. **Concurrency** — N/A; this is a schema/vocabulary change, not a new concurrent write
   path.
4. **Orphans** — N/A; no new svg_id/plot associations created.
5. **Dead computation** — `formatStatusLabel`'s dropped `"hold"` branch is exactly this
   failure mode in reverse (removing dead code for a value that can no longer occur, not
   leaving it to silently rot).
