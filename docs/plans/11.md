## 1. Context already true

- **D-025 (accepted, amends D-108)** and **spec/15** already pin the three-part design:
  `colonies.svg` becomes a runtime `text` column; `create_colony_from_manifest()` is a
  second `security definer` write path shaped like `bulk_set_initial_plot_data` (D-023);
  the upload screen renders the SVG and requires an explicit confirmation before the RPC
  writes `verified: true` — the **only** code path that ever does (invariant 2, as
  restated 2026-08-17 in `docs/decisions/D-025-colony-onboarding-in-app.md`).
- **`ColonyMap.tsx:6`** today does
  `import colonySvgRaw from "../../../../fixtures/shree-vatika-2/colony.svg?raw"` — a
  build-time import, hardcoded to the one fixture. This plan removes it entirely; grepping
  `apps/map/src` for `?raw` must return nothing when done (spec/15 acceptance criterion 1).
- **`App.tsx` already loads every colony's full row** via `loadVerifiedColonies` →
  `fetchVerifiedColonies` (`lib/db/colonies.ts`), which does `select("*")` — once the `svg`
  column exists, `ColonyRow` picks it up with zero query changes. `App.tsx` holds this list
  in its own `colonies` state and already knows `selectedColonyId` when it renders
  `<ColonyMap>` — the SVG for the selected colony is sitting right there, one `.find()`
  away, and must be threaded in as a prop rather than `ColonyMap` issuing a second fetch.
- **`apps/map/src/pwa/offlineCache.ts`** types its cached list as `ColonyRow[]`
  (`saveColonyList`/`loadColonyList`) — the SVG rides along in the offline snapshot
  automatically, no code change needed there. This is D-025's stated intent ("it rides
  along with the offline snapshot the PWA already caches"), not a gap.
- **RLS today (M8, `20260815020000_m8_auth_rls_lockdown.sql`)**: `anon`/`authenticated`
  have **no** `insert`/`update` grant at all on `colonies` or `plots` — only `select`.
  `service_role` has `insert`/`update`. A `security definer` function runs with its
  **owner's** privileges regardless of the caller's grants — this is why
  `apply_plot_transition` and `bulk_set_initial_plot_data` need no table-level grant for
  `anon`/`authenticated`, only their own `execute` grant. `create_colony_from_manifest`
  follows the identical shape: `revoke execute ... from public; grant execute ... to
  authenticated;`.
- **The manifest fields the app actually consumes, confirmed by grep — nothing else**:
  `colony.{id, name, generated, source.file}` and, per plot, exactly the seven fields
  `scripts/import-seed.ts` already extracts: `svg_id, block, number, area_sqft, length_ft,
  breadth_ft, facing, is_corner`. `colony.viewbox`/`scale`/`north_deg` and every plot's
  `centroid`/`confidence`, and the whole top-level `features` array, are **never read** by
  `apps/map` — `ColonyMap.tsx` derives viewBox/bounds from the parsed SVG's own `viewBox`
  attribute (`svgEl.viewBox.baseVal`), and static features (gardens/roads/amenities) are
  baked into the SVG's classes per D-005, not read from JSON at runtime. Do not add
  columns or RPC parameters for fields the app doesn't use.
- **`scripts/import-seed.ts`** is the only other writer of `colonies`/`plots` (via
  `SUPABASE_SERVICE_ROLE_KEY`, bypassing RLS same as today) and stays the fixture/local-dev
  path (D-025's consequence list: "`import-seed.ts` stays... It is not the onboarding path
  any more"). It currently does **not** read or insert `colony.svg` — this plan updates it
  to, so the shared fixture (`fixtures/shree-vatika-2/`) keeps working after the schema
  change, and so `make db-reseed` continues to produce a colony that actually renders.
  It already does the exact svg_id/manifest cross-check spec/15 wants for the upload screen
  (`ColonyMap.tsx`... no — `import-seed.ts:73-84`, `matchAll(/id="(plot-[A-Z]+-\d+)"/g)`
  against `manifest.plots`); this plan extracts that into a shared function so the two call
  sites (the Node script and the new browser parser) can never drift.
- **Reuse by exact path** — do not reimplement:
  - `apps/map/src/features/bulk-import/BulkImportScreen.tsx` — the structural precedent
    for `ColonyUploadScreen.tsx`: a `Stage` union driving a full-screen overlay, parse
    client-side before any RPC call, one narrow write, a result screen listing what
    happened. Reuse the shape, not the code (different stages, different fields).
  - `apps/map/src/shared/parsePaise.ts`'s `parseNullablePaise` — **not needed here**; no
    manifest field this plan touches is money. Named only so it isn't reached for by
    mistake.
  - `contract/colony.schema.json` itself, imported as the literal file (see §2.2) — never
    hand-transcribe its rules into a second, hand-maintained validator. Invariant 1: this
    file **is** the interface: two independent restatements of it (Python's `make
    contract`, a hand-rolled TS check) are exactly the kind of silent drift invariant 1
    warns about, and the whole reason this screen exists is to be the one remaining human
    check standing between a bad file and a "deliverable".

## 2. The exact task

### 2.1 — Migration: `colonies.svg` + `create_colony_from_manifest()`

New `apps/map/supabase/migrations/20260817000000_m15_colony_upload.sql`:

- `alter table colonies add column svg text;` — **nullable**, no backfill statement. This
  repo's Supabase is local-only with no linked remote project (CLAUDE.md's Commands
  section); the only row that exists anywhere is the fixture, and `import-seed.ts` (§2.3)
  is updated in this same plan to always populate `svg` on insert. `supabase db reset`
  (or `make db-reseed`) is the recovery path after this migration, same as any other
  schema change to a table `import-seed.ts` populates — do not write a backfill UPDATE for
  a table with no rows worth backfilling.
- `create or replace function create_colony_from_manifest(p_colony_id text, p_colony_name
  text, p_source_file text, p_generated date, p_svg text, p_plots jsonb, p_replace boolean
  default false) returns jsonb`, `security definer`, `set search_path = public, pg_temp`.
  Guard `if auth.uid() is null then raise exception 'not authenticated'; end if;` (mirrors
  both existing RPCs).
  - `p_plots` unpacked with `jsonb_to_recordset(p_plots) as x(svg_id text, block text,
    number text, area_sqft integer, length_ft numeric, breadth_ft numeric, facing text,
    is_corner boolean)` — same technique as `bulk_set_initial_plot_data`.
  - **Returns a typed outcome, never raises for an expected refusal** — same
    "`apply_plot_transition` never throws for `illegal_transition`/`conflict`" precedent
    (`NAVIGATION.md`). Shapes:
    - `{"ok": true, "colony_id": ...}` on success.
    - `{"ok": false, "reason": "colony_exists"}` — the colony id already exists and
      `p_replace` was false.
    - `{"ok": false, "reason": "would_orphan_history", "missing_svg_ids": [...]}` — see
      the replace path below.
  - **Fresh create** (`p_replace = false` and no existing row, or `p_replace = true` and no
    existing row — replace with nothing to replace is just a create): insert one `colonies`
    row (`id, name, source_file, generated, svg, verified = true` — always `true`, because
    by the time this function is called the upload screen's confirmation has already
    happened; that confirmation **is** invariant 2's one writer, not a parameter this
    function trusts from the caller). Insert every row from `p_plots` into `plots` with
    `status = 'available'`, every operational field (`owner_name`, `owner_phone`,
    `broker_name`, `rate_paise`, `booking_amount_paise`, `booking_date`, `registry_date`,
    `notes`) left `null`, `updated_by = 'import'`. Insert one `plot_history` row per plot,
    `changed_by = 'import'`, `note = 'Colony upload'` — the same sentinel `import-seed.ts`
    uses (D-025 point 2: "Seeds `plot_history` with the existing `import` sentinel"), so
    a freshly uploaded colony's plots start in the same bulk-import "correction window"
    (D-023) a pipeline-seeded colony's do, and so `fetchRecentHistoryForPlots`'s existing
    `not in (import, bulk_import)` filter already excludes them from the share summary with
    zero new code.
  - **Replace** (`p_replace = true` and the colony id already exists): first compute
    `v_missing` = every existing `plots.svg_id` for this `colony_id` that is **absent**
    from `p_plots`. If `v_missing` is non-empty, return the `would_orphan_history` refusal
    immediately — nothing is written. This is D-118's id-stability hazard, arrived at from
    the app side: a re-cut colony that drops an `svg_id` would leave that plot's
    `plot_history` (invariant 5, commission-dispute evidence) attached to a row nothing can
    ever look up again by name in a re-uploaded manifest.
    If the check passes: update the `colonies` row's `name`/`source_file`/`generated`/`svg`
    (never `verified` — already `true`, stays `true`). For each `p_plots` row: if a
    matching `(colony_id, svg_id)` row exists, update **only** its seven geometry columns
    (`block, number, area_sqft, length_ft, breadth_ft, facing, is_corner`) — never
    `status`, never any operational/money field, never `version`, never `updated_by`. A
    geometry re-cut is a mechanical correction, not an event any concurrency guard is
    watching (no client ever writes those columns, so nothing races against them — see
    tier-2's "Derived fields" rule), and bumping `version` here would spuriously fail an
    unrelated in-flight status save with a confusing "someone else changed this". If no
    matching row exists, insert it fresh exactly as the create path does (new plot added by
    the re-cut), including its own `plot_history` `'import'`/`'Colony upload'` row.
  - `revoke execute on function create_colony_from_manifest(text, text, text, date, text,
    jsonb, boolean) from public; grant execute on function create_colony_from_manifest(...)
    to authenticated;` — same belt-and-suspenders as both existing RPCs.

### 2.2 — Client-side manifest validation (pure, DOM-free)

- New `apps/map/src/lib/colony/svgPlotIds.ts` — `extractSvgPlotIds(svgRaw: string):
  Set<string>`, the exact regex `import-seed.ts:73` already uses
  (`/id="(plot-[A-Z]+-\d+)"/g`), extracted so both call sites (`import-seed.ts` and the new
  browser parser below) share one implementation. Update `import-seed.ts` to import and use
  it instead of its own inline `matchAll` (same de-dup, no behavior change there).
- Add `ajv` (`^8`) to `apps/map/package.json` dependencies — validates the manifest against
  the **actual** `contract/colony.schema.json` file, not a hand-transcribed copy (§1's
  invariant-1 reasoning). Import it the same way `ColonyMap.tsx` already imports the
  fixture SVG: `import colonySchemaRaw from
  "../../../../contract/colony.schema.json?raw"; const colonySchema =
  JSON.parse(colonySchemaRaw);` — Vite's `?raw` (already relied on for `colony.svg?raw`
  today) needs no `resolveJsonModule` or `tsconfig` `include` change, unlike a direct
  `.json` import would.
- New `apps/map/src/lib/colony/parseColonyManifest.ts`:
  - `validateColonyManifest(json: unknown): { ok: true; manifest: ColonyManifest } | { ok:
    false; errors: string[] }` — runs the Ajv-compiled `colonySchema` against `json`;
    `errors` are Ajv's own messages (already file/field-specific, don't reformat them).
  - `checkManifestVerifiedFalse(manifest): boolean` — spec/15 step 2: a manifest whose
    `colony.verified` is `true` is rejected outright (`D-025`: the pipeline only ever
    emits `false`, so `true` in an uploaded file means someone hand-edited it).
  - `checkSvgIdsAgree(manifest, svgRaw: string): { ok: true } | { ok: false; inManifestNotSvg:
    string[]; inSvgNotManifest: string[] }` — using `extractSvgPlotIds`, same symmetric-
    difference check `import-seed.ts` already does.
  - No network calls, no DOM APIs beyond what Ajv itself needs (none) — this file is
    unit-testable exactly like `parseBulkImportFile.ts`.

- `apps/map/scripts/import-seed.ts` — add `svg: readFileSync(svgPath, "utf-8")` to the

### 2.4 — `ColonyUploadScreen.tsx` and wiring into the app

- New `apps/map/src/features/colony-upload/ColonyUploadScreen.tsx` — full-screen overlay,
  `BulkImportScreen.tsx`'s shape (`Stage` union, not its code):
  1. Two file inputs (or one combined picker), accepting `colony.json` and `colony.svg`
     by filename/extension, not by upload order.
  2. On both present: parse the JSON, run `validateColonyManifest` — a schema failure
     renders the Ajv errors and goes no further (spec/15 criterion 3, no RPC call).
  3. `checkManifestVerifiedFalse` — a `true` manifest is rejected with a clear message
     (criterion 4).
  4. `checkSvgIdsAgree` — a mismatch lists both `inManifestNotSvg`/`inSvgNotManifest` sets
     and stops (criterion 6).
  5. **Render the SVG at full size** (reuse `parseColonySvg`-shaped logic — the same
     `DOMParser` step `ColonyMap.tsx` already does; a plain inline `<div
     dangerouslySetInnerHTML>`-free DOM append, matching how `ColonyMap.tsx` mounts its
     SVG today, not a new rendering path) with the plot count, block letters, and colony
     name from the validated manifest.
  6. A checkbox — "I compared this against the site plan" — and an "Upload" button
     disabled until it's ticked (criterion 5).
  7. On confirm: call `createColonyFromManifest(client, manifest, svg, replace: false)`.
     - `{ok: true}` → success screen, "Done" closes back to the colony picker, which must
       refetch (`loadVerifiedColonies`) so the new colony appears without a manual reload.
     - `{ok: false, reason: "colony_exists"}` → show the refusal and a second checkbox/
       button, "Replace this colony's geometry" — ticking it and re-confirming re-calls
       with `replace: true`. This is the only place `replace: true` is ever sent; it is
       never the default (spec/15 criterion 7 — "refused **without** the replace flag").
     - `{ok: false, reason: "would_orphan_history", missingSvgIds}` → show the list of
       plot ids the new file is missing and refuse outright; **no retry-with-force** — the
       fix is the family member re-cutting the DXF to include those plots (D-118), the same
       "correction lives in the DXF, not in the app" discipline invariant 6 already states.
  - Reachable from `ColonyPicker.tsx` via a new "Upload a colony" button, visible to every
    signed-in family member (no role gating — D-007, all users are equal admins).
- `App.tsx`: render `<ColonyUploadScreen>` as a sibling overlay state (`showUpload:
  boolean`, same pattern `showInstallInstructions` already uses), triggered by
  `ColonyPicker`'s new button; on close, re-run the existing `fetchColonies()` closure
  (already defined in the colonies-loading effect — lift it so the upload-close handler can
  call it, rather than duplicating the fetch).
- `ColonyMap.tsx`: delete the `colonySvgRaw` import. Add a required `colonySvg: string`
  prop (App.tsx passes `colonies.find((c) => c.id === selectedColonyId)!.svg` — the
  colony is always present in the already-loaded, already-verified list by construction of
  how `selectedColonyId` gets set, per the existing comment at `ColonyMap.tsx:54-56`).
  `parseColonySvg(raw)` keeps its exact signature, now called with the prop instead of the
  module-level import. If `colonySvg` is falsy (a pre-migration row somehow still `null`,
  or a colony whose upload never finished), render a plain "This colony has no map data"
  message instead of calling `parseColonySvg` — a null/empty string reaching
  `DOMParser.parseFromString` must not white-screen the app the way the sixth bug in
  `docs/plans/10.md` did for an unrelated reason; this is the cheap, direct guard against
  that same failure class.

## 3. Pinned constraints

- **`verified` is set by the RPC unconditionally to `true`, never taken from a parameter.**
  There is no `p_verified` argument. The upload screen's disabled-until-ticked confirmation
  gate is what makes calling the RPC at all equivalent to a human having confirmed — this
  is invariant 2's restated wording made literal in code, and is the entire reason this
  plan does not accept a manifest whose own `colony.verified` is `true` (§2.2 step 3): the
  flag must never travel from the file, only from the button.
- **The RPC returns typed refusals (`{ok: false, reason: ...}`), it never raises for
  `colony_exists` or `would_orphan_history`.** Only a genuinely unexpected DB error aborts
  and rolls back — same split `bulk_set_initial_plot_data` already established between
  "expected, recorded" and "unexpected, thrown".
- **A replace only ever touches the seven geometry columns on an existing plot row** —
  `status`, every operational/money field, `version`, and `updated_by` are untouched. This
  is the one true "new" design decision in this plan (nothing in the codebase already does
  a partial-column update); do not widen it to a full-row overwrite without re-opening this
  plan, since a full overwrite would silently erase real booking data on every re-cut.
- **A replace that would orphan any existing plot's history is refused outright, with no
  force-through option.** The fix is always upstream, in the DXF (D-118) — this plan does
  not add a "delete this plot's history and proceed anyway" path, ever.
- **`create_colony_from_manifest`'s `p_plots` carries exactly the seven fields `import-
  seed.ts` already writes** (`svg_id, block, number, area_sqft, length_ft, breadth_ft,
  facing, is_corner`) — no `centroid`, no `confidence`, no `features`. Confirmed by grep
  (§1) that nothing in `apps/map` reads any of those today; adding columns/params for them
  is scope creep this plan explicitly rejects.
- **Schema validation imports the real `contract/colony.schema.json` via Ajv + `?raw`**,
  not a hand-rolled TypeScript re-statement of the schema's rules. This is a real,
  user-visible dependency addition (`ajv` in `apps/map/package.json`) — call it out in the
  build report's "Decided alone" line even though it's pinned here, since adding a runtime
  dependency is exactly the kind of choice CLAUDE.md's reporting format wants surfaced.
- **`colonies.svg` is a nullable column with no backfill migration.** Do not add one — see
  §2.1's reasoning (local-only DB, single fixture row, `import-seed.ts` updated in the same
  plan). If a future session finds a real deployed Supabase project with real colony rows
  predating this migration, that is new information this plan didn't have and needs its own
  decision, not a retrofit of this one.

## 6. Failure modes (spec/00-rules.md checklist)

### `create_colony_from_manifest` (§2.1)

1. **Partial writes** — the whole call (colony upsert + every plot upsert/insert + every
   `plot_history` insert) runs inside the function's own transaction; an unexpected error
   anywhere rolls back the entire call, including a create that got partway through its
   plot loop. Matches `bulk_set_initial_plot_data`'s existing guarantee exactly.
2. **Idempotency** — a byte-identical re-upload of the same manifest+SVG with `replace:
   true` is safe and re-applies (geometry columns get re-written to the same values,
   `plot_history` gets no new rows since the replace path never inserts history for
   already-existing plots) — deliberately not a strict no-op check, matching the plan-10
   "correction window" spirit for consistency, but the blast radius here is smaller since
   only geometry moves. Without `replace: true`, a repeat call is refused outright
   (`colony_exists`), never silently ignored.
3. **Concurrency** — the replace path's per-plot geometry update should `select ... for
   update` each existing row before updating it (same lock pattern as both existing RPCs),
   so a replace racing a live status write on the same plot serializes rather than racing;
   since the two touch disjoint columns this is defense-in-depth, not correctness-critical,
   but the lock pattern is free and consistent to keep.
4. **Orphans** — the entire point of the `would_orphan_history` refusal (§2.1, §3): an
   `svg_id` present in the DB but missing from a replace's manifest is caught and refused
   before any write, never silently dropped. A manifest `svg_id` with no `plots` row match
   on replace is simply inserted as a new plot (a re-cut adding a plot is not an orphan
   risk — nothing pointed at it before).
5. **Dead computation** — N/A. The function never touches `facing`/`is_corner`/`area_sqft`
   derivation logic — those arrive pre-computed from the manifest, same as `import-seed.ts`
   today (D-112: computed once, at export, in `tools/pipeline`).

### `ColonyUploadScreen.tsx` / client parsing (§2.2, §2.4)

1. **Partial writes** — N/A, no direct writes; the screen only ever calls the one RPC.
2. **Idempotency** — N/A, delegated to the RPC (above).
3. **Concurrency** — two family members uploading the same new colony id at once: the
   second call's `insert` on `colonies.id` (primary key) fails with a unique-violation,
   which is an unexpected error under this plan's classification (not one of the two named
   refusals) and so aborts/rolls back per failure mode 1 — surfaces to the second uploader
   as a generic failure, not a silent partial colony. Acceptable for a 5–6-person family
   tool; not worth a `select ... for update` on a table with no existing row to lock.
4. **Orphans** — the client-side `checkSvgIdsAgree` catches the manifest/SVG mismatch
   before any network call; the server-side `would_orphan_history` check catches the
