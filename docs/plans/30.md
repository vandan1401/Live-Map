# Plan 30 (revised) — Colony backdrop reachable from the app itself, reusing the exact functions already built

Owner direction (2026-09-12): backdrop upload should be reachable from the app's own colony
list, not only the local admin portal. On reflection (owner's own follow-up: "isn't this
too much effort... do we need migrations and all this?") this is **not** a rework of the
upload/manifest pipeline — plan 29's storage bucket, `colonies.backdrop_*` columns, and
`lib/colony/colonyBackdrop.ts`'s `uploadColonyBackdropImage`/`updateColonyBackdropTransform`
are reused byte-for-byte. The only real gap: those two functions only ever ran with the
admin-portal's service-role key, which bypasses RLS. Calling them from the app means calling
them with the ordinary signed-in (authenticated, anon-key) client, which today has **no**
write grant on either the Storage bucket or `colonies` at all. This plan's entire job is
opening exactly that door, as narrowly as it can be opened, and wiring one small UI to it.

The admin-portal backdrop feature (routes, UI) is **left in place, unchanged** — this plan
adds a second caller of the same two functions, not a replacement. (An earlier draft of
this plan removed it and routed everything through `create_colony_from_manifest()` instead
— reverted, per the owner's own pushback, before any of it was built. `contract/
colony.schema.json` and `contract/SPEC.md` are untouched by this plan; confirm `git status`
shows no changes there before starting.)

## 1. Context already true

- **Already shipped, reused as-is:** `colony-backdrops` Storage bucket (public,
  `<colonyId>.jpg`); 11 `colonies.backdrop_*` columns; `get_public_colony()`'s 10 non-admin
  fields; every rendering path (`resolveMapBackdropFromRow` and everything downstream). None
  of this changes.
- **`lib/colony/colonyBackdrop.ts`'s two functions, exact current bodies:**
  `uploadColonyBackdropImage(client, colonyId, {bytes, imageWidth, imageHeight})` uploads to
  Storage (`upsert: true`) then `client.from("colonies").update({backdrop_storage_path,
  backdrop_image_width, backdrop_image_height}).eq("id", colonyId)` — **no check that the
  update actually matched a row**. `updateColonyBackdropTransform(client, colonyId, args)`
  does the same shape of bare `.update()` for the other 8 columns. Both are client-agnostic
  today only because their one real caller (`admin-portal/backdropRoutes.ts`) always uses
  the service-role key, which bypasses RLS and privilege checks entirely — a `.eq("id",
  colonyId)` naming a real row always matches. That stops being true the moment an
  authenticated client calls them (task B).
- **Current grants/RLS on `colonies`, exact** (`20260815020000_m8_auth_rls_lockdown.sql:139`,
  `20260831000000_m16_organizations.sql:92-96`): `revoke insert, update, truncate on
  colonies, plots from anon, authenticated` (M8) — `authenticated` has **zero** write
  privilege on any column of `colonies` today, table-wide. The only SELECT policy is
  `colonies_authenticated_select` (`for select using (auth.role() = 'authenticated' and
  org_id = nullif(auth.jwt() -> 'app_metadata' ->> 'org_id', '')::uuid)`) — this is the exact
  expression task A's new UPDATE policy mirrors.
- **Postgres column-level privileges layer independently of a table-wide revoke.** `grant
  update (col_a, col_b) on t to role` after a blanket `revoke update on t from role` still
  lets `role` update exactly `col_a`/`col_b` — Postgres checks column-level ACLs
  independently of the table-level one. This is the mechanism that lets `authenticated`
  write the 11 `backdrop_*` columns without reopening `verified`, `svg`, `name`, or anything
  else on the same row — no RPC, no `security definer` function, needed for this.
- **Storage RLS today has no policy on `colony-backdrops` at all** (plan 29 §3: bucket is
  `public: true` for reads; writes only ever went through the service-role key, which
  bypasses Storage RLS the same way it bypasses table RLS).
- **`colonies.id` is a real, enforced-unique `text primary key`** — resolving
  `<colonyId>.jpg` back to exactly one `colonies.org_id` for the Storage policy (task A) is
  sound (same reasoning already recorded in the reverted draft of this plan).
- **`ColonyPicker.tsx` (79 lines) already lists every colony with a per-row action button**
  (`ShareLinkButton`, `apps/map/src/features/colony-picker/ShareLinkButton.tsx`) and its own
  "Upload a colony" button (`onUpload` prop, opens `ColonyUploadScreen` from `App.tsx`) —
  this is the actual "colony section" of the app, reachable without opening any colony's
  map, and the natural, precedented place for a second per-row action button.
  `App.tsx:44-45,118-128` already owns the exact `showUpload: boolean` /
  `<ColonyUploadScreen ... onClose={...} />` pattern this plan's own UI state mirrors.
- **Risk tier:** `apps/map/supabase/migrations/**` (task A) is Tier 1 regardless of how
  small the change is — `/plan` then `/review` applies. `ColonyPicker.tsx`,
  `lib/colony/colonyBackdrop.ts`, and the new screen component are all Tier 2
  (`apps/map/src/{features,lib/colony}/**`) — no separate Tier-1 gate for those files
  themselves, but the whole unit of work is planned/reviewed together since the migration
  is what makes the rest of it possible.

## 2. The exact task

**A. Migration — `apps/map/supabase/migrations/20260912020000_colony_backdrop_authenticated_write.sql`:**

```sql
-- Storage: an authenticated org member may upload/replace their own org's colony backdrop.
-- Two policies (insert + update) -- Storage's upsert resolves to an UPDATE at the
-- storage.objects row level on conflict, so both are needed for upsert:true to work for
-- this role the way it already does for the service-role key.
create policy "org members upload their own colony's backdrop"
on storage.objects for insert
to authenticated
with check (
  bucket_id = 'colony-backdrops'
  and exists (
    select 1 from colonies c
    where c.id = substring(name from '^(.*)\.jpg$')
      and c.org_id = nullif(auth.jwt() -> 'app_metadata' ->> 'org_id', '')::uuid
  )
);

create policy "org members replace their own colony's backdrop"
on storage.objects for update
to authenticated
using (
  bucket_id = 'colony-backdrops'
  and exists (
    select 1 from colonies c
    where c.id = substring(name from '^(.*)\.jpg$')
      and c.org_id = nullif(auth.jwt() -> 'app_metadata' ->> 'org_id', '')::uuid
  )
)
with check (
  bucket_id = 'colony-backdrops'
  and exists (
    select 1 from colonies c
    where c.id = substring(name from '^(.*)\.jpg$')
      and c.org_id = nullif(auth.jwt() -> 'app_metadata' ->> 'org_id', '')::uuid
  )
);

-- colonies: column-level grant, NOT a table-wide one -- authenticated stays unable to touch
-- verified/svg/name/status/anything else on this row. RLS policy below is still required
-- (a grant alone does not scope rows to the caller's own org).
grant update (
  backdrop_storage_path, backdrop_image_width, backdrop_image_height,
  backdrop_transform_x, backdrop_transform_y, backdrop_transform_scale,
  backdrop_transform_rotate_deg, backdrop_darken_alpha,
  backdrop_enabled_on_admin, backdrop_enabled_on_public, backdrop_attribution
) on colonies to authenticated;

create policy "colonies_authenticated_update_backdrop" on colonies
  for update using (
    auth.role() = 'authenticated'
    and org_id = nullif(auth.jwt() -> 'app_metadata' ->> 'org_id', '')::uuid
  )
  with check (
    auth.role() = 'authenticated'
    and org_id = nullif(auth.jwt() -> 'app_metadata' ->> 'org_id', '')::uuid
  );
```

Comment every policy inline (this repo's own convention, every prior migration does this) —
state plainly that the column-level grant, not the row policy, is what keeps this narrow to
backdrop fields, since that split is easy for a future reader to miss.

**B. `lib/colony/colonyBackdrop.ts` — fix the un-checked update, now load-bearing.** Both
functions must confirm their `.update()` actually matched a row, not just that it returned
no error — RLS silently matching zero rows (wrong org, or a typo'd/nonexistent colony id) is
indistinguishable from success unless the code checks. Add `.select("id").maybeSingle()` to
each `.update()` chain; if the returned data is `null`, throw a clear error (`"colony not
found, or you do not have access to it"` / similar) rather than resolving successfully. This
was always a latent gap (a wrong colony id passed to the admin-portal route today "succeeds"
having done nothing), not something newly introduced by RLS — fixing it here is pinned as
part of this plan, not a drive-by.

**C. New `apps/map/src/features/colony-picker/ColonyBackdropScreen.tsx`** — a full-screen
overlay, same shape as `ColonyUploadScreen.tsx`/`BulkImportScreen.tsx`. Props: `client:
SupabaseClient`, `colony: ColonyRow`, `onClose: () => void`. Renders:
- A file input (`accept="image/jpeg"`), "Upload image" button — reads `naturalWidth`/
  `naturalHeight` via a real `Image` decode (same technique
  `admin-portal/static/backdropEditor.js`'s `readImageDimensions` already uses, ported to
  TypeScript/React — a new small pure-ish helper, e.g. exported from this same file or a
  sibling `readImageDimensions.ts` if it needs its own test), then calls
  `uploadColonyBackdropImage(client, colony.id, { bytes, imageWidth, imageHeight })` directly
  with the **authenticated** `client` already passed down from `App.tsx` — no HTTP hop, no
  admin portal, relying on task A's new policies.
- 7 number/checkbox fields (x, y, scale, rotateDeg, darkenAlpha, enabledOnAdmin,
  enabledOnPublic) + 1 text field (attribution), pre-filled from `colony.backdrop_*` (already
  on every `ColonyRow` since plan 29 — no new fetch), "Save alignment" button calling
  `updateColonyBackdropTransform(client, colony.id, {...})` directly.
- Reads `isJpegBuffer` (`lib/colony/colonyBackdrop.ts`, kept, already unit-tested) against
  the file's first 3 bytes before ever uploading, same client-side-first-before-network
  posture as this app's other upload screens.

**D. `ColonyPicker.tsx`** — one new prop, `onBackdrop: (colonyId: string) => void`, one new
button per row next to `ShareLinkButton`:

```jsx
<button type="button" className="colony-picker-backdrop" onClick={() => onBackdrop(colony.id)}>
  Backdrop
</button>
```

**E. `App.tsx`** — mirrors the existing `showUpload`/`ColonyUploadScreen` pattern exactly:
new state `backdropColonyId: string | null`; `ColonyPicker` gets
`onBackdrop={setBackdropColonyId}`; when set, render `<ColonyBackdropScreen client={client}
colony={colonies.find((c) => c.id === backdropColonyId)!} onClose={() =>
setBackdropColonyId(null)} />` instead of the picker (same `!`-non-null-assertion
justification `App.tsx`'s existing `selectedColony` line already uses: this id only ever
comes from a button rendered for a colony already in `colonies`).

**F. Tests** — `colonyBackdrop.test.ts` gains: an authenticated-client success case (a real
scratch org member updates their own org's scratch colony's backdrop and it lands); an
authenticated-client **rejection** case (a scratch user from org A calling either function
against org B's colony gets the new "not found or no access" error, not a silent no-op) —
this is the one test the plan's whole security argument rests on, run for real, not assumed;
a nonexistent-colony-id case (same error, proving task B's fix independent of org). A
parallel Storage-RLS case (authenticated upload succeeds for the caller's own org's colony
path, is rejected for a different org's). `ColonyPicker.test.tsx` gains a render check that
the new "Backdrop" button appears per row and calls `onBackdrop` with the right id.

## 3. Pinned constraints

- **Column-level `grant update (...)`, never a table-wide grant** — this is the entire reason
  `authenticated` can touch backdrop fields but nothing else on `colonies`; do not simplify
  to `grant update on colonies to authenticated`.
- **Two Storage policies (insert + update), both with the same org-join `with check`** — an
  `upsert:true` call needs both; test the replace path (task F), not just the first upload.
- **Task B's row-matched check is not optional** — without it, RLS turns "wrong org" and
  "nonexistent colony" into silent successes instead of errors, for both callers (admin
  portal included) going forward.
- **The admin-portal backdrop feature is untouched** — do not remove or refactor
  `admin-portal/backdropRoutes.ts`/`backdropEditor.js`/`portal.js`'s existing "Backdrop"
  button. Two callers of the same two functions is fine here — they are not two
  *implementations*, just two UIs in front of one write path each, and admin-portal's
  service-role path remains a legitimate fallback (e.g. if RLS is ever misconfigured).
- **No changes to `contract/`, `create_colony_from_manifest()`, or `tools/pipeline`.**

## 4. Non-goals

- Removing or consolidating the admin-portal backdrop UI.
- Any manifest/JSON-upload involvement — backdrop stays entirely decoupled from
  `create_colony_from_manifest()`, reachable and editable independent of ever re-uploading
  a colony's svg/json.
- A drag-to-align UI — same plain numeric fields as the admin portal's version.
- Fixing `colonies.id`'s cross-org global-uniqueness gap — unrelated, still owner-deferred.

## 5. Acceptance criteria

- `mingw32-make gate` from repo root — same documented baseline (5 pre-existing failures,
  nothing new); `tools/pipeline` byte-identical and untouched.
- **The cross-org rejection tests (task F) actually use two independently created scratch
  orgs and fail red without task A's policies** — confirm by reading the diff.
- Applied for real against the local Docker Supabase instance; `apps/map`
  typecheck/lint/build clean, `dist/` clean of `admin-portal`.
- Not achievable from here: opening `ColonyBackdropScreen` in a real browser. Flag as

- Not run as part of this plan: applying the migration to production (same ordering as
  every prior phase — local first, verified, then production, owner-run, after
  `20260912000000`/`20260912010000`, which this migration depends on).

## 6. Failure modes

1. **Partial writes** — Storage upload then a separate `colonies` update (two round trips,
   same accepted shape as plan 29). An orphaned Storage object with no matching update is
   harmless (task B's fix doesn't change this — it only prevents a *silent* failure, not a
   *partial* one, which was already accepted).
2. **Idempotency** — unchanged from plan 29: `upsert:true` and plain field overwrites are
   naturally idempotent.
3. **Concurrency** — unchanged: last-write-wins, accepted (D-007, no finer-grained write
   protection anywhere else in this app either).
4. **Orphans** — unchanged from plan 29's own reasoning.
5. **Dead computation** — unchanged: image dimensions recorded once, at upload time.
