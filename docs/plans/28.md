# 28 — Bharatkshetra public link: synthetic aerial backdrop + real OSM place/road labels

Tier 2/3 (no `contract/` change, no plot-state write). `/plan` run per this project's own
process for a non-trivial multi-file addition; `/review` is not required by CLAUDE.md's risk
table for this path set, but `/check` is.

## 1. Context already true

- **D-022/D-027**: the ground texture is a mirror-tiled, non-georeferenced photo, painted by
  filling the whole visible world rect (`drawColony.ts` line ~92-93) before `fillDecor`
  draws roads/plots on top. This plan does not touch that mechanism — it adds one more draw
  call, for one colony only, layered on top of that same ground fill and under everything
  `fillDecor`/plots draw. Every other colony's render is byte-for-byte unchanged.
- **D-036 (this session, already applied)**: `spec/00-rules.md`'s "never build satellite/
  aerial imagery" row is narrowed to allow exactly this — a synthetic, AI-generated,
  OSM-vector-composited backdrop, per-colony opt-in via a checked-in config, never a
  default. Already edited; `docs/decisions/D-036-*.md` has the full reasoning. Nothing left
  to do here except not violate the narrow scope (no real satellite/drone photo, ever; no
  colony gets this without an explicit `mapBackdrop.json` entry).
- **D-034's precedent** (`apps/map/src/config/presentation.json`,
  `lib/colony/presentationConfig.ts`): per-colony config is a checked-in JSON file resolved
  client-side, not a database table, for exactly the reasons D-034 gives (5-6 users, changes
  a few times a year, no admin UI justified). This plan's `mapBackdrop.json` follows the same
  pattern — but shaped as `{ "<colonyId>": {...} }` with no `default` block, since "no
  backdrop" is the normal case for every colony that doesn't have an entry, not something
  needing a fallback value.
- **Coordinate system** (`view.ts`): world/SVG space is `model.width` × `model.height` SVG
  viewBox units (feet, via `px_per_ft`). `L.CRS.Simple` binds `lat = -y, lng = x`
  (`colonyLatLngBounds`, `leafletViewState`) — this is the ONLY place that flip is written
  down; nothing new in this plan re-derives it, everything below expresses positions as
  plain world `(x, y)` and lets existing helpers do the lat/lng conversion.
- **"Zoomed to colony on load" is already true, unchanged.** `usePublicColonyCanvas.ts`'s
  `fit()` calls `map.fitBounds(colonyLatLngBounds(model.width, model.height))` — this fits
  the colony's own bounding box, not the (much larger) backdrop raster's coverage. Because
  the backdrop is layered UNDER the existing colony render rather than replacing the fit
  target, the default view is already "zoomed to the colony" by construction, exactly as
  the owner asked. No new code is needed for this specific requirement — only: don't change
  `fit()`'s bounds argument, and don't let the backdrop asset's own size influence it.
- **The prototype's approved output** (`experiments/map-texture-poc/`, see memory
  `map-integration-exploration.md`) is the source of every number pinned below.
  `backdrop_duotone_v2.png` is BACKGROUND-ONLY (the punchier duotone treatment, no colony
  SVG baked into its pixels) — this is the file to ship, not `stitched_duotone_v2.png` or
  `stitched_bharatkshetra.png`, both of which have the SVG frozen into the raster and would
  visibly desync from the live plot layer the moment a status changes.
- Reusable functions: `colonyLatLngBounds`, `leafletViewState`, `visibleBounds` (`view.ts`);
  `loadGrass`-shaped async image loader pattern (`loadGrass.ts`); `ColonyCanvasLayer.
  setGrassImage`'s "construct with null, swap in once decoded" pattern
  (`colonyCanvasLayer.ts`) — the backdrop image load must follow this same
  don't-block-first-paint shape, not `useColonyCanvas.ts`'s eager-await one.

## 3. Pinned constraints

**Forward transform (SVG-world → raster-pixel), reused verbatim from `experiments/
map-texture-poc/bharatkshetra_transform_v2.json` — do not re-derive or re-eyeball:**
```
x = 731.25, y = 345.0, scale = 0.0703125, rotateDeg = 2.5
```
Composition (matches `bake_static.html`'s CSS exactly): `raster = translate(x,y) ·
rotate(rotateDeg) · scale(scale) · svgPoint`, transform-origin `(0,0)`. The canvas inverse
(`backdropPixelToWorld`, in the order `ctx.translate` → `ctx.rotate` → `ctx.scale` are
*applied*, which is the reverse of how they're *called* since each subsequent call
pre-multiplies) must produce:
```
svgPoint = (1/scale) · rotate(-rotateDeg) · (rasterPoint - (x, y))
```
Verified by hand this session (Python, `experiments/map-texture-poc/`): round-tripping
`(500, 600)` through forward-then-inverse returns `(500.0000000000005, 600.0000000000002)`
— float-tolerance exact. The unit test in §2.13 must assert the same round-trip.

**Backdrop image:** `imageWidth = 1440, imageHeight = 960` (native size of
`backdrop_duotone_v2.png` — do not resize/recompress in a way that changes these numbers
without also updating this config, since the transform above is pinned to this exact pixel
grid).

**Label world coordinates** (already converted from the raster-pixel positions in
`zoom_labels_demo.html` via the inverse transform above — do not recompute from scratch,
reuse these numbers). **Corrected mid-build (`/review` 2026-09-08, real content-honesty
finding):** the road labels originally shipped as `"Bibdod Road"` — the prototype's own

**Default view is a PADDED fit, not a tight one, for a backdrop colony** (also `/review`

tight fit.

**`minZoom`/`maxBounds` for a backdrop colony are DERIVED from the raster's own extent, not
a fixed guess — six `/review` 2026-09-08 passes to land on this:**
1. A first fix pinned `minZoom` at a guessed `-8`, which let a visitor pan/zoom out past the
   raster's own edge onto bare grass with no falloff (two of the six "MD2512" road-ref
   labels sit within a few dozen raster px of that edge).
2. A second fix computed `minZoom` from `mapBackdropTransform.ts`'s
   `backdropWorldBounds(transform, imageWidth, imageHeight)` (the raster's real
   axis-aligned world bounding box, from its 4 corners since `rotateDeg` tilts it) via
   `map.getBoundsZoom(bounds)` — still wrong: Leaflet's default (`inside: false`) returns
   the zoom at which the bounds fit ENTIRELY INSIDE the viewport (letterboxed), the opposite
   of "cover the viewport". On a portrait phone this left 61.5% of the screen as bare grass
   around the photo.
3. `useMapBackdrop.ts`'s `applyBackdropMinZoom(map, backdrop)` calls
   `map.setMinZoom(map.getBoundsZoom(bounds, true))` — `inside: true` returns the zoom at
   which the *viewport* fits inside the bounds instead, i.e. the raster covers the whole
   screen — and `map.setMaxBounds(bounds)`, so panning (not just zooming) can't reach past
   the same edge either. Called from `usePublicColonyCanvas.ts`'s `fit()` and again on
   every later resize, so an orientation change re-derives it rather than keeping a stale
   value. Every other colony keeps the original `minZoom: -2`, no `maxBounds` at all. Still
   not the final version — see 4.
4. Landed: a 4th pass (`/review` 2026-09-08, a third correction) found `getBoundsZoom`
   clamps its own return value to the map's CURRENT `minZoom`, so writing #3's result back
   into `minZoom` made every call after the first ratchet up-only — a resize into a MORE
   permissive orientation (e.g. portrait → landscape) silently lost zoom-out range instead
   of gaining it. Fixed by resetting to a named placeholder
   (`BACKDROP_PLACEHOLDER_MIN_ZOOM = -20`, exported from `useMapBackdrop.ts` and reused at
   `usePublicColonyCanvas.ts`'s `L.map()` construction so the two can't drift apart) via a
   `map.setMinZoom(BACKDROP_PLACEHOLDER_MIN_ZOOM)` call immediately before every
   re-measurement — safe, since `setMinZoom` only moves the camera when the *current* zoom
   is now out of range, never on its own. Still not the final version — see 5.
5. Landed: a 5th pass found `backdropWorldBounds` (used by #2-4 above) is the box
   CIRCUMSCRIBING the raster's rotated corners, not a coverage bound — with `rotateDeg`
   nonzero it's a strict superset of the real raster, so fitting the viewport inside it
   still left visible bare-grass wedges at the image's true (rotated) edges even while
   nominally "covering the screen". Fixed by adding `mapBackdropTransform.ts`'s
   `backdropCoveredWorldBounds` — the box actually INSCRIBED in the tilted raster, insetting
   the circumscribing one by the rotation overhang on each axis — and switching
   `applyBackdropMinZoom` to use that instead. Unlike the four passes before it, this one
   is also unit-tested directly (`mapBackdropTransform.test.ts`'s dedicated case), not just
   fixed and trusted, since this exact category of mistake had already happened once.
6. Landed: a 6th pass found the inset in #5 only stays positive-area up to
   `atan(imageHeight/imageWidth)` of rotation (33.7° for 1440×960) — past that the Y inset
   alone exceeds half the box and the result inverts (`minY > maxY`) with nothing
   downstream catching it (`L.latLngBounds` silently normalises an inverted pair). Fixed by
   having `backdropCoveredWorldBounds` throw in that case rather than hand a future
   colony's manual alignment a wrong, unflagged `minZoom`/`maxBounds` — Bharatkshetra's own
   `rotateDeg` (2.5°) is nowhere near this limit. Unit-tested (throws past the limit, does
   not throw at the pinned value).

**`VIGNETTE_FADE_RANGE` must match the prototype it's cited against, not an independent
guess** (also `/review` 2026-09-08 — a first value, `1.2`, cited the prototype but didn't
actually match its formula). The prototype's `edgeBlurOpacity()` fades over a **1.6x scale
ratio** (`(s - baseScale) / (baseScale * 0.6)`); Leaflet zoom is `log2(scale)` (`view.ts`'s
own header comment), so the equivalent zoom-delta is `Math.log2(1.6) ≈ 0.678`, computed in
code, not hardcoded as a decimal.

**Layer discipline** (`NAVIGATION.md`'s table, unchanged by this plan): `mapBackdrops.ts`'s
static import map is the only place a colony id is matched to an asset — no other new file
branches on `colonyId === "bharatkshetra"`. `resolveMapBackdrop` returning `null` must be a
complete, silent no-op everywhere it's checked (§2.10-11) — never a thrown error, never a
console warning (a colony with no backdrop is the overwhelmingly normal case, not a
degraded one).

**`is_corner`/`facing`-style "computed once, never at render" discipline does not apply
here** — the backdrop transform and label positions are static per-colony config, not
derived from live plot data; there is nothing to keep in sync at render time by
construction.

## 6. Failure modes

This task writes no database state — no `plots`, `plot_history`, `colonies` row, no
manifest, no migration. `spec/00-rules.md`'s "writing plot state" checklist is N/A.

Two real, open risks this plan does not fully resolve (a `/review` 2026-09-08 pass on the
first draft of this section pointed out that calling the first one "the one real, open
risk" was itself no longer accurate once the second was found):

1. **`backdrop-filter: blur()` on `.public-colony-backdrop-vignette` is a compositor-level
   effect that samples the frame underneath it every paint** — tier-3.md's "no SVG filters,
   blur forces a repaint on every zoom step" rule is about SVG filters specifically (this is
   a plain CSS backdrop-filter on one small fixed-position DOM element, not an SVG filter on
   redrawn map content), but the underlying concern — mobile Safari on an older iPhone is the
   real target device (tier-3.md) — is not proven fine here by any automated test, because
   none exists for this. If a human tester finds this janky on a real phone, the fix is a
   one-line, Tier-3, no-plan-needed removal (drop the `<div>` and its CSS, or gate it behind
   a cheap capability check).
2. **A failed/blocked backdrop image fetch is a real case on the stated target device (a
   rural-India phone on a public link), not a hypothetical one.** `useMapBackdrop.ts`'s
   `attachMapBackdrop` now tears down the label markers and forces the vignette to 0 opacity
   when `loadMapBackdropImage` resolves `null` (`/review` 2026-09-08 — without this, a
   failed fetch left the padded fit, raster-derived `minZoom`/`maxBounds`, a fully-opaque
   vignette, 9 label markers, and the ODbL attribution all applied around an image that
   never rendered, strictly worse than the ordinary no-backdrop render). Two pieces still
   don't react to the failure — the padded fit/`minZoom`/`maxBounds` stay as applied
   (reverting camera state after the fact was judged its own can of worms), and the ODbL
   attribution still renders (it's resolved synchronously from config, not from whether the
   async load actually succeeded) — both recorded in `PROGRESS.md` → `## Deferred`, not
   silently accepted.
