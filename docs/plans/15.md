# Plan 15 — Blockless plot IDs in the contract

**No spec file** — this isn't a pre-written milestone, it's a real-world trigger: the Jai Dev
Residency colony (mid-normalisation, `PROGRESS.md` → `## Current`) has bare plot numbers
`1`–`6` that are genuinely separate plots from its explicit `A-1`..`A-6` plots (owner-confirmed
directly this session), and the owner wants these to render as plain numeric IDs (`plot-14`),
not forced under an invented placeholder block letter. **Tier 1** — this is `contract/`
territory, invariant 1 ("changing it means changing both halves in one commit").

`tools/pipeline/colonies/jai-dev-residency.json` is explicitly **not** part of this plan —
there is still no `colony.dxf` for Jai Dev Residency in this repo (the owner has it, mid-
normalisation in AutoCAD, outside version control), so nothing can actually be exported
regardless of what this plan builds. This plan only makes the contract and both halves able
to *represent and handle* a blockless plot, verified with synthetic/unit-level data — the
same convention M10–M13 already use for `fixtures/shree-vatika-2/colony.dxf`, which also
doesn't exist yet.

## 1. Context already true

- **Today's contract hard-requires a block letter.** `contract/colony.schema.json`: plot
  `svg_id` pattern `^plot-[A-Z]+-[0-9]{2,}$`, `block` pattern `^[A-Z]+$`, both listed in
  `plots[].required`. `contract/SPEC.md:44`: "ID format: `plot-{BLOCK}-{NN}` — block uppercase,
  number zero-padded to two digits."
- **`plots.block` is already `text not null` with no format check at the DB level**
  (`apps/map/supabase/migrations/20260812120000_m2_schema.sql:33`) — an empty string is a
  legal value today, no migration needed.
- **`docs/cad-layer-standard.md`'s existing convention**: `blocks` in a colony config lists
  the block letters in use; "the first entry is the default, applied to bare numbers"
  (`docs/cad-layer-standard.md:47`). `pipeline.matching.assign.assign_plot_numbers`
  (`tools/pipeline/pipeline/matching/assign.py:45-105`) implements this today: bare labels
  (no `-`) resolve to `config.blocks[0]`; labels with `-` resolve to the named block if it's
  in `config.blocks`, else `MatchingError`.
- **`ColonyConfig`** (`tools/pipeline/pipeline/extract/types.py:39-51`) is the typed,
  already-loaded shape of `tools/pipeline/colonies/<id>.json`, built by
  `load_colony_config` (`tools/pipeline/pipeline/extract/dxf.py:32-50`).
- **Four `ColonyConfig(...)` construction call sites exist today**, all with `blocks=("A",)`:
  `tools/pipeline/pipeline/extract/dxf.py:38` (via `load_colony_config`, reads from JSON),
  `tools/pipeline/tests/test_matching.py:24`, `tools/pipeline/tests/test_export.py:37`,
  `tools/pipeline/tests/test_dxf.py:31`.
- **`tools/pipeline/colonies/shree-vatika-2.json`** is the one existing colony config
  (`blocks: ["A"]`, no other field to add for blockless support) — it must keep validating
  and keep exporting identical output; this plan does not change its behavior.
- **Display sites that assume `block` is always a non-empty letter, all doing
  `${block}-${number}` independently** (duplicated four times, no shared helper today):
  `apps/map/src/features/plot-detail/PlotDetailContent.tsx:16`,
  `apps/map/src/features/plot-table/PlotTableRow.tsx:52`,
  `apps/map/src/lib/colony/searchPlots.ts:17`,
  `apps/map/src/lib/colony/shareSummary.ts:40`.
  `apps/map/src/shared/format.ts` is the existing home for this kind of pure display helper
  (`formatRupees`, `formatDate`, `formatRelativeTime`, `formatStatusLabel`, `formatActorName`
  already live there) — reuse it, don't create a new file.
  `apps/map/src/features/colony-upload/ColonyUploadStageView.tsx:99-100` shows a distinct
  concern: the set of unique blocks across the whole manifest, joined by `", "` — an empty
  string in that `Set` needs handling too (it would otherwise show as a stray blank entry).
- **`extractSvgPlotIds`** (`apps/map/src/lib/colony/svgPlotIds.ts:6`) regex-matches
  `id="(plot-[A-Z]+-\d+)"` — used by both `scripts/import-seed.ts` and
  `parseColonyManifest.ts`'s `checkSvgIdsAgree`. Must recognize a blockless id too, or a
  blockless plot silently reads as "missing from the SVG" even when present.
- **`fetchPlotsByColony`** (`apps/map/src/lib/db/plots.ts:36-52`) orders by `svg_id` lexically

- **Existing test-fixture convention**: pure functions get inline-constructed test data, not

## 2. The exact task

### contract/ (Tier 1 core)

1. `contract/colony.schema.json`:
   - `plots[].properties.svg_id.pattern`: `^plot-[A-Z]+-[0-9]{2,}$` →
     `^plot-(?:[A-Z]+-)?[0-9]{2,}$`.
   - `plots[].properties.block.pattern`: `^[A-Z]+$` → `^[A-Z]*$` (allow empty string).
   - Leave `block` in `plots[].required` unchanged — a blockless plot still carries
     `"block": ""`, never an omitted field. This keeps `apps/map`'s `PlotRow`/manifest
     TypeScript types (`block: string`) untouched — no `| null` or `?` needed anywhere.
2. `contract/SPEC.md`:
   - Line 44: update the ID format line to state both shapes — `plot-{BLOCK}-{NN}` for a
     lettered plot, `plot-{NN}` for a blockless one, `block: ""` in the manifest for the
     latter.
   - Add a second example plot object to the `colony.json` sample block (§ colony.json,
     around line 62-67) showing a blockless plot alongside the existing `plot-A-14` one, e.g.
     `{ "svg_id": "plot-07", "block": "", "number": "07", ... }`.

### tools/pipeline/ (Tier 1 — matching/export)

3. `tools/pipeline/pipeline/extract/types.py`: add `default_block: str | None` to
   `ColonyConfig`, positioned after `blocks` — **no Python-level default value**, forcing
   every construction site to be explicit (only 4 exist, see §1). `None` means "bare numbers
   get no block"; a string means "bare numbers get this letter" (today's behavior, explicit
   instead of implicit).
4. `tools/pipeline/pipeline/extract/dxf.py`'s `load_colony_config` (lines 32-50): resolve
   `default_block` from the JSON as
   `data.get("default_block", data["blocks"][0] if data["blocks"] else None)` — so an
   existing colony config with no `default_block` key (i.e. `shree-vatika-2.json`,
   unmodified) keeps today's exact behavior, while a new config can opt into either a named
   default block or `null`/absent-`blocks` for blockless bare numbers via an explicit
   `"default_block": null` key.
5. `tools/pipeline/pipeline/matching/assign.py`'s `assign_plot_numbers` (lines 45-105): for a
   bare label (no `-`), use `config.default_block` instead of `config.blocks[0]`
   unconditionally:
   - `config.default_block` is a string → `block = config.default_block` (unchanged
     behavior when it equals `blocks[0]`).
   - `config.default_block is None` → `block = ""`.
   `default_block_count` still increments for every bare label regardless of which branch.
   `svg_id` construction: `f"plot-{block}-{padded}"` if `block` else `f"plot-{padded}"`.
   Explicit `BLOCK-NUMBER` labels are unaffected — still validated against `config.blocks`,
   unchanged.

   (`tests/test_matching.py:24`, `tests/test_export.py:37`, `tests/test_dxf.py:31`) to add

## 3. Pinned constraints

- **`block: ""` (empty string), never an omitted field, never `null`.** The schema keeps
  `block` in `plots[].required`; every plot object always has the key. This is what keeps
  `apps/map`'s existing `block: string` TypeScript type (`apps/map/src/lib/db/types.ts:38,110`)
  correct with zero type changes anywhere in `apps/map`.
- **`ColonyConfig.default_block: str | None` is a required dataclass field, no Python default
  value.** All 4 construction sites must be explicit. This is deliberate: a config that
  doesn't say what bare numbers mean is a bug waiting to happen, not a case to paper over
  with an implicit fallback at the dataclass level (the fallback lives in
  `load_colony_config` instead, where it can special-case "absent from the JSON file").
- **Backward compatibility is exact, not approximate**: `shree-vatika-2.json` is not touched.
  Loading it must produce `default_block="A"` (via the `data.get(...)` fallback in
  `load_colony_config`, since it has no `default_block` key and `blocks[0] == "A"`), and
  `make export`/the golden test against it must produce byte-identical output to before this
  plan.
- **Lexical sort consequence, accepted, not fixed here**: `fetchPlotsByColony`'s `order by
  svg_id ASC` means `"plot-07"` sorts before every `"plot-A-..."` id (ASCII `'0'` < `'A'`),
  so blockless plots as a group appear before all lettered-block plots in the table view,
  not interleaved by number. This is a real, visible consequence for a colony that mixes
  both — pin it as accepted for this plan (the trigger colony's exact display order is the
  owner's call once real data exists, not something to guess a fix for now).
- **`svg_id` regex change is additive only** — `^plot-[A-Z]+-[0-9]{2,}$` becomes
  `^plot-(?:[A-Z]+-)?[0-9]{2,}$`, a strict superset. No previously-valid id becomes invalid.
  Same for `block`'s `^[A-Z]+$` → `^[A-Z]*$`.
- **No `tools/pipeline/colonies/jai-dev-residency.json` in this plan** (§ header) — not even
  a draft. There is no `colony.dxf` for it in this repo to export against, so writing that
  config now would be unverifiable and premature.
- **No migration to `apps/map/supabase/migrations/`** — `plots.block text not null` already
  accepts `''`, confirmed in §1.

## 6. Failure modes

N/A for `apps/map/src/lib/plot-status/` / `plot_history` state writes — this plan touches no
write path, no RPC, no migration. Walking `spec/00-rules.md`'s checklist for what this plan
*does* touch (contract shape, config loading, id parsing/display):

- **Partial writes**: N/A — no multi-step write introduced.
- **Idempotency**: `assign_plot_numbers` is already pure/deterministic; the `default_block`
  branch adds no new source of non-determinism. Re-running `make export` against
  `shree-vatika-2.json` unchanged must still be byte-identical (pinned in §3).
- **Silent re-identification**: the risk this plan is *about* — a blockless id colliding with
  a lettered one, or two blockless plots colliding with each other. Both are already covered
  by `assign_plot_numbers`'s existing `seen: dict[str, Ring]` collision check (line 90-94),
  keyed on the final `svg_id` string — unchanged logic, just now also reachable with a
  blockless `svg_id` shape. §2 item 12's mixed-case test exercises this directly.
- **Orphans**: `extractSvgPlotIds`'s regex change (§2 item 11) is exactly what prevents a new
  orphan class — a blockless plot present in the SVG but invisible to `checkSvgIdsAgree`
  (or vice versa) would silently pass upload validation with a mismatched plot count.
- **Dead computation**: none introduced — every new field (`default_block`) and function
  (`formatPlotLabel`) has a real caller from the start (§2 items 4-5, 9).
