# Plan 21 — Multi-tenant data model: `organizations`, org-scoped RLS, existing data → org #1

**Tier 1.** First of three planned phases toward the SaaS conversion PROGRESS.md's
2026-08-27 entry explored (docs only, no code). This phase only: the data model and
row-level isolation. **Not in this phase:** the public per-colony link mechanism (phase 2)
and the owner's admin portal tool for creating orgs/adding people (phase 3) — see
Non-goals. This phase's own "admin" surface is a CLI arg and a hand-run SQL backfill,
nothing more.

## 1. Context already true

- The app is single-tenant today: one Supabase project, 5 real family accounts, RLS is
  `select`-only and `authenticated`-only with no further scoping
  (`apps/map/supabase/migrations/20260815020000_m8_auth_rls_lockdown.sql`, D-019, D-020,
  D-021). Public deployment is already permitted (D-021) — this phase does not touch that.
- Three security-definer RPCs already establish the exact pattern this phase extends:
  attribution/identity is **always derived server-side from `auth.jwt() -> 'app_metadata'`,
  never a client parameter** (D-020) — `apply_plot_transition()` (above migration),
  `bulk_set_initial_plot_data()` (`20260816000000_bulk_initial_plot_import.sql`),
  `create_colony_from_manifest()` (`20260817000000_m15_colony_upload.sql`). `app_metadata`
  is service-role-only to write; `scripts/create-user.ts` is the only place that happens
  today, setting `{ display_name }`. This phase adds `org_id` to that same object, written
  the same way, read the same way — not a new mechanism.
- Owner decisions locked in this session (not yet written anywhere else — record them here
  since this is the plan that acts on them):
  1. A user belongs to **exactly one** organization. No multi-org membership, no
     org-switcher UI, in this phase or planned later.
  2. The public link (phase 2) will be **per-colony**, not per-org — irrelevant to this
     phase's schema except that it confirms `colonies` stays the right unit for later,
     `organizations` is purely an isolation boundary above it.
  3. The admin portal (phase 3) is a **separate small tool**, not a screen inside
     `apps/map`'s shipped bundle — irrelevant to this phase except that it means this
     phase must leave org/user creation usable from a script or raw SQL, not block on a
     UI existing yet.
  4. Existing colonies + the 5 real accounts become **org #1** by migration. No
     re-onboarding.
- Schema today (`20260812120000_m2_schema.sql`): `colonies.id` is `text` (not uuid);
  `plots.id`/`plot_history.id` are `uuid default gen_random_uuid()`; `plots.colony_id`
  references `colonies(id)`; `plot_history.plot_id` references `plots(id)`. `pgcrypto` is
  already enabled (for `gen_random_uuid()`).
- Reusable functions/types to extend, by exact path — do not create parallel ones:
  `apps/map/src/lib/auth/testHelpers.ts` (`createScratchUser`, `serviceRoleClient`),
  `apps/map/src/lib/auth/rls.test.ts` (`createScratchPlot`, all three `describe` blocks),
  `apps/map/src/lib/db/types.ts` (`ColonyInsert`, `PlotInsert`), `apps/map/scripts/
  create-user.ts`, `apps/map/scripts/import-seed.ts`.

## 2. The exact task

**A. New migration, `apps/map/supabase/migrations/<timestamp>_m16_organizations.sql`:**

1. `create table organizations (id uuid primary key default gen_random_uuid(), name text
   not null, created_at timestamptz not null default now());`. Enable RLS on it too —
   `select`-only, `authenticated`-only, scoped to the caller's own org (mirrors the other
   three tables below) — no client role ever needs to read another org's row, and none
   needs to read the table at all yet (no UI reads it this phase), but leaving it
   RLS-disabled while every other table is locked down is the kind of asymmetry a later
   session won't think to double back on.
2. Add `org_id uuid not null references organizations(id)` to `colonies`, `plots`, and
   `plot_history` — denormalized on all three (not just `colonies`, joined from there) so
   RLS on `plots`/`plot_history` stays a flat column comparison, no join, matching this
   project's actual scale (PROGRESS.md 2026-08-27: ≤20 orgs, 1–15 colonies each, 5–10
   concurrent viewers — a join costs nothing here, but a flat comparison costs nothing
   either and is strictly harder to get wrong in a policy expression).
3. Backfill, in one `do $$ ... $$` block so the same generated id threads through every
   statement (a literal pasted in twice risks a typo'd mismatch): declare `v_org_id uuid :=
   gen_random_uuid()`; insert one `organizations` row with that id and
   `name = 'Original organisation (rename me)'` — a deliberate, obvious placeholder; do not
   guess the real business name from account usernames or passwords, neither of which is
   good evidence. Then `update colonies set org_id = v_org_id`, `update plots set org_id =
   v_org_id`, `update plot_history set org_id = v_org_id` (every existing row — there is
   exactly one tenant today by construction), then `update auth.users set raw_app_meta_data
   = raw_app_meta_data || jsonb_build_object('org_id', v_org_id::text)` for every existing
   row (all 5 real accounts + any test artifacts already in the target DB) — `auth.users`
   is a plain Postgres table, no Admin API needed for a bulk one-time backfill.
4. Update the three `_authenticated_select` policies from the M8 migration
   (`colonies_authenticated_select`, `plots_authenticated_select`,
   `plot_history_authenticated_select`) to add an org check to their `using` clause:
   `auth.role() = 'authenticated' and org_id = nullif(auth.jwt() -> 'app_metadata' ->>
   'org_id', '')::uuid`. `nullif(..., '')` before the cast matters: an absent or blank
   `org_id` claim must fail the equality (zero rows), never throw a cast error on empty
   string (spec/08 criterion 2's "zero rows, not a permission error" wording, which the
   M8 migration's own comment already commits to for the anon case — this preserves it for
   the "authenticated but somehow orgless" case too).
5. Alter `apply_plot_transition()`: after the existing `select * into v_current from plots
   where id = p_plot_id for update`, add a check that `v_current.org_id` equals the
   caller's own `org_id` claim (same expression as the RLS policies above); raise an
   exception naming it plainly (e.g. `'not authorized for this organization'`) if not. This
   is the load-bearing addition, not a formality — this function is `security definer` and
   its `select` bypasses RLS entirely, so without this check any authenticated user from
   any org could transition any plot in the database just by knowing/guessing its uuid.
   RLS only protects `select`/`update` issued directly through PostgREST; it does not
   protect what a security-definer function body does internally.
6. Alter `bulk_set_initial_plot_data()`: its per-row `update plots set ... where colony_id
   = p_colony_id and svg_id = v_row.svg_id` must also require `org_id = <caller's org>` in
   the same `where` — same reasoning as #5. A row that doesn't match now (wrong org) should
   fall into whatever this function's existing "not found / not eligible" skip path already
   is, not a separate new error shape.
7. Alter `create_colony_from_manifest()`: derive `v_org_id` once at the top the same way
   (`auth.jwt() -> 'app_metadata' ->> 'org_id'`, cast, raise if null/absent — an
   authenticated session with no org should never be able to create a colony). On the
   fresh-insert path, set this as the new colony's `org_id` and every inserted plot's
   `org_id`. On the `p_replace` path, **before** doing anything else, check the existing
   colony's current `org_id` equals `v_org_id`; if not, return the same
   `jsonb_build_object('ok', false, 'reason', ...)` shape this function already uses for
   `colony_exists` (pick a distinct reason string, e.g. `'org_mismatch'`) rather than
   raising — this function already talks to its caller in that shape, stay consistent.
   Never let a replace silently succeed against another org's colony.
8. Grants: `organizations` needs `select` granted to `anon, authenticated` (RLS still
   filters it) for symmetry with the other three tables' grant lines in the M8 migration;
   no client role gets `insert`/`update`/`delete` on it in this phase (org creation is
   phase 3's job, done via `service_role` only, same class of gap `scripts/create-user.ts`
   already fills for users).

**B. `apps/map/src/lib/db/types.ts`:** add `org_id: string` to `ColonyInsert` and
`PlotInsert` (flows automatically into `ColonyRow`/`PlotRow`, which extend them). This is
service-role-path-only — the real app never constructs one of these directly (Tier-2 rule:
inserts are grant-revoked for `anon`/`authenticated` since M8; the only client-visible path
is the RPCs above, which take no `org_id` parameter at all — it must not be added to
`create_colony_from_manifest`'s or `callCreateColonyFromManifest`'s TypeScript signature,
since it is derived server-side, never client-supplied, same as `p_actor` was removed in
M8). Grep for every call site of `insertColony(` and `insertPlots(` (at minimum:
`scripts/import-seed.ts`, `rls.test.ts`'s `createScratchPlot`) and update each to pass it —
do not rely on TypeScript alone to have caught every one silently.

**C. `apps/map/scripts/create-user.ts`:** add a required 4th positional CLI argument, the
org's uuid (`pnpm create-user <username> <password> "<Display Name>" <org_id>`). Fail loud
with the existing `fail()` helper if it's missing — same posture as the existing 3
required args, no default. Set `app_metadata: { display_name: displayName, org_id }`.

**D. `apps/map/scripts/import-seed.ts`:** it inserts `colonies`/`plots`/`plot_history`
directly via the service-role key (bypasses RLS and the RPCs entirely) — it needs an org id
too, from a new required CLI arg or env var (match this script's existing argument-parsing
style, whichever it already uses), applied to every row it writes. Fail loud if absent —
same posture as C.

**E. `apps/map/src/lib/auth/testHelpers.ts`:** `createScratchUser` gains a required `orgId:
string` parameter (no default org — a hidden shared default org between parallel test
files is exactly the kind of cross-test collision this table exists to prevent) and passes
`app_metadata: { display_name: displayName, org_id: orgId }`. Add a `createScratchOrg():
Promise<string>` helper (service-role insert into `organizations`, returns the new id) so
call sites can get one without hand-rolling the insert. Do **not** add a
`deleteScratchOrg`/wire org cleanup into `deleteScratchUser` — this repo's tests already
never clean up scratch colonies/plots either (they accumulate until `make db-reseed`,
per PROGRESS.md's 2026-08-25 and 2026-08-30 entries); matching that existing convention
avoids a foreign-key-order cleanup problem (an org can't be deleted while a colony still
references it) for no real benefit at this test volume. Leave a one-line comment saying so,
so a future session doesn't "fix" it into a FK violation.

**F. `apps/map/src/lib/auth/rls.test.ts`:** `createScratchPlot` takes an explicit `orgId:
string` parameter (no default) and sets it on the colony insert and the plot insert. Update
every existing call site to pass a scratch org's id. Add a new `describe` block — the
acceptance-critical test for this whole plan — proving cross-org isolation: two scratch
orgs, one scratch user per org, one scratch colony+plot per org; assert user A's `select`
for user B's plot/colony ids returns zero rows (not an error), and vice versa; also assert
`apply_plot_transition` called by user A against user B's plot id fails (the exception from
task A.5), not silently no-ops.

## 3. Pinned constraints

- **One org per user, no exceptions in this phase.** `org_id` lives as a single scalar in
  `app_metadata`, not an array, not a join table. A future multi-org-membership feature is
  a schema migration, not a compatibility shim to pre-build here.
- **`org_id` is always server-derived from the session, never a client parameter** — the
  exact D-020 shape. No RPC in this phase gains a `p_org_id` argument. No TypeScript
  function signature in `lib/db` or `lib/colony` gains an `orgId` parameter for the real
  app's write paths (test helpers and admin scripts are the only exception, since they act
  with the service-role key and have no session to derive from).
- **Every security-definer RPC that looks up a row by a client-supplied id must
  independently re-check org ownership.** RLS does not apply inside `security definer`
  function bodies. This is not optional hardening — without it, org isolation exists only
  for direct PostgREST queries and every RPC remains a cross-org write hole. Applies to all
  three RPCs named in task A (5, 6, 7); if a fourth security-definer function is added
  later in this same migration, it needs the same check.
- **Zero rows, never a permission error, for an absent/blank `org_id` claim** — same
  wording spec/08 criterion 2 already committed to for the anon case (M8 migration
  comment). Use `nullif(x, '')::uuid`, not a bare `::uuid` cast, in every policy
  expression that reads the claim.
- **The org #1 backfill runs inside one `do $$ ... $$` block**, one generated id reused
  by reference across every statement in it — never a literal pasted twice, never a
  second `gen_random_uuid()` call for the "same" org.
- **`organizations.name` for org #1 is an explicit, obvious placeholder string** (`
  'Original organisation (rename me)'`), not a guess at the real business name from
  existing account usernames/passwords. Renaming it is a one-line `update` the owner runs
  (or asks for) once they've decided — not blocking, not part of this plan's acceptance.
- **This migration touches the production Supabase project's real data** (5 real accounts,
  real colonies) once applied there, not just the local Docker instance `make gate` runs
  against. Per this repo's own risk posture (CLAUDE.md), running it against production is
  a separate, explicit step the owner confirms — this plan's acceptance criteria (below)
  cover the local gate only; running it against production is a distinct action to flag
  clearly and get a go-ahead for, not to bundle silently into "done."

  revoke a public link). Phase 3, later. This phase's only "admin" actions are the
  updated `create-user.ts` CLI arg and hand-run SQL for creating additional orgs beyond

- Renaming org #1 to the real business name.
- Anything in `contract/` — this phase is pure `apps/map` schema/RLS/RPC/script work; the
  SVG/manifest contract between the pipeline and the app is untouched.
- `tools/pipeline` — untouched. Its own test count/gate must come back byte-identical to
  before this plan.
- Self-hosting / Oracle Cloud migration (PROGRESS.md's separate, later hosting decision).

## 6. Failure modes

Walking `spec/00-rules.md`'s five, since this plan writes state (schema + a one-time data
backfill):

- **Partial writes.** Supabase applies each migration file inside one transaction by
  default — the backfill's `do $$ ... $$` block (task A.3) and the policy/RPC changes all
  live in the same file, so a failure partway rolls back the whole migration, not just the
  step that failed. Do not split the backfill into a second migration file that could apply
  after the first without it, or vice versa.
- **Idempotency.** This is a one-time forward migration (Supabase tracks applied
  migrations; it never reruns one that already succeeded), so idempotency-on-rerun isn't a
  real concern the way it is for `tools/pipeline`'s export. The concern that matters here is
  the opposite one, covered above: don't let the org id used across the backfill's several
  statements diverge from itself.
- **Concurrency.** Unchanged from before this plan for the actual write path —
  `apply_plot_transition`'s row lock and version check are untouched; task A.5 only adds a
  check before that logic runs, not a new lock or a new race window. The migration itself
  runs once, offline from any live traffic pattern this repo has (a solo local `make gate`
  run, or a scheduled production migration window) — not a concurrent-write scenario worth
  a dedicated test.
- **Orphans.** Going forward, `org_id not null` on all three tables means no row can exist
  without one — no orphan risk there. The real risk in this plan is not a data orphan but a
  *security* one: a security-definer RPC that forgets the org re-check (task constraint
  above) doesn't leave an orphaned row, it lets one org silently read or write another's
  data. That's why it's called out as its own pinned constraint rather than filed under
  this checklist item alone.
- **Dead computation.** N/A — every new column and check added here is read by the RLS
  policies or the RPCs in the same migration; nothing is written and never consulted.
