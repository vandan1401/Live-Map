# Plan 35 — auto-generate `colonies.public_token` at creation, backfill existing colonies

## 1. Context already true

- `colonies.public_token` (nullable `uuid unique`, added by
  `20260831010000_m17_public_colony_link.sql`, D-031) is null on every colony today unless
  someone explicitly ran `regeneratePublicLink()` — reachable only from the local-only
  admin-portal tool (`apps/map/admin-portal/`, port 5002, owner-run, `make admin-portal` is
  on CLAUDE.md's "Never run" list for Claude) or `pnpm generate-public-link` (`apps/map/
  scripts/generate-public-link.ts`).
- `ShareLinkButton.tsx` (`apps/map/src/features/colony-picker/`) only ever *reads*
  `colony.public_token` off the already-fetched `ColonyRow` and renders "No public link
  yet" when it's null. It has no write path and this plan does not give it one — that split
  (generate is admin-only, copy is everyone's) was itself owner ask, PROGRESS.md's
  2026-09-01 entry ("Copy share link" added to the home-screen colony picker), and stays.
- Colony creation is one RPC, `create_colony_from_manifest` (current live definition: the
  `create or replace function create_colony_from_manifest(...)` block in
  `apps/map/supabase/migrations/20260831000000_m16_organizations.sql:338-473` — confirmed
  this is the current definition by grepping every migration for the function name;
  `20260817000000_m15_colony_upload.sql` and `20260829000000_select_zoom_ref.sql` are
  earlier, superseded bodies, nothing after M16 touches it). This RPC is also invariant 2's
  "exactly one code path" that sets `verified = true` (D-025) — its own `comment on
  function` (lines 475-479) says so explicitly and says no `p_verified` parameter should
  ever be added. `pgcrypto` is already enabled (`20260812120000_m2_schema.sql:4`) and
  `gen_random_uuid()` is already used server-side elsewhere in this same function (the
  `v_org_id uuid := gen_random_uuid()` pattern one migration up, `20260831000000_m16_
  organizations.sql:52`, and in the `organizations`/`colonies` id columns' own defaults).
- `regeneratePublicLink()`'s own comment (`apps/map/src/lib/colony/publicColony.ts:15-18`)
  states D-031's existing rule: token generation is **not idempotent by design** — an
  explicit regenerate call invalidates whatever token existed. This plan does not touch
  `regeneratePublicLink`/`revokePublicLink` or that rule; it only changes what the *insert*
  branch of `create_colony_from_manifest` does, and, separately, adds a one-time backfill
  for rows that predate this change.
- Owner's ask this session, clarified via `AskUserQuestion`: auto-generate on colony
  creation (not: add a generate button to the main app; not: leave the current admin-only
  flow as-is).
- Working tree currently has unrelated uncommitted WIP (Cloudflare Worker + `wrangler.toml`
  + `publicLinkUrl.ts` hash-to-path rework for social-preview unfurling). **Do not touch
  those files.** This plan's only touch points are the migration, the RPC-body comment, and
  test files named below.

## 2. The exact task

1. New migration `apps/map/supabase/migrations/20260918000000_colony_upload_auto_public_
   link.sql`:
   - `create or replace function create_colony_from_manifest(...)` — **same 9-argument
     signature**, unchanged (no PostgREST schema-cache reload needed; D-033 only requires
     that when a function's *parameter list* changes, and this change is body-only, same
     precedent as `20260913000000_colony_backdrop_any_image_format.sql`'s RLS-only change
     needing no reload).
   - In the `insert into colonies (...)` branch (currently lines 411-418 of the M16 file —
     re-read the file fresh before editing, line numbers will have shifted once this new
     migration exists), add `public_token` to the column list and `gen_random_uuid()` to
     the values list. Every *newly created* colony gets a token the moment
     `create_colony_from_manifest` inserts it — no second call, no client-supplied value.
   - In the `update colonies set ... where id = p_colony_id` replace branch (currently
     lines 405-409), **do not** touch `public_token` in the common case — an existing,
     already-shared link must never silently rotate out from under whoever has it (D-031).
     But also add: `and public_token is null` is wrong (that's a `where`, not a `set`)  —
     instead add `public_token = coalesce(public_token, gen_random_uuid())` to the `set`
     list. This is the mechanism that also backfills any *pre-existing* colony the moment
     it's next replaced/re-uploaded, at zero extra cost, and is a no-op (keeps the current
     value) for every colony that already has one.
   - Update the `comment on function create_colony_from_manifest is '...'` string
     (currently lines 475-~485) to document the new behaviour in the same voice as the
     existing comment (mentions the `verified` invariant already) — add one sentence: every
     colony this function creates or replaces ends up with a non-null `public_token`
     (generated once, never rotated by this function after that).
   - One-time backfill statement in the same migration, after the function replace:
     `update colonies set public_token = gen_random_uuid() where public_token is null;`
     — covers every colony that exists today and would otherwise wait for its next
     re-upload to get a link. Unconditional (not scoped to `verified = true`) is fine:
     an unverified colony is invisible to `ColonyPicker`/`ShareLinkButton` regardless
     (`fetchColoniesByOrg`/the picker's own `verified: true` filter, D-108), so giving it a
     token too is harmless and one line simpler than filtering.
2. `apps/map/src/lib/colony/createColonyFromManifest.test.ts` — add assertions, no new
   `it()` blocks needed beyond what's listed:
   - In the existing "creates a colony with verified: true and plots seeded under the
     import sentinel" test (line 74), add `expect(colony?.public_token).not.toBeNull();`
     right after the existing `expect(colony?.verified).toBe(true)` (line 85).
   - In the existing "replace updates only geometry columns..." test (line 135), capture
     `before.public_token` (fetch it alongside `before` at line 138) and assert
     `after?.public_token === before?.public_token` — proves a replace never rotates an
     existing token.
   - New test: "a replace gives a pre-existing null public_token a value, without
     rotating it on a second replace" — create a colony (gets a token from step 1 above,
     can't easily reach the pre-migration null state through the app's own RPC anymore, so
     instead: use `serviceRoleClient()` to directly `update colonies set public_token =
     null` after creation, simulating an old row), call `createColonyFromManifest(...,
     true)` to replace it, assert `public_token` is now non-null, then replace a second
     time and assert it's the *same* value as after the first replace (not rotated again).
3. No app code changes — `ShareLinkButton.tsx`/`ColonyPicker.tsx`/`publicColony.ts` are
   already correct for "read whatever `public_token` is on the row"; they just start
   getting a non-null value sooner.

## 3. Pinned constraints

- `create_colony_from_manifest`'s parameter list stays exactly the existing 9 arguments —
  do not add a `p_public_token` parameter. Token generation is server-only, matching how
  `v_org_id` is already derived server-side, never client-supplied (D-020's shape).
- `gen_random_uuid()` only, from the already-enabled `pgcrypto` extension — no new
  extension, no `uuid-ossp`.
- The insert branch: unconditional `gen_random_uuid()`. The replace branch:
  `coalesce(public_token, gen_random_uuid())` — never overwrite a non-null value. This is
  the one load-bearing rule of this whole plan; getting it backwards silently breaks every
  link already shared with a family member or posted somewhere.
- Backfill statement runs once, in this migration, unconditionally on `public_token is
  null` — not scoped to `verified`, per the reasoning in task 1 above.
- Do not modify `regeneratePublicLink`, `revokePublicLink`, `ShareLinkButton.tsx`,
  `ColonyPicker.tsx`, the admin-portal, or any file under the currently-uncommitted
  Worker/`publicLinkUrl.ts` rework.

## 6. Failure modes

This task writes state (a migration + a backfill `UPDATE`) — walking `spec/00-rules.md`'s
checklist:

- **Partial writes.** The backfill `UPDATE ... where public_token is null` is a single
  statement, atomic by Postgres default. The function-body replace (`create or replace
  function`) is DDL, also atomic. No multi-step client-side sequence to leave half-done.
- **Idempotency.** Running this migration twice: the `create or replace function` is
  idempotent by construction (replaces itself with the same body). The backfill `UPDATE`
  is idempotent in effect — the first run sets every null token to a fresh UUID; the second
  run finds no rows matching `public_token is null` and updates nothing. Re-running
  `create_colony_from_manifest` itself on the same colony (a second replace) must **not**
  regenerate the token — pinned above via `coalesce`.
- **Concurrency.** No new concurrency surface — `public_token` was never part of the
  optimistic-concurrency (`version`) machinery `applyPlotTransition` owns, and this plan
  doesn't touch plots at all, only `colonies`. Two concurrent replaces of the same colony
  already serialize through Postgres's normal row-level locking on the `update`; the
  `coalesce` makes the outcome the same regardless of interleaving (both either see a
  non-null token and leave it, or one of them wins setting the first non-null value).
- **Orphans.** None created — this plan never deletes or disconnects anything; it only
  ever turns a `null` into a `uuid` on a row that already exists.
- **Dead computation.** None — every token generated is immediately live: readable by
  `ShareLinkButton` (already-fetched `ColonyRow`) and resolvable by `get_public_colony`
  (M17) the moment it's set, no unused intermediate state.

## Deviation from this plan (found during `/review`)

§2.1 and §6 above pinned `coalesce(public_token, gen_random_uuid())` on the replace
branch, reasoning it would only ever backfill a pre-migration null token. `/review` caught
that this was wrong once combined with the one-time backfill: after the backfill runs, the
*only* way a colony reaches the replace branch with a null token is a deliberate
`revokePublicLink()` call, and `coalesce` would silently un-revoke it on the next
re-upload. Shipped instead: the replace branch never touches `public_token` at all — see
`PROGRESS.md`'s 2026-09-18 entries (`## Current` and `## Log`) for the full reasoning.
