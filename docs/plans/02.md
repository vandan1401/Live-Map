## 2. The exact task

1. `apps/map/supabase/migrations/20260813000000_m4_apply_plot_transition.sql` — new
   migration, additive only (no edits to the M2 migration file). Adds one Postgres
   function, `apply_plot_transition(p_plot_id uuid, p_expected_version integer,
   p_new_status text, p_actor text, p_note text default null) returns plots`, `language
   plpgsql`, default `security invoker` (anon/authenticated already hold the table grants
   from M2; no elevation needed). Body (see §3 for the exact contract):
   - `select * into v_current from plots where id = p_plot_id for update;` — row lock,
     re-reads the true committed row if blocked behind a concurrent writer.
   - Not found → `raise exception ... using errcode = 'P0002'` (reuses Postgres's
     standard `no_data_found` code — this is a programmer error, not a business outcome).
   - Version mismatch → `raise exception 'version_conflict:%', v_current.updated_by;` —
     message-prefix-based, not SQLSTATE-based (PostgREST's SQLSTATE passthrough for
     custom codes is not something to depend on; the message text is ours to control).
   - Else: `update plots set status = p_new_status, version = version + 1, updated_by =
     p_actor, updated_at = now() where id = p_plot_id returning * into v_current;` then
     `insert into plot_history (plot_id, status, changed_by, note) values (p_plot_id,
     p_new_status, p_actor, p_note);` then `return v_current;`.
   - Explicit `grant execute on function apply_plot_transition(uuid, integer, text, text,
     text) to anon, authenticated;` — don't rely on Postgres's default-PUBLIC-execute
     behaviour being obvious to the next reader; the table grants in M2 were all explicit
     too.
2. `apps/map/src/lib/plot-status/transitions.ts` — `PLOT_TRANSITIONS: Record<PlotStatus,
   PlotStatus[]>` (the amended D-013 table, §3) and `isLegalTransition(from, to): boolean`.
3. `apps/map/src/lib/plot-status/recentEdit.ts` — `RECENT_EDIT_WARNING_MINUTES = 5` (named,
   commented with why — spec/04 pins this number explicitly) and `isRecentlyEdited(updatedAt:
   string, now: Date): boolean`.
4. `apps/map/src/lib/db/plotTransitions.ts` — the only file allowed to call
   `client.rpc('apply_plot_transition', ...)` (layer rule: `supabase.from`/`.rpc` only in
   `lib/db/`, NAVIGATION.md). One function, `callApplyPlotTransition(client, args):
   Promise<PlotRow>`, throws on any RPC error including the `version_conflict:` one —
   parsing that message into a typed result is the domain layer's job, not `lib/db`'s.
5. `apps/map/src/lib/plot-status/applyPlotTransition.ts` — the single write entry point.
   Exact shape pinned in §3. Validates legality **before** any network call (short-circuits
   illegal transitions with zero DB round-trips — testable by asserting a spy client's
   `.rpc` was never invoked). Calls `callApplyPlotTransition`; on a thrown error whose
   message starts with `version_conflict:`, parses the winner's name and returns a
   `conflict` result instead of throwing.
6. Tests (all new, TDD — write first per `/build`'s rule for `lib/*` pure layers):

## 3. Pinned constraints

- **The legal transition table** (D-013, amended):
  ```
  available  → booked, hold
  booked     → registered, available
  hold       → available
  registered → available
  ```
  Same-status "transitions" (e.g. `available → available`) are **not** legal — the table
  has no self-entries, and `isLegalTransition` returns `false` for them. A Save action
  that doesn't change status is a UI-level no-op, not a call into this function.
- **`applyPlotTransition()`'s exact signature and return type** — this is the one write
  path per `plots.status`; nothing else may call `plots.update()` or the RPC directly:
  ```ts
  export type PlotTransitionResult =
    | { ok: true; plot: PlotRow }
    | { ok: false; reason: "illegal_transition" }
    | { ok: false; reason: "conflict"; winnerName: string };

  export async function applyPlotTransition(
    client: SupabaseClient,
    input: {
      plotId: string;
      fromStatus: PlotStatus;
      toStatus: PlotStatus;
      expectedVersion: number;
      actor: string;
      note?: string | null;
    },
  ): Promise<PlotTransitionResult>
  ```
  `illegal_transition` and `conflict` are **typed outcomes, never thrown** — spec/04:
  "Mismatch returns a typed conflict." Anything else unexpected (network failure, plot not
  found, a genuinely unknown Postgres error) throws, because those are not business
  outcomes a caller should be routing UI copy on.
- **Undo is not a new function.** Per spec/04, undo is "a new forward transition with a new
  history row" — the Tier 2 UI follow-up calls `applyPlotTransition()` again with
  `toStatus` set to the status in `history[1]` (the row before the most recent one) and
  `fromStatus`/`expectedVersion` from the current read. No domain-layer change needed for
  this; noted here only so the follow-up doesn't invent a second write path.
- **Atomicity is enforced by the database function, not by the two-call sequence.** Two
  separate `supabase-js` calls (`.update()` then `.insert()`) cannot be atomic — a network
  partition between them is a real partial-write path. The Postgres function body is one
  transaction; that's the actual mechanism, and the "forced mid-write failure" acceptance
  test (§5) has to prove *that*, not just that the function "looks like" one transaction.
- **Concurrency is enforced by `select ... for update`, not by the version check alone.**
  A bare `select` + conditional `update` is the exact race `spec/00-rules.md` warns about
  ("a race with a comfortable-looking shape"). The row lock is what makes the second
  concurrent caller block and re-read the post-commit version before its own check runs.
- **`RECENT_EDIT_WARNING_MINUTES = 5`** (spec/04 pins this number explicitly as a business
  trade-off — do not let it drift to a different value without updating the spec too).
- **Actor is an opaque string** (D-016) — `applyPlotTransition` does not validate it against
  a roster, does not look it up anywhere, just stores what it's given. Any validation
  (non-empty, trimmed) belongs to the Tier 2 UI that collects it, not this layer.

**Scratch-data strategy for integration tests (#2–#4):** insert a throwaway colony
(`id: 'test-m4-<random suffix>'`) and one plot per test via the existing `insertColony`/
`insertPlots` functions, using a fresh random suffix per test run. There is **no delete
grant** on these tables (M2's migration withheld it deliberately) — scratch rows are
harmless residue in the local dev DB, not a real colony, and are cleared by
`supabase db reset` whenever that's next run for another reason. Do not touch
`fixtures/shree-vatika-2/`'s real rows in any test.

## 6. Failure modes (spec/00-rules.md checklist, applied to this task)

1. **Partial writes** — this is the task's entire point. Handled by the single
   `apply_plot_transition` Postgres function being one transaction; proved by criterion 3's
   forced-failure test, not assumed from the SQL "looking atomic."
2. **Idempotency** — a double-tap must append exactly one history row. Handled by the
   version check rejecting the second call outright; proved by criterion 4.
3. **Concurrency** — two clients writing the same plot; one must fail named. Handled by
   `select ... for update`; proved by criterion 2's real concurrent test, not by the
   presence of the row lock in the SQL.
4. **Orphans** — N/A here; this task writes to existing rows, it does not create
   plot/SVG associations.
5. **Dead computation** — N/A; this task touches `status`, `version`, `updated_by`,
   `updated_at` only. `facing`/`is_corner`/`area_sqft` are untouched, exactly as M2 left
   them.
