# Plan 23 — Multi-tenant SaaS conversion, phase 3 of 3: the admin portal

**Tier 1** (identity — this tool creates accounts and assigns organization membership,
the same class of action `scripts/create-user.ts` already performs). Third and last of the
three planned phases (docs/plans/21.md's Non-goals). Phase 1 (`organizations`, org-scoped
RLS, D-030) and phase 2 (the public per-colony link, D-031) are both complete, committed,
applied locally only. This phase: a small local web tool — owner-run, never deployed —
covering the four actions docs/plans/21.md's Non-goals named for this phase: create an
org, create a user, assign a user to an org, generate/revoke a colony's public link.

## 1. Context already true

- **No new database schema.** `organizations` (`id, name, created_at`) and `org_id` on
  `colonies`/`plots`/`plot_history` already exist (`20260831000000_m16_organizations.sql`,
  D-030); `colonies.public_token` already exists
  (`20260831010000_m17_public_colony_link.sql`, D-031). This phase adds **zero migrations**
  — it is pure application code, reading/writing tables that already exist with the grants
  they already have.
- **The owner decided, and plan 21 recorded (§1, decision 3):** "The admin portal (phase 3)
  is a **separate small tool**, not a screen inside `apps/map`'s shipped bundle." This is
  the one phase that actually builds that tool — phases 1 and 2 deliberately stayed at "a
  CLI arg and hand-run SQL."
- **The established precedent for "a separate small tool" already exists in this repo:**
  `tools/pipeline/ui/` (PROGRESS.md 2026-08-30) — a local server bound to `127.0.0.1` only,
  never started by Claude (CLAUDE.md's guard hook blocks `make ui`, "long-running servers
  are mine"), plain HTML/JS/CSS with no build step (D-114's "verify page is three files,
  not one" philosophy carried over). This phase follows the same shape, in this app's own
  ecosystem (Node/TypeScript, not Flask) since it needs `@supabase/supabase-js`'s Admin API
  the same way `scripts/create-user.ts` already does.
- **Every account-creation/attribution mechanism this tool touches already has an
  established, unforgeable shape — reuse it, do not invent a second one:**
  `usernameToEmail(username)` (`apps/map/src/lib/auth/username.ts`) is "the one place
  username validation lives," throwing `InvalidUsernameError` on a bad username — reused by
  the login form and `create-user.ts`; this tool's user-creation route must call it too, not
  re-validate independently. `app_metadata` (not `user_metadata`) is the only place
  `display_name`/`org_id` live, service-role-write-only (D-020) — `client.auth.admin.*`
  calls, never a `.from("auth.users")` query (there is no such PostgREST table exposed).
- **The `.from()`-only-in-`lib/db` rule (tier-2.md) does not extend to `client.auth.admin.*`
  calls** — `create-user.ts` and `testHelpers.ts`'s `createScratchUser` already call
  `client.auth.admin.createUser(...)` directly, inline, with no `lib/` wrapper. This tool's
  user-management logic (create/list/reassign) follows that same precedent: inline in the
  tool's own action module, not a new `lib/auth/adminUsers.ts` layer that nothing else needs.
  Reads/writes against `organizations`/`colonies` **do** go through `lib/db`, per that same
  rule, extending the existing files rather than querying from a third place.
- **Reusable functions/types to extend, by exact path — do not create parallel ones:**
  `apps/map/src/lib/db/colonies.ts` (`fetchColonyById`, the `.rpc`/`.from` convention to
  match), `apps/map/src/lib/colony/publicColony.ts` (the domain layer that already owns
  public-link semantics, D-031 — this phase's link actions belong here, not reinvented in
  the portal), `apps/map/src/lib/auth/username.ts` (`usernameToEmail`,
  `InvalidUsernameError`), `apps/map/src/lib/db/client.ts` (`createDbClient`), `apps/map/
  scripts/generate-public-link.ts` (today inlines the token-generation logic this phase
  must promote into a shared function — see task B).
- **`scripts/generate-public-link.ts`'s current logic is the one piece of near-duplicate
  work this plan must not re-copy**: it directly does
  `client.from("colonies").update({ public_token: token })`. Once the portal needs the same
  action, that logic is promoted into `lib/colony/publicColony.ts` and the script calls the
  promoted function too — one implementation, two callers, matching this repo's "reuse by
  exact path" convention throughout `docs/plans/21.md`/`22.md`.

## 2. The exact task

**A. `apps/map/src/lib/db/organizations.ts`** (new — mirrors `colonies.ts`'s shape,
`.from()` lives here per tier-2.md):
- `fetchOrganizations(client): Promise<OrganizationRow[]>` — `select * from organizations
  order by name`.
- `insertOrganization(client, name: string): Promise<OrganizationRow>` — `insert into
  organizations (name) ... select().single()`. No validation beyond non-empty (Postgres's
  `not null` already guards the column) — an org name is free text, unlike a username.
- `OrganizationRow` type (`apps/map/src/lib/db/types.ts`): `{ id: string; name: string;
  created_at: string }`.

**B. `apps/map/src/lib/colony/publicColony.ts`** — add two functions, promoted out of
`scripts/generate-public-link.ts`'s inline logic:
- `regeneratePublicLink(client, colonyId): Promise<{ ok: true; token: string } | { ok:
  false; reason: "colony_not_found" }>` — looks up the colony via `fetchColonyById`
  (`lib/db/colonies.ts`), generates `crypto.randomUUID()`, updates `public_token`, returns
  the new token. Not idempotent by design (D-031 territory: regenerating invalidates the
  previous link) — same behavior `generate-public-link.ts` already has today, just moved.
- `revokePublicLink(client, colonyId): Promise<void>` — `update colonies set public_token =
  null where id = colonyId`. New capability — today this is hand-run SQL per docs/plans/
  22.md task H; this phase is what makes it a button instead, per plan 21's Non-goals list
  for this phase ("generate/revoke a public link").
- **`scripts/generate-public-link.ts` is refactored to call `regeneratePublicLink`**
  instead of inlining the update — its CLI behavior (usage message, output format, exit
  codes) must not change; this is a pure internal refactor. Re-verify its existing
  acceptance bar (docs/plans/22.md task J: runs for real, fails loud on an unknown id,
  succeeds with a real one) still holds after the refactor.

**C. `apps/map/admin-portal/actions.ts`** (new — the tool's own domain layer, one file,
plain functions taking a `SupabaseClient` and returning typed data or throwing, exactly
like `lib/colony/*.ts`'s existing shape, but living outside `src/` since this tool is never
part of the shipped bundle):
- `listOrgUsers(client, orgId): Promise<{ id: string; email: string; displayName: string |
  null }[]>` — `client.auth.admin.listUsers({ page, perPage: 200 })`, looping pages until a
  page returns fewer than `perPage` (handles this project's real scale, PROGRESS.md
  2026-08-27: ≤20 orgs, 5–10 users each, so in practice one page — the loop exists so a
  future larger deployment doesn't silently truncate), filtering client-side on
  `user.app_metadata.org_id === orgId` (there is no server-side filter in the Admin API for
  a custom `app_metadata` field). Never reads/returns `user_metadata` (D-020's
  unforgeability boundary — this tool must not treat it as authoritative for the same
  reason `getDisplayName` in `lib/auth/session.ts` does not).
- `createOrgUser(client, args: { username: string; password: string; displayName: string;
  orgId: string }): Promise<{ id: string }>` — calls `usernameToEmail(args.username)` first
  (propagates `InvalidUsernameError` on a bad username, caught by the route handler below
  into a 400), then `client.auth.admin.createUser({ email, password, email_confirm: true,
  app_metadata: { display_name: args.displayName, org_id: args.orgId } })` — identical
  shape to `create-user.ts`'s own call, this phase's second caller of that exact pattern.
- `reassignUserOrg(client, userId, newOrgId): Promise<void>` — **fetches the user first**
  (`client.auth.admin.getUserById(userId)`), rebuilds `app_metadata` as `{ ...current,
  org_id: newOrgId }` (preserving `display_name` and anything else already there), then
  calls `updateUserById(userId, { app_metadata: merged })`. Fetch-then-merge as defense in
  depth — **update, post-build:** GoTrue's Admin API was measured to already merge
  `app_metadata` server-side on its own (see the corrected §3 note), so a bare
  `{ app_metadata: { org_id: newOrgId } }` would not actually have dropped `display_name`
  the way this task originally assumed by analogy to phase 1's raw-SQL backfill bug — keep
  the fetch-then-merge anyway since it stays correct regardless of that undocumented
  server-side behavior.

**D. `apps/map/admin-portal/server.ts`** (new — plain `node:http`, no new dependency, same
"Node's built-in" posture `generate-public-link.ts` already established for
`crypto.randomUUID()`): routes, each requiring `Content-Type: application/json` on every
mutating request (see Pinned constraints — the CSRF mitigation) and reading
`VITE_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` from `.env` the same way every existing
script does (`process.loadEnvFile?.()`, then fail loud if either is missing, before the
server even starts listening):

| Method | Path | Calls |
|---|---|---|
| GET | `/api/organizations` | `fetchOrganizations` |
| POST | `/api/organizations` `{name}` | `insertOrganization` |
| GET | `/api/organizations/:id/users` | `listOrgUsers` |
| POST | `/api/users` `{username,password,displayName,orgId}` | `createOrgUser` |
| PATCH | `/api/users/:id` `{orgId}` | `reassignUserOrg` |
| GET | `/api/organizations/:id/colonies` | `fetchColoniesByOrg` (task E) |
| POST | `/api/colonies/:id/public-link` | `regeneratePublicLink` |
| DELETE | `/api/colonies/:id/public-link` | `revokePublicLink` |

Every route catches a thrown error and returns `{ ok: false, error: message }` with a 4xx/
5xx status — same "errors reach the operator as a sentence, not a stack trace" posture
`tools/pipeline/ui/server.py` already established (tier-3.md's CLI-error rule, carried over
even though this is Tier 1 code, since the audience — the owner, at a terminal — is the
same). Static files (`admin-portal/static/{index.html,portal.js,portal.css}`) served for
any non-`/api` GET. `main()` binds `127.0.0.1` only, port `5002` (pipeline UI already owns
`5001`).

**E. `apps/map/src/lib/db/colonies.ts`:** add `fetchColoniesByOrg(client, orgId):
Promise<ColonyRow[]>` — `select * from colonies where org_id = orgId order by name`. Same

## 3. Pinned constraints

- **Zero new database migrations.** Every table/column/RPC this phase touches already
  exists from phases 1 and 2. If a build session finds itself wanting a new column here,
  stop — that is scope creep past this plan, not an implementation detail.
- **This tool is never deployed, never bound beyond `127.0.0.1`, and never started by
  Claude** — the same posture `tools/pipeline/ui/` already established, extended with a
  guard-hook rule (task I) and a `CLAUDE.md` "Never run" entry (task J) before this plan is
  considered done, not as an afterthought.
- **No login/auth layer on the portal itself.** Its trust boundary is "whoever has shell
  access to run it locally with the `.env`'s `SUPABASE_SERVICE_ROLE_KEY` already has full
  admin access to that Supabase project regardless" — identical to every existing script.
  Do not add a password gate; it would be theater over the same boundary the service-role
  key already draws.
- **Every mutating route requires `Content-Type: application/json`, rejecting anything
  else before touching Supabase.** This is a real, cheap CSRF mitigation, not decoration —
  unlike `tools/pipeline/ui/`'s file-processing actions, this tool can create user accounts
  and reassign organization membership, a higher blast radius than that precedent's own
  posture covers, and a stray cross-site form POST cannot forge a JSON content-type without
  script access to the page (which same-origin/CORS already blocks for a cross-site
  caller).
- **`app_metadata` is read-then-merged in `reassignUserOrg`, as defense in depth — not
  because it is strictly required.** The plan originally assumed, by analogy to phase 1's
  raw-SQL `||` backfill bug, that a bare `{ app_metadata: { org_id: newOrgId } }` would
  silently drop `display_name`. **Measured directly against the local Supabase instance
  during the build (2026-08-31, confirmed again during `/review` via a direct
  `PUT /auth/v1/admin/users/<id>` probe): GoTrue's Admin API already merges `app_metadata`
  server-side on its own** — a bare overwrite does not drop `display_name`. That assumption
  does not transfer from phase 1's hand-written SQL `update` to this Admin API call; the
  two are different code paths with different behavior. `reassignUserOrg` keeps the
  fetch-then-merge anyway, since it stays correct even if that server-side behavior is ever
  undocumented-and-changed, but it is not the acceptance-critical line the original text
  claimed — the "fails red against a naive overwrite" acceptance criterion in §5 below is
  correspondingly **not achievable** and was dropped after being tested once, per the note
  there.
- **Whichever Supabase project's credentials are in `.env` is the project this tool acts
  on** — same as every existing script (`create-user.ts`, `generate-public-link.ts`,
  `import-seed.ts`). Running this tool against the production project is exactly as
  consequential as running any of those against production, and gets the same "confirm
  which environment first" posture this repo's Log entries already establish for
  `create-user.ts` (PROGRESS.md 2026-08-25: "after confirming with the owner which
  environment... since it's real, hard-to-reverse state on a shared system").
- **This tool never reads or displays plot-level data** (status, owner, money, history) —
  its whole scope is organizations, user/org membership, and a colony's public-link token
  only. Reaching into `plots` for anything is out of scope, a finding if it appears.
- **Port 5002**, not colliding with `tools/pipeline/ui/`'s `5001`.

## 6. Failure modes

Walking `spec/00-rules.md`'s five, since this plan writes state (new orgs, new user
accounts, org reassignment, public-link tokens) via a persistent local server rather than a
one-shot script:

- **Partial writes.** Every write this tool performs is a single Supabase call
  (`insert`/`update`/one Admin API call) — no multi-step write to leave half-done.
  `reassignUserOrg`'s fetch-then-merge is a read followed by one write, not two writes; a
  crash between them leaves the user's `app_metadata` exactly as it was before the call,
  never half-updated.
- **Idempotency.** `insertOrganization`/`createOrgUser` are not idempotent by design —
  calling either twice creates two rows/accounts, matching every other creation path in
  this app (`create-user.ts` already has this exact property). `reassignUserOrg` and
  `revokePublicLink` **are** idempotent — calling either twice with the same arguments
  produces the same end state, which is the correct semantics for "set this field to X."
  `regeneratePublicLink` is deliberately **not** idempotent (same as `generate-public-
  link.ts` today) — rerunning it must produce a new token, invalidating the old one.
- **Concurrency.** This tool has one operator (the owner) running it locally, ad hoc — not
  a concurrent-write scenario worth a dedicated test, same conclusion plan 21 reached for
  its own one-time migration. `reassignUserOrg`'s fetch-then-merge has a theoretical
  last-write-wins race if two admin actions targeted the same user's `app_metadata`
  simultaneously from two different tools; not worth guarding against at "one owner, one
  browser tab" usage.
- **Orphans.** An organization with zero users or zero colonies is not an orphan — it's a
  normal, valid state (a newly created org before anyone's been added to it). No new table
  is created that could hold a row nothing references.
- **Dead computation.** N/A beyond the normal bar — every route, action function, and UI
  control in this plan is exercised by the new tests in task K or the manual run in
  acceptance; nothing is added speculatively for a later phase.
