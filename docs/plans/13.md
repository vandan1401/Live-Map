## 1. Context already true

- **M10 and M11 are built.** `pipeline.extract.types` gives `Ring(layer, handle, points)`,
  `Label(layer, handle, text, point)`, `ColonyConfig(id, name, units, expected_plots,
  blocks, number_width, number_range, north_deg, source)`. `pipeline.geom` gives
  `contains(ring, point) -> bool` and `GeomError` — reuse `contains` directly for the one
  containment test this module needs; do not reimplement point-in-polygon.
- **Matching assumes the geom stage already ran.** By the time `pipeline.matching` sees
  rings, `validate_ring`/`validate_disjoint`/`validate_within` have already guaranteed each
  ring is closed, non-self-intersecting, mutually non-overlapping (beyond
  `AREA_OVERLAP_TOLERANCE_SQFT`), and inside `COL-SITE`. This module does not re-validate
  ring geometry — it only resolves identity and kind.
- **D-118 rewrote spec/12 from scratch.** The old three-rung ladder (contained →
  nearest-within-threshold → flag) and the `nearest` distance threshold are deleted. There
  is **one** containment test: a label belongs to the ring that contains its insertion
  point. Every other outcome is a hard error naming the entity handle(s) — not a flag, not
  a best guess. Do not resurrect a distance-threshold fallback.
- **`DxfIngestResult.rings` and `.labels` are not pre-split by kind.** `rings` mixes
  `COL-SITE`/`COL-PLOT`/`COL-GARDEN`/`COL-AMENITY`/`COL-WATER`; `labels` mixes
  `COL-PLOT-NO`/`COL-FEATURE-NO`. This module's functions take pre-filtered
  `Sequence[Ring]`/`Sequence[Label]` (same convention as `pipeline.geom.validate_disjoint`,
  which also takes a `Sequence[Ring]` rather than a whole ingest result) — filtering by
  layer is the caller's job (a CLI wiring or a later M13 orchestration step), not this
  module's. `COL-SITE` never reaches either function in this module.
- **Existing error-reporting idiom to match**: `DxfConformanceError`
  (`pipeline/extract/dxf.py:28-29`) and `GeomError` (`pipeline/geom/__init__.py:31-34`) both
  raise, never return a bool, and always name the entity handle. Add one new exception,
  `MatchingError`, same shape, reused by both `assign.py` and `classify.py` — put it
  somewhere both import from without duplicating the class (e.g. `pipeline/matching/__init__.py`).
- **`docs/cad-layer-standard.md`'s feature keyword table is the source of truth for
  `classify.py`'s keyword constant**, current text (already edited this session, uncommitted):
  `CLUB`/`COMMUNITY` → `clubhouse`, `GARDEN`/`PARK`/`OPEN SPACE`/`GREEN` → `park`,
  `TEMPLE`/`MANDIR` → `temple`, `OHT`/`TANK`/`SUMP` → `tank`, `PARKING` → `parking`,
  `RESERVED` → `reserved`, `OTHER` → `other`. Case-insensitive substring match against the
  label's stripped text (already MTEXT-stripped/whitespace-stripped by
  `pipeline.extract.dxf._read_label`). Checked in the order listed above; the first keyword
  group that matches wins — pinned here so a label matching two groups (unlikely, but
  possible) has a deterministic outcome instead of an implementation-order accident.
- **Blocking prerequisite, already identified and logged in `PROGRESS.md` → `## Deferred`
  (2026-08-20, plan 12's `/review` pass): `contract/colony.schema.json`'s `kind` enum

  to change alongside it.
- **`docs/cad-layer-standard.md`'s keyword table has no keyword mapped to `playground`**

## 2. The exact task

**Task 0 — contract prerequisite (Tier 1, `contract/`):**
- `contract/colony.schema.json`: add `"reserved"` and `"other"` to the `kind` enum
  (currently line 74: `"enum": ["park", "clubhouse", "temple", "tank", "playground", "parking"]`).
- `contract/SPEC.md`: update the `amenity` row (line 24, currently "clubhouse, temple,
  tank, playground, parking") and the `data-kind` sentence (lines 30-31, currently lists
  `clubhouse`, `temple`, `tank`, `parking`, `park`) to include `reserved` and `other`, so
  the doc, the schema, and `docs/cad-layer-standard.md` all agree on the same seven-value
  set: `park`, `clubhouse`, `temple`, `tank`, `playground`, `parking`, `reserved`, `other`.
- Verify with `make contract` (must stay green — no fixture currently uses these two
  values, so this is a pure enum-widening, non-breaking change) before writing any
  `pipeline/matching` code.

**Task 1 — `tools/pipeline/pipeline/matching/assign.py`** (identity):
Implement a function taking pre-filtered `Sequence[Ring]` (the colony's `COL-PLOT` rings),
`Sequence[Label]` (its `COL-PLOT-NO` labels), and the colony's `ColonyConfig`, that:
1. Regex-validates every label's text against `^([A-Z]+-)?[0-9]+$` before anything else —
   reject with `MatchingError` naming the label's handle and its literal text otherwise
   (covers criterion 7: `12.5M`, `7A` must never reach block/number resolution).
2. Matches each ring to the label(s) whose `.point` it contains (via `pipeline.geom.contains`).
   Raise `MatchingError`, naming the offending handle(s), for: a ring with zero matching
   labels; a ring with two or more matching labels (name both label handles); a label
   matching zero rings; a label matching more than one ring (the ambiguous case the spec's
   "anything ambiguous is a hard error" goal covers even though it isn't individually
   enumerated in the acceptance table).
3. Resolves each matched label's block/number per spec/12 "Block resolution and padding":
   no prefix → `config.blocks[0]`; explicit prefix → must be in `config.blocks` or error;
   number must fall within `config.number_range` (inclusive) or error; number's decimal
   digit count must not exceed `config.number_width` or error (criterion 10: `100` with
   width `2` errors, it is never truncated or silently allowed through); otherwise
   zero-pad to `config.number_width` and build `svg_id = f"plot-{block}-{padded_number}"`.
4. After resolving every ring, raise `MatchingError` naming both ring handles if two rings
   produced the same `svg_id` (criterion 6).
5. Counts and returns, alongside the matched plots, how many took the default block vs. an
   explicit prefix — as a structured field on the return value (a dataclass), not a
   `print()`/log line, so a caller or test can assert on it directly.

**Task 2 — `tools/pipeline/pipeline/matching/classify.py`** (classification):
Implement a function taking pre-filtered `Sequence[Ring]` (the colony's
`COL-GARDEN`/`COL-AMENITY`/`COL-WATER` rings) and `Sequence[Label]` (its `COL-FEATURE-NO`
labels) that:
1. Derives each ring's class directly from its layer: `COL-GARDEN` → `garden`,
   `COL-AMENITY` → `amenity`, `COL-WATER` → `water`. No area clustering, no keyword ladder
   over the ring itself, no "unclassified defaults to garden" — all three are deleted per
   spec/12 and must not reappear.
2. Runs the same containment matching as Task 1 step 2 (one label per ring, both
   directions) — reuse the matching logic rather than re-deriving it a second time (see
   §1's `MatchingError`-sharing note; a small shared internal helper used by both
   `assign.py` and `classify.py` is the expected shape, exact location left to the
   implementer).
3. Resolves each matched ring's `kind` from its label's text against the keyword constant
   in §1 (case-insensitive substring, first match in table order wins). A label matching no
   keyword group is a `MatchingError` naming the entity handle (criterion 13's `XYZ` case)
   — never a default.
4. Returns one typed value per ring carrying at least: the ring (or its handle), the
   matched label, the derived `class`, and the resolved `kind`. Feature `svg_id`
   construction is **not** this module's job (see §4) — do not build one.

**Task 3 — tests first**, `tests/test_matching.py` (new file), synthetic `Ring`/`Label`/
`ColonyConfig` data only, following `tests/test_dxf.py`'s in-memory-construction
convention (§1). Cover every criterion in §5's table individually — one test per row is
expected, not one combined test, so a future regression names exactly which behavior broke.

## 3. Pinned constraints

- **The containment ladder is gone. One test, `pipeline.geom.contains`, no distance
  threshold, no `nearest` fallback anywhere in this module.** Reintroducing one is the
  single most likely wrong turn here (D-118, tier-1.md "Matching is identity" — "never add
  a rung that guesses").
- **`MatchingError`** — new exception, same raise-only shape as `DxfConformanceError`/
  `GeomError`: always names the entity handle(s) involved, never returns a bool or a
  result/flag object.
- **`number_width` is read from config only, never derived from the drawing or from the
  matched set's own max number** (docs/cad-layer-standard.md's own stated reason: a
  colony growing from 99 to 100 plots must not silently re-pad every `svg_id` and orphan
  `plots`/`plot_history` rows already in the database — invariant 5).
- **A number whose digit count exceeds `number_width` is an error, not a truncation or a
  silent wider pad** (criterion 10). This is a distinct check from `number_range` (criterion
  11) — both must exist; a number can be inside `number_range` and still be too wide for
  `number_width` (they are independent config values, not derived from each other).
- **`confidence` is not this module's concern.** Spec/12 says it is always written as
  `"manual"` on this path, but that field belongs to the manifest M13/export produces —
  `assign.py`'s return type does not need a `confidence` field; do not add one speculatively.
- **The keyword table constant must stay textually in sync with
  `docs/cad-layer-standard.md`'s table and with `contract/colony.schema.json`'s `kind`
  enum.** This exact drift (a doc edit adding `RESERVED`/`OTHER` without updating the
  schema) is what blocked this plan from starting cleanly — see §1. A future edit to any
  one of the three (the doc's table, this constant, the schema's enum) without the other
  two is a `/review` finding.
- **No file-format import** (`ezdxf`, `fitz`, `cv2`, `PIL`) anywhere in
  `pipeline/matching/` — same purity boundary as `pipeline/geom/` (tier-1.md, tier-2.md
  "format code stays at the edge"). Depending on `pipeline.extract.types` and
  `pipeline.geom` is fine and expected.
