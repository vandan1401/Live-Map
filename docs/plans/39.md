## 2. The exact task

1. `apps/map/src/lib/auth/changePassword.ts` (new). Export `MIN_PASSWORD_LENGTH` and
   `changePassword({ client, verifyClient, email, current, next, confirm })` returning
   `{ ok: true, othersSignedOut: boolean } | { ok: false, reason, message }` with `reason` one of
   `"too-short" | "mismatch" | "same" | "wrong-current" | "rate-limited" | "recent-login-needed" | "failed"`.
   Order, pinned:
   a. Client-side validation first, no network: new length ≥ 8; new === confirm; new !== current.
   b. Verify the CURRENT password server-side: `verifyClient.auth.signInWithPassword({ email, password: current })`.
      `verifyClient` is a STATELESS client (`persistSession:false, autoRefreshToken:false`) so the live
      session is never replaced. Any error → `wrong-current` (or `rate-limited` for HTTP 429 / code
      `over_request_rate_limit`). Immediately after a successful verify, `verifyClient.auth.signOut({ scope: "local" })`
      (swallow its error) so the extra session this created is revoked at once.
   c. `client.auth.updateUser({ password: next })` on the live client. Map GoTrue codes:
      `same_password` → `same`; `reauthentication_needed` / `reauthentication_not_valid` →
      `recent-login-needed`; 429 → `rate-limited`; anything else → `failed`.
   d. Only after (c) succeeds: `client.auth.signOut({ scope: "others" })`. If THIS call errors, the
      password IS changed: return `{ ok: true, othersSignedOut: false }`, never a failure.
2. `apps/map/src/lib/db/browserClient.ts`: `getBrowserDbClient(options?)` passes `options` through to
   `createDbClient` (default behaviour unchanged).
3. `apps/map/src/features/auth/ChangePasswordDialog.tsx` (new): overlay reusing the `login-screen-*`
   classes; fields Current / New / Confirm (all `type="password"`, `autoComplete` `current-password` /
   `new-password`), Cancel, Submit disabled while submitting; shows the `message` on failure; on success
   shows "Password changed." plus "Your other devices were signed out." only when `othersSignedOut`, and
   a Close button. Props: `client`, `email`, `onClose`, optional `createVerifyClient` (defaults to a
   stateless `getBrowserDbClient`) for tests. It clears all three fields after any submit.
4. `ColonyPicker.tsx`: new prop `onChangePassword`; a "Change password" button next to `Log out` in
   BOTH branches. `App.tsx`: state to show the dialog while `session` exists, `email = session.user.email`
   (if absent, do not render the button path: same stance as `getDisplayName` returning null).
   `colony-picker.css`: a `.colony-picker-change-password` style that does not overlap `.colony-picker-logout`.
5. Tests (new): `src/lib/auth/changePassword.test.ts` (pure/mocked: validation order, error mapping,
   `othersSignedOut:false` path, verify session cleaned, no network on invalid input);
   `src/lib/auth/changePassword.live.test.ts` against the local stack with a scratch user:
   wrong current refused and password unchanged; success then login works with the new password and fails
   with the old; a second signed-in client (other device) is signed out after success while the changing
   session stays valid; `same` refused; rate-limit not asserted. `ChangePasswordDialog.test.tsx`
   (render, submit, failure message, success copy, fields cleared). `ColonyPicker.test.tsx`: the button
   renders in both branches and calls the callback.
6. NAVIGATION.md: one row for `changePassword`. Do not touch `admin-portal/`.

## 3. Pinned constraints

- Minimum new password length: **8** (matches the admin portal). No maximum, no complexity rules.
- The current password is verified by GoTrue, never compared in the browser. No password, and no GoTrue
  raw error text, is ever logged, thrown in a message, or put in the DOM beyond the fixed messages.
- Fixed user-facing messages: wrong current → "Current password is incorrect."; too short → "New password
  must be at least 8 characters."; mismatch → "The new passwords do not match."; same → "Choose a password
  different from your current one."; rate limited → "Too many attempts. Wait a minute and try again.";
  recent login needed → "Please sign out, sign in again, then change your password."; failed → "Could not
  change the password. Try again."
- Other devices are signed out with `scope: "others"` (not `"global"`, which would log the user out
  here too). The device changing the password stays signed in.
- No server, migration, GoTrue-config or Tailscale change. Works unchanged on cloud and on the box.
- `src/` imports nothing from `admin-portal/`. If `MIN_PASSWORD_LENGTH` is duplicated, a test must pin
  the two values equal.
- Every file ≤ 250 lines (invariant 7).

## 6. Failure modes (spec/00-rules.md, apps/map: writing state; here the write is a GoTrue password)

1. **Partial writes** — three steps: verify, update, sign out others. Verify failing writes nothing.
   Update failing leaves the old password intact. Update succeeding then sign-out-others failing is a
   SUCCESS with `othersSignedOut:false`; it is never reported as a failure (that would tell the user their
   new password did not take when it did).
2. **Idempotency** — a double-tap: the submit button is disabled while in flight. A repeated submit
   after success fails at verify (the current password is now the new one) with a clear message, never
   a second change.
3. **Concurrency** — two devices changing at once: each verifies the current password first, so the
   second fails with "Current password is incorrect" once the first lands; last writer cannot silently win.
   Tested with the live test's second client for the sign-out part.
4. **Orphans** — the stateless verify session is revoked immediately (`scope:"local"`); no stray
   long-lived refresh token is left behind.
5. **Dead computation** — N/A (nothing derived or stored by the app).

## Deviations from this plan (found in /review, all fixed before commit)

- §2.1b said "any verify error → `wrong-current`". Wrong: a dropped connection or a 5xx would have told a
  member their correct password was wrong. Now ONLY GoTrue's `invalid_credentials` is `wrong-current`;
  everything else is `failed` ("Check your connection and try again"). New reason `weak-password`.
- §3/§6 claimed step d (`signOut({scope:"others"})`) is what signs other devices out. GoTrue's own
  `updateUser({password})` already revokes the other sessions; step d is a backup. The success copy now says
  "will be signed out within the hour" because an access token already on a lost device stays valid until it
  expires (JWT_EXPIRY, about an hour).
- An update refused because this device's own session is gone (`AuthSessionMissingError` /
  `session_not_found`) now says to sign in again instead of "Try again".
- `showChangePassword` is reset when the session ends, so the dialog cannot reappear for the next person who
  signs in on a shared phone.
- Live test strengthened: asserts the specific error name for the other device, and proves the verify session
  is revoked on the server (forced-failure case) by trying to refresh it. Test users are deleted afterwards.
