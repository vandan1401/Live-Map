## 1. Context already true

  point is `apps/map/src/components/map/colonyTheme.ts`: the canvas renderer never paints a
  literal colour, it calls `resolveColonyTheme()`, which reads CSS custom properties off

  colour today is a `--colony-status-*` variable in `apps/map/src/styles/colony-theme.css`
  (lines 76-78: `available`/`booked`/`registered`; a fourth, `--colony-status-hold`, exists

  values and fails the build if one appears outside `colony-theme.css`. A JSON config file
  is data, not source, so this is unaffected — but no new hex literal may appear in any
  `.ts`/`.tsx` file as part of this work.
- `plots.status` is `text` with a DB CHECK restricted to `'available', 'booked',
  'registered', 'hold'` (`20260812120000_m2_schema.sql`), and the TypeScript `PlotStatus`
  type (`apps/map/src/lib/db/types.ts:4`) is the literal union `"available" | "booked" |
  "registered"`. The legal-transition table (D-013, `apps/map/src/lib/plot-status/
  transitions.ts`) is keyed on exactly those three. **This plan does not add, remove, or
  rename a status.** It only makes each existing status's *display name* and *colour*

  Tier-1 plan — it touches `transitions.ts`, the DB CHECK, and `apply_plot_transition()`/
  `bulk_set_initial_plot_data()`'s own status validation — deliberately not attempted here
  (user decision this session: ship the safe JSON-config version now, split the arbitrary-

- `formatStatusLabel(status: string): string` (`apps/map/src/shared/format.ts:67-70`) is
  the one place status display text is produced today (`"registered"` → `"Registry done"`,
  everything else capitalised). Six call sites: `StatusLegend.tsx`, `PlotStatusActions.tsx`,
  `PlotTableRow.tsx`, `PlotDetailContent.tsx`, `shareSummary.ts`, and `format.test.ts`.
- `NO_OWNER_TOKENS = new Set(["", "NMC"])` (`apps/map/src/lib/colony/
  parseBulkImportFile.ts:33`) is the CSV bulk-import convention for "this cell means no
  owner yet" (D-029). It is a plain module constant today, read by
  `parseSimpleBulkImportRows`, called by `parseSimpleBulkImportCsv`, called from

  props).
- `ColonyPicker.tsx:30,45` hardcodes the literal heading `"Nimantran Group Colonies"` in two
  JSX return branches (empty-state and populated-state).
- `drawPlotDimensions()` (`apps/map/src/components/map/drawDimensions.ts:99-141`) is the one

  as `` `${ft} ft` `` (line 139). Its one caller is `drawColony.ts:213`, itself called by
  both `useColonyCanvas.ts` (private map) and, per NAVIGATION.md, shared with

- Reuse, do not reimplement: `formatPlotLabel` (existing), `resolveColonyTheme` (existing,

## 2. The exact task

Add one checked-in JSON config file and a single pure resolver, then thread the resolved
values through five existing call sites. No new component, no new screen, no new table, no
migration.

**2.1 — Config file and resolver**

- `apps/map/src/config/presentation.json` — one file, shape:
  ```json
  {
    "default": {
      "homeHeading": "Nimantran Group Colonies",
      "noOwnerTokens": ["", "NMC"],
      "statusLabels": { "available": "Available", "booked": "Booked", "registered": "Registry done" },
      "statusColors": { "available": "#e8b84b", "booked": "#3b82f6", "registered": "#ff145a" },
      "dimension": { "offset": 1, "textFormat": "{value} ft" }
    },
    "colonies": {
      "bharatkshetra": { "noOwnerTokens": ["", "IV"] }
    }
  }
  ```
  The `default` block's values are exactly today's hardcoded values (see §1) — this file's
  first commit changes no behaviour anywhere. `colonies.<id>` entries are a **shallow
  per-key override**: an entry present in a colony's block replaces that whole key's value
  (e.g. `noOwnerTokens`) from `default`; a key absent from the colony's block falls back to
  `default`'s value for that key. No deep-merge inside `statusLabels`/`statusColors` (a
  colony overriding one status colour must repeat all three) — this keeps the resolver a
  single `{ ...default, ...override }` object spread, no recursive merge code to test.
- `apps/map/src/lib/colony/presentationConfig.ts` (Domain layer, DOM-free per
  NAVIGATION.md's layer table) — imports the JSON, exports:
  - `interface PresentationConfig { homeHeading: string; noOwnerTokens: string[];
    statusLabels: Record<PlotStatus, string>; statusColors: Record<PlotStatus, string>;
    dimension: { offset: number; textFormat: string } }`
  - `resolvePresentationConfig(colonyId?: string): PresentationConfig` — `colonyId`
    omitted (or matching no entry in `colonies`) returns `default` verbatim; a matching
    entry does the shallow per-key override described above. Pure function, no I/O.
  - Unit tests in `presentationConfig.test.ts`: default-only resolution, colony-specific
    override of one key leaves other keys at default, unknown colony id falls back to
    default, `bharatkshetra`'s real override resolves to `["", "IV"]`.

## 3. Pinned constraints

- **No new status, no DB migration, no change to `transitions.ts` or any
  `apply_plot_transition`/`bulk_set_initial_plot_data` validation.** `PlotStatus` stays the
  3-value union. This is the line that keeps this plan Tier 2/3 instead of Tier 1 — do not
  cross it while implementing. If a step turns out to require touching
  `apps/map/src/lib/plot-status/**` or `apps/map/supabase/migrations/**`, stop and say so
  rather than proceeding.
- `presentation.json`'s `default` block values must exactly match today's hardcoded values
  at the moment of the first commit (listed verbatim in §2.1) — this is what makes adding
  the config file itself a behaviour-neutral commit, separable from any later commit that
  changes a value.
- `applyStatusColorOverrides` always writes all three status properties explicitly (never a
  conditional/partial set) — pinned in §2.4, restated here because a partial-set
  implementation is the one version of this feature that silently reintroduces a
  cross-colony colour leak, and it would pass every test that doesn't specifically check
  colony-switch-back.
- `formatStatusLabel`'s existing 1-argument call sites and `NO_OWNER_TOKENS`'s default
  behaviour must not change for any colony without a `presentation.json` override — every
  existing test in `format.test.ts` and `parseBulkImportFile.test.ts` passes with zero
  edits to their assertions (only new tests are added, per §2.1-2.6).
- `bharatkshetra`'s real override is `noOwnerTokens: ["", "IV"]` — this is the one concrete
  data point the user gave; use it verbatim in `presentation.json`, don't invent a
  placeholder.

## 4. Non-goals

- Arbitrary-count / new status names (e.g. "house built", "registry" as a 4th distinct
  status from "registered") — separate Tier-1 plan, not started here.
- An in-app UI for editing `presentation.json` — it is a checked-in file, edited by hand and
  deployed like any other source change, same as `tools/pipeline/colonies/<id>.json` today.
- Per-colony override of `homeHeading` — the user's ask was for one deployment-wide value
  (there is currently one org), so `homeHeading` lives only in `default`, not per colony.
  Revisit if a second org with its own branding is ever onboarded.
- Touching the dead `--colony-status-hold` CSS variable or DB CHECK value — out of scope,
  noted in §1, not removed either (removal is its own, unrelated cleanup).
- `LABEL_SIZE`, `LINE_WIDTH`, `DASH`, `LINE_ALPHA`, `TICK_HALF`, `TEXT_GAP` in
  `drawDimensions.ts` — only `offset` (spacing) and the text template were asked for.
- Any change to `PlotStatusActions.tsx`'s `ALL_STATUSES`/`PlotTableRow.tsx`'s
  `ALL_STATUSES`/`StatusLegend.tsx`'s `STATUSES` arrays — those enumerate which statuses
  exist, unchanged by this plan.

## 6. Failure modes

N/A — no state writes. Every change in this plan is either a pure function
(`resolvePresentationConfig`, `formatStatusLabel`, `drawPlotDimensions`'s text formatting),
a `style.setProperty` call on the DOM (not persisted, re-applied fresh on every mount/colony
switch per §2.4's pinned constraint), or JSX text. Nothing here writes to `plots`,
`plot_history`, `colonies`, or any other table — the plot-status write path
(`applyPlotTransition`) and its DB constraints are untouched, per §3.
