# Plan 22 — Multi-tenant SaaS conversion, phase 2 of 3: the public per-colony read-only link

**Tier 1.** Second of three planned phases (docs/plans/21.md's Non-goals). Phase 1
(`organizations`, org-scoped RLS, existing data → org #1) is complete and applied locally;
production application is still pending the owner's go-ahead (PROGRESS.md `## Current`).
This phase: an unauthenticated, per-colony, token-scoped read-only view — plot status only,
never buyer name/phone/money fields. **Not in this phase:** any admin UI to create/copy/
revoke the link (phase 3's admin-portal job) or richer public interactivity (pan/zoom,
click-for-detail) — see Non-goals.

## 1. Context already true

- **The exact shape was already scoped by the owner (PROGRESS.md, 2026-08-27 entry):**
  "Public links need a second, distinct mechanism: an unauthenticated role scoped by a
  random unguessable token, reading a restricted [surface] that never exposes PII
  columns — enforced in the database, not filtered at the app layer." Per plan 21's
  clarification session: the link is **per-colony**, not per-org.
- **The established RPC pattern already does the "enforced in the database" part.**
  `apply_plot_transition`, `bulk_set_initial_plot_data`, `create_colony_from_manifest` are
  all `security definer` functions that bypass RLS by design and do their own
  authorization check inside the function body (docs/plans/21.md, D-030). This phase adds
  a fourth RPC in the same family — the one deliberate difference is that this one checks
  a **token**, not `org_id`, since its whole purpose is to work for a caller who is not a
  member of any organization.
- **`colonies` schema today**
  (`20260812120000_m2_schema.sql` + `20260817000000_m15_colony_upload.sql` +
  `20260829000000_select_zoom_ref.sql` + `20260831000000_m16_organizations.sql`):
  `id text primary key, name, verified boolean, source_file, generated, created_at, svg
  text, select_zoom_ref_width_px numeric, select_zoom_ref_height_px numeric, org_id uuid
  not null`. `plots` carries the PII/money columns this phase must never expose:
  `owner_name, owner_phone, broker_name, rate_paise, booking_amount_paise, booking_date,
  registry_date, notes, updated_by`.
- **D-108 (no unverified colony is a deliverable) already has two enforcement points** —
  `fetchVerifiedColonies`'s `.eq("verified", true)` and `loadPlotStatuses`/`loadPlotDetail`'s
  own check. This phase's new RPC is the third: `verified = true` in its own `where`
  clause, non-negotiable, independent of the other two (this RPC bypasses RLS and neither
  existing check runs on this path).
- **A real plot's visible label (block/number) is already baked into the SVG text** at
  export time (`tools/pipeline/pipeline/export/svg.py`, NAVIGATION.md) — it is not read
  from the database at render time by any existing code path. This is why "status only" is
  a sufficient data contract for a usable map: block/number are already visible in the SVG
  geometry the RPC returns regardless; nothing further needs to be fetched for them.
- **No router exists in this app.** `App.tsx` is one component with a manual state gate
  (`session` → `LoginScreen` → `ColonyPicker`/`ColonyMap`); there is no react-router, no
  server-side route table, and `wrangler.toml`'s `[assets]` block has no
  `not_found_handling = "single-page-application"` entry — a path segment like
  `/public/<token>` would 404 on direct load against the real Cloudflare deployment today.
  Changing that is a deploy-config edit outside this plan's remit (CLAUDE.md blocks Claude
  from running the deploy command itself, and a routing change is exactly the kind of
  "affects the live site" edit to keep minimal). A **hash fragment** URL
  (`#/public/<token>`) needs no server or `wrangler.toml` change at all — a hash is never
  sent to the server, so `/` keeps serving the same `index.html` it always has, and
  `public/sw.js`'s asset caching is completely unaffected. This is the reason to choose it
  over a path segment, not a stylistic preference.
- **Reusable functions/types to extend, by exact path — do not create parallel ones:**
  `apps/map/src/lib/db/colonies.ts` (add the new RPC caller alongside
  `callCreateColonyFromManifest`, same file, same comment convention — "the only place
  `.rpc(...)` for this function appears"), `apps/map/src/lib/db/types.ts` (`ColonyRow`),
  `apps/map/src/components/map/renderColonyPreview.ts` (the still, non-interactive
  single-canvas renderer already used by the upload-confirmation screen — see task E),
  `apps/map/src/lib/auth/testHelpers.ts` (`serviceRoleClient`, `createScratchOrg`,
  `createScratchPlot` — reuse for the new RPC's live-integration tests; note
  `createScratchPlot` defaults `verified: false`, which this phase's tests must flip via a
  direct service-role update since the new RPC gates on it), `apps/map/scripts/
  create-user.ts` (the CLI-script style/`fail()` pattern to mirror for the new script).

## 2. The exact task

**A. New migration, `apps/map/supabase/migrations/<timestamp>_m17_public_colony_link.sql`:**

1. `alter table colonies add column public_token uuid unique;` — nullable: `null` means no
   active public link for that colony (the default, and the state every colony is in
   today). The `unique` constraint doubles as the index the new RPC's lookup needs — no
   separate `create index` statement.
2. New function `get_public_colony(p_token uuid) returns jsonb`, `security definer`,
   `set search_path = public, pg_temp`, **no `auth.uid()` check** — this is the one RPC in
   the app that must work for a caller with no session at all, by design. Body:
   - Look up the colony by `public_token = p_token and verified = true` (D-108, restated
     above — non-negotiable, independent of the RLS-based checks elsewhere).
   - Not found (wrong/revoked/regenerated token, or the colony isn't verified yet): return
     `jsonb_build_object('found', false)` — a return value, never a raised exception. This
     is the same "zero rows / zero result, not a permission error" idiom spec/08 criterion
     2 and this repo's other RPCs (`create_colony_from_manifest`'s `ok: false` shapes)
     already use, extended to a case that also covers "token genuinely doesn't exist" so a
     client can never distinguish "wrong token" from "right token, not verified yet" from
     response shape alone — that ambiguity is deliberate, not a gap (see Pinned
     constraints).
   - Found: return `jsonb_build_object('found', true, 'colony', jsonb_build_object('id',
     ..., 'name', ..., 'svg', ...), 'plots', <jsonb array of {svg_id, status} for every
     plot in that colony, coalesced to '[]' if none>)`. **Never select or return any other
     column** — no `owner_name`, `owner_phone`, `broker_name`, `rate_paise`,
     `booking_amount_paise`, `booking_date`, `registry_date`, `notes`, `updated_by`,
     `version`, `org_id`, `is_corner`, `facing`, `area_sqft`, `block`, `number`. Write the
     `select`/`jsonb_build_object` column list out explicitly — never `select *` or
     `to_jsonb(plots)` for this function, since either would silently start leaking a
     column the moment one is added to the table later, with no test able to catch it
     until a real PII leak already happened.
   - **Deliberately does not check `org_id` anywhere** — the one explicit, documented
     deviation from docs/plans/21.md's "every security-definer RPC must independently
     re-check org ownership" pinned constraint. State why in the function's `comment on
     function`: this RPC's whole purpose is to serve a caller who belongs to no
     organization at all; the token *is* the authorization boundary here, in the same role
     `org_id` plays for the other three RPCs. A future session must not "fix" this into an
     org check — that would make every public link unreachable.
3. Grants: Postgres grants `EXECUTE` to `PUBLIC` on a new function by default —
   `revoke execute on function get_public_colony(uuid) from public;` then `grant execute
   ... to anon, authenticated;` (mirrors the exact revoke/grant dance
   `20260815020000_m8_auth_rls_lockdown.sql` already established for
   `apply_plot_transition`). Grant to `authenticated` too, not anon-only — a signed-in org
   member previewing their own colony's public link before sharing it is a real, expected
   use even though it isn't built as a UI button until phase 3.
4. **No RLS policy changes** on `colonies`/`plots`/`organizations` — this function bypasses
   RLS by design (`security definer`), same as the other three RPCs; the tables' existing
   authenticated-and-own-org-only policies are untouched and must stay that way (an anon
   `select` against `colonies`/`plots` directly must still return zero rows — the *only*
   way anon reads anything is through this one function with a valid token).

**B. `apps/map/src/lib/db/types.ts`:** add `public_token: string | null` to `ColonyRow`
only (not `ColonyInsert` — no insert path ever sets it; it starts `null` and is set later,
service-role-only, task C). Add `PublicColonyResult = { found: false } | { found: true;
colony: { id: string; name: string; svg: string }; plots: { svg_id: string; status:
PlotStatus }[] }`.

**C. `apps/map/src/lib/db/colonies.ts`:** `fetchPublicColony(client, token): Promise<
PublicColonyResult>` — the only place `.rpc("get_public_colony", { p_token: token })`

`callCreateColonyFromManifest`.

**D. `apps/map/src/lib/colony/publicColony.ts`** (new, Domain layer — DOM-free, mirrors
`listColonies.ts`/`plotStatus.ts`'s split): `loadPublicColony(client, token)` thin wrapper
around `fetchPublicColony`. **`apps/map/src/lib/colony/publicLinkUrl.ts`** (new, pure, no
`client` dependency — unit-testable without a browser): `parsePublicToken(hash: string):
string | null`, matching `#/public/<uuid>` and returning the uuid or `null` for anything
else (including the app's normal `""`/`"#"` hash on every other load).

**E. `apps/map/src/components/map/renderColonyPreview.ts`:** add an optional third
parameter, `statuses?: Record<string, string>`, defaulting to today's exact behaviour
(every plot forced to `"available"`) when omitted — **the upload-confirmation call site
(`ColonyUploadScreen.tsx`) must not change its call, and its rendered output must be
byte-identical to before** (invariant 2/D-025: this function is the one place that renders
what the upload gate's human confirmation is judging, and that gate's behaviour is not
this plan's to touch). When a real `statuses` map is supplied, thread it into `drawColony`'s
draw-state `statuses` field instead of the synthesized all-available one. This is the one
piece of UI code the public view and the upload preview genuinely share: both are a single
still, non-interactive canvas render of a colony from raw SVG + a status map, with no
Leaflet, no gestures, no sync — reusing it (rather than hand-rolling a second copy of the
DPR-aware canvas-sizing/grass-texture-loading scaffolding) is the correct call as long as
the existing call site's behavior is provably unchanged.

**F. `apps/map/src/features/public-colony/PublicColonyView.tsx`** (new): given `client`
and `token`, calls `loadPublicColony` once on mount; renders one of three states —
loading, "This link is invalid or has been revoked" (covers `found: false`, wrong token,
revoked token, and not-yet-verified colony indistinguishably, matching task A2's
deliberate ambiguity), or the colony name plus `renderColonyPreview`'s static render fed
the real `{svg_id: status}` map from the RPC response. No search, no table view, no share
summary, no plot-detail sheet, no click-to-select, no legend filter — see Non-goals.

**G. `apps/map/src/App.tsx`:** near the top, after the existing `if (!client)` early
return, add: parse `window.location.hash` via `parsePublicToken`; if it resolves to a
token, return `<PublicColonyView client={client} token={token} />` immediately — before
the `session` check, `LoginScreen`, and every other authenticated-path branch. A visitor
with a public link never needs a session, and a signed-in owner opening their own public
link to check it should see the same public view everyone else sees, not their normal
authenticated map.

**H. `apps/map/scripts/generate-public-link.ts`** (new, mirrors `create-user.ts`'s
structure/`fail()` pattern exactly): `pnpm generate-public-link <colony_id>` — service-role
client, generates a new random token (`crypto.randomUUID()`, Node's built-in, no new
dependency), `update colonies set public_token = <token> where id = <colony_id>`, prints
the resulting shareable URL (`<app origin>/#/public/<token>` — the script does not know the
real deployed origin, so print the token and the hash fragment, with a one-line comment
telling the operator to prepend their own domain). Fails loudly (existing `fail()` shape) if
the colony id doesn't exist, mirroring `create-user.ts`'s posture on a missing argument.
This is this phase's entire "admin surface" — the same "a CLI arg and hand-run SQL, nothing
more" posture plan 21 established for phase 1, deliberately not a portal UI (phase 3's job).
Revocation in this phase is a **hand-run SQL** `update colonies set public_token = null
where id = '<id>';` — not a second script — matching plan 21's own precedent of leaving a
genuinely rare admin action as raw SQL rather than tooling it prematurely.

**I. `apps/map/package.json`:** add `"generate-public-link": "tsx scripts/
generate-public-link.ts"` next to the existing `"create-user"` entry.

**J. Tests (live-integration, real local Docker Supabase, no mocks — this repo's existing
convention throughout `lib/auth/*.test.ts` and `lib/colony/*.test.ts`):**

- A cross-org proof, alongside the phase-1 pattern in `rls-cross-org.test.ts` or a new

## 3. Pinned constraints

- **The token is the entire authorization boundary for this RPC — no `org_id` check, ever,
  by design.** This is a one-line, easy-to-get-wrong deviation from docs/plans/21.md's
  otherwise-universal "every security-definer RPC re-checks org ownership" rule; the
  function's own SQL comment must state why, so a later session doesn't "fix" it into
  breaking every public link.
- **The RPC's column list is explicit and hand-written, never `select *`/`to_jsonb(row)`.**
  A wildcard here is a silent future PII leak the moment any column is added to `plots` or
  `colonies` — this is the actual security property "restricted view" was describing in
  the 2026-08-27 exploration notes, now enforced as an explicit column list instead of a
  separate Postgres view object (a function achieves the identical guarantee here and
  matches this repo's existing RPC-not-view idiom for every other write/read boundary).
- **`verified = true` is checked inside this RPC independently** — it does not rely on
  `fetchVerifiedColonies`'s or `loadPlotStatuses`'s existing checks, neither of which this
  code path calls.
- **Found vs. not-found is the only signal returned — never a distinct "wrong token" vs.
  "right token, not verified yet" vs. "revoked" response.** Deliberate: a distinguishable
  response would let a caller confirm a *guessed* uuid belongs to a real, existing colony
  (a real information leak, however minor) even without ever seeing its data.
- **Hash-fragment routing (`#/public/<token>`), not a path segment**, and no
  `wrangler.toml`/Cloudflare/service-worker change of any kind. If a path-based scheme is
  ever wanted later, that is a distinct, explicit deploy-config change requiring its own
  sign-off — not something to fold into this plan.
- **`renderColonyPreview`'s existing call site (`ColonyUploadScreen.tsx`) must render
  byte-identical output to before** — the new `statuses` parameter is additive and
  optional, defaulting to the exact current all-"available" behaviour. This is the
  acceptance-critical regression check for task E, not a formality (invariant 2/D-025).
- **No PII/money column name may appear anywhere in `get_public_colony`'s SQL body, in
  `PublicColonyResult`'s TypeScript shape, or in `PublicColonyView.tsx`'s rendered output.**
  Grep for `owner_name`, `owner_phone`, `broker_name`, `_paise`, `booking_date`,
  `registry_date`, `notes` across every new file this plan adds as part of `/review`.
- **This migration's new column/function must be applied to production separately**, same
  posture plan 21 already established and PROGRESS.md's `## Current` already tracks for
  phase 1 — not bundled silently into "done" here.

## 4. Non-goals

- Any admin UI to generate, copy, display, or revoke a public link (phase 3's admin-portal
  tool). This phase's only "admin" surface is `generate-public-link.ts` plus hand-run SQL
  for revocation, same posture as phase 1's own admin surface.
- Pan/zoom, click-to-select, plot-detail sheet, search, table view, share summary, or the
  live realtime subscription on the public view. Realtime is structurally out anyway this
  phase: Supabase Realtime's `postgres_changes` still requires RLS to permit the row to an
  `anon` subscriber, and `plots`' RLS stays authenticated-and-org-scoped-only (task A4) —
  wiring `attachSync`/`subscribePlotChanges` against this path would silently deliver zero
  events, not a visible error. A public visitor gets a snapshot as of page load; refresh to
  see new statuses. If the owner wants live updates on the public view later, that needs
  its own RLS/mechanism design, not a wiring change against the existing subscription path.
- Rate-limiting or abuse protection on `get_public_colony` (e.g. against token
  brute-forcing). A uuid token has 122 bits of entropy — brute-forcing it is not a
  realistic threat at this app's scale, and Supabase's own platform-level rate limiting
  already applies to every PostgREST/RPC call regardless. Not designed further here.
- Per-org (rather than per-colony) public links — confirmed cut in plan 21's clarification
  session, not revisited.
- Multi-org membership, org-switcher UI, org creation/renaming UI — unchanged Non-goals
  carried over from plan 21.
- `contract/` and `tools/pipeline` — untouched. This phase is pure `apps/map`
  schema/RPC/script/UI work.

## 6. Failure modes

Walking `spec/00-rules.md`'s five, since this plan writes state (a new nullable column, a
new function, a script that performs a real update):

- **Partial writes.** The migration file's schema/function/grant statements apply in one
  Supabase transaction, same as every other migration here — nothing in this phase's
  migration is split across files. `generate-public-link.ts`'s single `update ... where id
  = ...` is one statement — no multi-step write to leave half-done.
- **Idempotency.** `generate-public-link.ts` is not idempotent by design — running it twice
  on the same colony *should* produce two different tokens (that is exactly "regenerate,
  invalidating the old one"), not a no-op. This is the opposite expectation from most of
  this repo's scripts and worth stating explicitly so a test doesn't wrongly assert
  same-token-twice. The migration itself is the normal one-time-forward-only case.
- **Concurrency.** `get_public_colony` is read-only — no lock, no write, no race to reason
  about beyond Postgres's normal MVCC snapshot read. `generate-public-link.ts`'s update is
  a single-row `update`, not a read-then-write — no lost-update race is possible even under
  concurrent regeneration (the last `update` simply wins, which matches "the latest
  generated link is the valid one" being the only sensible semantics here).
- **Orphans.** `public_token uuid unique` with no `not null` means a colony with no public
  link is simply `null` — never an orphaned placeholder row. No new table is created that
  could hold rows nothing references.
- **Dead computation.** N/A beyond the normal bar — every new column, function, and script
  in this plan is exercised by the new tests in task J or the manual run in acceptance;
  nothing is added speculatively for a later phase.
