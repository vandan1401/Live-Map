# Plan 29 — Colony backdrop: image + alignment uploadable, not a code change

PROGRESS.md "## Backlog — owner-requested, not started", item 6 (raised 2026-09-09).

## 1. Context already true

- **What exists today (docs/plans/28.md, D-036):** a per-colony synthetic-aerial backdrop.
  The raster is a **Vite static import** — `apps/map/src/components/map/mapBackdrops.ts`'s
  `BACKDROPS: Record<string, string>` has exactly one entry,
  `bharatkshetra: bharatkshetraBackdropUrl` (imported from
  `apps/map/src/assets/backdrops/bharatkshetra.jpg`, 535KB). Its alignment/metadata is a
  **checked-in JSON file**, `apps/map/src/config/mapBackdrop.json`, keyed by colony id, each
  entry shaped as `MapBackdropData` (`transform: {x,y,scale,rotateDeg}`, `imageWidth`,
  `imageHeight`, `darkenAlpha`, `enabledOnAdmin`, `enabledOnPublic`, `attribution`, `labels`).
  `resolveMapBackdrop(colonyId, surface)` joins the two Records and gates on the per-surface
  enabled flag. Adding a colony's backdrop or nudging its alignment today means editing both
  files and redeploying — this plan's whole reason to exist.
- **Where it's consumed:** `useMapBackdrop.ts`'s `resolveBackdropFit(colonyId, surface, model)`
  (calls `resolveMapBackdrop` internally) is called **synchronously**, inside the mount
  effect, **before** `L.map()` is constructed — both `useColonyCanvas.ts:128` (admin) and
  `usePublicColonyCanvas.ts:98` (public) need `bounds`/`minZoom` from it as constructor args.
  `attachMapBackdrop()` then does the async image fetch (`loadMapBackdropImage`, resolves
  `null` on failure — never blocks or crashes the mount). This existing sync/async split is
  **load-bearing and must be preserved**: the metadata lookup stays synchronous, only the
  raster fetch is async, exactly as today.
- **Both hooks are already near invariant 7's 250-line cap**: `useColonyCanvas.ts` is 239
  lines, `usePublicColonyCanvas.ts` is 231 — both call out in their own comments (see
  `useMapBackdrop.ts`'s header) that backdrop logic was centralized there specifically to
  protect this cap. This plan must not add meaningful lines to either hook file — see
  Pinned Constraints for the exact shape that keeps the diff to one changed line per call
  site.
- **The admin portal (`apps/map/admin-portal/`, D-032, docs/plans/23.md phase 3)** is this
  repo's existing, precedented place for owner-privileged, occasional, non-realtime actions
  on colony/org data — local-only Node `http` server, service-role key is the real gate, no
  login layer, JSON-content-type CSRF check on every mutating route
  (`requireJsonContentType`), guard-hook-blocked from Claude same as `make serve`/`make ui`.
  It already has a per-colony-row actions column (Generate/Revoke public link) in its
  `colony-table`. This plan reuses that shape rather than touching the main app's Tier-1
  colony-upload screen — a backdrop is decorative map dressing, not plot/manifest data
  subject to the human-verification gate (D-025/D-108), so there is no reason to reopen that
  screen's logic.
- **`lib/colony/publicColony.ts`** (`regeneratePublicLink`/`revokePublicLink`) is the exact
  precedent to mirror: a plain domain function taking a service-role `SupabaseClient`, doing
  `client.from("colonies").update(...)`, called from `admin-portal/server.ts`. No RLS policy
  change was needed for those because service-role bypasses RLS entirely — the same is true
  here.
- **`get_public_colony()`** (D-031, latest version `20260901010000_m20_public_link_zoom_ref.sql`)
  is the one hand-written-column-list RPC the public surface reads through — "never
  `select *`" is a hard rule enforced by its own comment and `publicColony.test.ts`'s
  forbidden-column-name test. Adding new non-PII columns to its two explicit column lists
  (the `colonies` select and the returned `jsonb_build_object`) is exactly what M19/M20 each
  already did once.
- **Known, pre-existing, explicitly owner-deferred limitation this plan does NOT fix:**
  `colonies.id` is a global `text primary key`, not org-scoped (PROGRESS.md Deferred,
  2026-09-01 entry) — two orgs cannot have a colony sharing an id today, full stop, for
  every table that references `colonies(id)`. This plan's storage object path
  (`<colony_id>.jpg`) inherits that exact same pre-existing global-uniqueness assumption.
  Not a new risk introduced here — do not attempt to fix it as part of this plan.
- **No Storage bucket exists in this project yet** — this is the first real use of a
  Supabase Storage path anywhere in this repo (confirmed: no `[storage]` block in
  `supabase/config.toml`, no `storage.buckets` insert in any existing migration).

## 2. The exact task

Replace the static-import + checked-in-JSON backdrop mechanism with a Supabase-Storage
raster plus `colonies`-table alignment metadata, both writable only via two new admin-portal
actions (upload the image; edit the alignment numbers) — no redeploy required for either.

**A. Migration 1 — `apps/map/supabase/migrations/20260912000000_colony_backdrop_storage.sql`**

```sql
insert into storage.buckets (id, name, public)
  values ('colony-backdrops', 'colony-backdrops', true)
  on conflict (id) do nothing;

alter table colonies
  add column backdrop_storage_path text,
  add column backdrop_image_width integer,
  add column backdrop_image_height integer,
  add column backdrop_transform_x double precision not null default 0,
  add column backdrop_transform_y double precision not null default 0,
  add column backdrop_transform_scale double precision not null default 1,
  add column backdrop_transform_rotate_deg double precision not null default 0,
  add column backdrop_darken_alpha double precision not null default 0,
  add column backdrop_enabled_on_admin boolean not null default false,
  add column backdrop_enabled_on_public boolean not null default false,
  add column backdrop_attribution text not null default '';
```

Pin: `backdrop_storage_path`/`backdrop_image_width`/`backdrop_image_height` stay **nullable**
(null = no image uploaded yet, the universal "no backdrop" state for every colony today).
Every other column gets a real default so a first image upload (which only ever touches the
three image columns, see task C) lands on a fully-valid, disabled-by-default row with no
null-handling needed downstream. No new RLS policy: `colonies` already has org-scoped,
select-only, authenticated RLS (D-030) that covers these columns for free; writes go through
the admin-portal's service-role client exactly like `public_token` already does (M17's own
comment: "Never a client-writable column" — same posture, extended to these 11). The Storage
bucket is `public: true` (anon reads need zero RLS — Supabase serves a public bucket's
objects via its own CDN-style endpoint, bypassing RLS entirely for `GET`); writes go through
the same service-role client, which bypasses Storage RLS too — **do not add any
`storage.objects` policy rows**, they would be dead code.

**C. `apps/map/src/lib/colony/colonyBackdrop.ts` (new, mirrors `publicColony.ts`'s shape)**

```ts
export async function uploadColonyBackdropImage(
  client: SupabaseClient,
  colonyId: string,
  args: { bytes: Uint8Array; imageWidth: number; imageHeight: number },
): Promise<void>
```
Uploads `args.bytes` to the `colony-backdrops` bucket at path `${colonyId}.jpg`
(`upsert: true` — a re-upload replaces in place, same object path, so `getPublicUrl`'s
result for a given colony never changes and nothing downstream needs to know a re-upload
happened). Content-type fixed to `image/jpeg` (see task D — non-JPEG is rejected before this
function is ever called). Then `.from("colonies").update({ backdrop_storage_path: \`${colonyId}.jpg\`, backdrop_image_width: args.imageWidth, backdrop_image_height: args.imageHeight }).eq("id", colonyId)`
— **only these three columns**, exactly so a re-upload never resets a previously-tuned
alignment (transform/darkenAlpha/enabled flags are untouched by this function, full stop).

```ts
export async function updateColonyBackdropTransform(
  client: SupabaseClient,
  colonyId: string,
  args: {
    x: number; y: number; scale: number; rotateDeg: number; darkenAlpha: number;
    enabledOnAdmin: boolean; enabledOnPublic: boolean;
  },
): Promise<void>
```
Plain `.from("colonies").update({ backdrop_transform_x: args.x, ... }).eq("id", colonyId)` —
one `.update()` call, all 7 fields always sent together (the admin-portal form always submits
the whole set — see task E — so there is no partial-update case to handle here).

**D. `apps/map/admin-portal/server.ts` + `actions.ts` — two new routes**

- `POST /api/colonies/:colonyId/backdrop-image` — body `{ imageBase64: string, imageWidth:
  number, imageHeight: number }`. Decode base64 to a `Buffer`; reject (400) unless the first
  3 bytes are `FF D8 FF` (the JPEG magic number — this project only ever ships JPEG
  backdrops, see `bake_static.html`/`stitch.html`'s own output convention, and rejecting
  early here is cheaper than a confusing Storage-side content-type mismatch later); reject
  (400) if the decoded buffer exceeds `MAX_BACKDROP_UPLOAD_BYTES = 15_000_000` (a named
  constant — 15MB is >25x the real shipped `bharatkshetra.jpg` (535KB), generous headroom
  for a bigger colony's aerial photo, small enough that a wrong-file mistake fails fast
  instead of hanging the local process). Calls `uploadColonyBackdropImage`.
- `PATCH /api/colonies/:colonyId/backdrop` — body `{ x, y, scale, rotateDeg, darkenAlpha,
  enabledOnAdmin, enabledOnPublic }`, all required. Calls `updateColonyBackdropTransform`.

Both follow this file's existing idiom exactly: `requireJsonContentType` already runs for
every non-GET route before dispatch (no new CSRF work needed); a thrown `Error` from the
action function reaches `sendError(res, 500, ...)` via the existing top-level `catch`.

New exported function, replacing `resolveMapBackdrop`:

```ts
export interface ColonyBackdropFields {
  id: string;
  backdrop_storage_path: string | null;
  backdrop_image_width: number | null;
  backdrop_image_height: number | null;
  backdrop_transform_x: number;
  backdrop_transform_y: number;
  backdrop_transform_scale: number;
  backdrop_transform_rotate_deg: number;
  backdrop_darken_alpha: number;
  backdrop_enabled_on_admin: boolean;
  backdrop_enabled_on_public: boolean;
  backdrop_attribution: string;
}

export function resolveMapBackdropFromRow(
  client: SupabaseClient,
  row: ColonyBackdropFields | null,
  surface: MapBackdropSurface,
): MapBackdrop | null
```

`null` row, `null`/`null` image width/height, or the per-surface flag being false all return
`null` (same three null-cases the old `resolveMapBackdrop` handled). Otherwise builds the
image URL via `client.storage.from("colony-backdrops").getPublicUrl(row.backdrop_storage_path).data.publicUrl`
(a pure string build, no network call — safe to call from the anon public client too) and
looks up `labels` from the shrunk JSON by `row.id`, defaulting to `[]` if absent.

## 3. Pinned constraints

- **Object path is `${colonyId}.jpg`, JPEG only, one object per colony, `upsert: true`.**
  Do not add extension/format flexibility — the owner's own offline stitching tool only ever
  outputs JPEG today, and multi-format support is unrequested scope.
- **`uploadColonyBackdropImage` never touches transform/darkenAlpha/enabled columns.** A
  re-upload must not silently reset a previously-tuned alignment — this is the single most
  important behavioral pin in this plan; a `/review` should specifically check the SQL
  `update` statement's column list in that function.
- **The metadata lookup (`resolveMapBackdropFromRow`) must stay fully synchronous** — no
  `await`, no Promise, callable inline inside the mount effect exactly like today's
  `resolveMapBackdrop`. Only the raster fetch (`attachMapBackdrop`'s existing
  `loadMapBackdropImage` call) is async, unchanged from today.
- **`get_public_colony()` gains 10 columns, never `backdrop_enabled_on_admin`.** Withhold-by-
  omission is this RPC's whole security model (see its own comment) — an admin-only flag
  reaching an anonymous caller is a real, if low-severity, information leak about the
  colony's owner-side configuration.
- **No Storage RLS policy is added.** Bucket `public: true` covers anon reads; the
  service-role admin-portal client bypasses Storage RLS for writes, same as it already
  bypasses `colonies`' RLS for `public_token` writes today. Adding a policy here would be
  dead code that the next reader has to figure out is dead.
- **`MAX_BACKDROP_UPLOAD_BYTES = 15_000_000`** (named constant, comment cites the real
  535KB shipped file as the calibration baseline) — reject oversized uploads in
  `server.ts` before ever calling Storage.
- **No automatic data migration for `bharatkshetra`'s existing backdrop.** Deleting the old
  static-import/JSON path means production temporarily has **no backdrop on either surface**
  for `bharatkshetra` from the moment this ships until the owner manually re-uploads the
  image and re-enters its known-good transform (`x: 864, y: 283, scale: 0.1050, rotateDeg: 0,
  darkenAlpha: 0.65, enabledOnAdmin: true, enabledOnPublic: true` — copy these exact values
  from today's `mapBackdrop.json`, they are already correct) through the new admin-portal UI.
  This is a real, known, temporary regression window — call it out explicitly in `/wrap`'s
  Next section, do not let it pass silently.
- **Migration application order matters, same as every prior phase**: local Docker first
  (`supabase db reset` or a plain `supabase migration up`), full verification, only then the
  owner applies both migrations to the real production project via the Dashboard SQL Editor
  in file order, followed by `NOTIFY pgrst, 'reload schema';` after the second one (D-033) —
  Claude does not touch production directly (CLAUDE.md's own boundary).

## 6. Failure modes

Walking `spec/00-rules.md`'s apps/map checklist — this task writes state (new `colonies`
columns, new Storage objects):

1. **Partial writes** — `uploadColonyBackdropImage` does a Storage upload *then* a table
   update; these are two separate calls, not one transaction (Postgres can't transact
   against the Storage API). If the table update fails after a successful Storage upload,
   the object exists but no row points at it — harmless (an orphaned object next to a bucket
   nobody lists by directory), not a correctness bug, and `upsert: true` means a retry
   overwrites the same object cleanly. If the Storage upload fails, the function must throw
   before ever calling `.update()` — verify this ordering explicitly in `/review`.
2. **Idempotency** — a double-click of "Upload" re-runs the same upload+update with the same
   object path and the same field values; `upsert: true` makes the Storage side idempotent,
   and the table `.update()` is naturally idempotent (same values in, same values out). A
   double-click of "Save alignment" is likewise idempotent — plain field overwrite, no
   counter, no history row.
3. **Concurrency** — two people editing the same colony's backdrop alignment via two admin-
   portal tabs at once is a real but low-stakes race (last write wins, no `version` column,
   no money/status at risk) — explicitly not worth `apply_plot_transition()`'s optimistic-
   concurrency machinery for a decorative, single-owner-tool field. Not a gap to fix here.
4. **Orphans** — a `colonies` row with `backdrop_storage_path` set but the Storage object
   deleted out-of-band (never happens through this plan's own UI, no delete action exists)
   would resolve to a broken image URL; `attachMapBackdrop`'s existing `imageFailed` handling
   (image `onerror` → `resolve(null)`) already covers exactly this case today for a network
   failure and needs no new code to also cover it here.
5. **Dead computation** — none; `backdrop_image_width`/`height` are recorded once at upload
   time (from the browser's own `Image.decode()`), never recomputed, same shape as `facing`/
   `is_corner` being computed once at pipeline export and stored.
