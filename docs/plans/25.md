# Plan 25 — Public colony link: show plot dimensions on click

**Tier 1** (`apps/map/supabase/migrations/**` and `apps/map/src/features/colony-upload/**`-
adjacent rendering code are both Tier 1 per CLAUDE.md's risk table; `get_public_colony` is a
security-relevant, anon-facing RPC). Narrow follow-on to docs/plans/22.md phase 2 (D-031),
already shipped and applied to production. Owner's ask, verbatim: "in the public link it
should atleast show the size of plot the dimension of all the sides when clicked it is not
showing currently."

## 1. Context already true

- **`PublicColonyView.tsx` is deliberately static today** — docs/plans/22.md task F: "No
  search, no table view, no share summary, no plot-detail sheet, no click-to-select." This
  plan is the one, explicit, narrow reversal of that specific Non-goal (click-to-see-
  dimensions only) — everything else that list named (search, table view, share summary,
  pan/zoom, the live realtime subscription) stays out of scope, unchanged.
- **`get_public_colony(p_token uuid)`** (`20260831010000_m17_public_colony_link.sql`, D-031)
  returns `{found, colony: {id, name, svg}, plots: [{svg_id, status}]}` via an explicit,
  hand-written `jsonb_build_object` column list — never `select *`. D-031's own reasoning
  already establishes the exact class of fact safe to add here: "block/number are already
  visible in the SVG's own baked-in plot-label text... so withholding them here loses
  nothing a public visitor couldn't already see." `area_sqft`/`length_ft`/`breadth_ft` are
  the same class of fact — pure geometry, never listed among the withheld PII/money columns
  (`owner_name`, `owner_phone`, `broker_name`, `rate_paise`, `booking_amount_paise`,
  `booking_date`, `registry_date`, `notes`, `updated_by`). This plan adds exactly these five
  fields (`block`, `number`, `area_sqft`, `length_ft`, `breadth_ft`) to the per-plot object,
  nothing else — the column list stays explicit and hand-written, same discipline.
- **The authenticated app already displays exactly this data, in this exact wording** —
  `apps/map/src/features/plot-detail/PlotDetailContent.tsx`: `<dt>Length</dt><dd>{plot.
  length_ft} ft</dd>`, `<dt>Breadth</dt><dd>{plot.breadth_ft} ft</dd>`, `<dt>Area</dt><dd>
  {plot.area_sqft} sq ft</dd>`, with `formatPlotLabel(plot)` (`shared/format.ts` — `{block}-
  {number}`, or just `{number}` when `block` is `""`) as the heading. Reuse this wording
  verbatim for the public panel — no new copy to invent, no drift from what a signed-in
  family member already sees for the same fact.
- **Hit-testing already exists and is reusable, by exact path:**
  `apps/map/src/components/map/plotPicker.ts`'s `pickPlotAt(model, x, y)` — SVG-user-space
  coordinates in, the `PlotShape` under that point out (or `null`). `apps/map/src/
  components/map/view.ts`'s `screenToWorld(view, viewport, px, py)` converts a canvas-
  relative pixel coordinate into that same SVG-user-space, given a `ViewState`
  (`{scale, cx, cy}`) and `Viewport` (`{width, height}`). Both are pure, DOM-free, already
  unit-tested independently — do not reimplement either.
- **`renderColonyPreview(container, svg, statuses?)`** (`components/map/
  renderColonyPreview.ts`) is the one function that draws this static preview — shared with
  `ColonyUploadScreen.tsx`'s upload-confirmation render (invariant 2/D-025: that confirmation
  is the only code path writing `verified: true`, so it must show what the map will show).
  Its `paint()` closure computes `viewport = {width, height}` and `view = fitView(model,
  viewport)` **before** the `ctx` null-check (jsdom has no canvas backend — `ctx` is `null`
  under test, but `viewport`/`view`/`model` are still computed) — this is why a click
  listener attached inside this function can be exercised in a jsdom test without a real
  canvas backend, same as the existing upload-screen tests already tolerate `ctx === null`.
  **The upload-confirmation call site must see zero behavior change** — it calls
  `renderColonyPreview(container, stage.svg)`, two args, and this plan's new parameter must
  default to "no click handling at all" when omitted, not just "a no-op handler."

## 2. The exact task

**A. New migration, `apps/map/supabase/migrations/<timestamp>_m19_public_link_dimensions.sql`:**
`create or replace function get_public_colony(p_token uuid)` — same signature, unchanged
grants (a return-shape change needs no new `revoke`/`grant`). The per-plot
`jsonb_build_object` in the `select coalesce(jsonb_agg(...), '[]'::jsonb) from plots ...`
query gains `'block', block, 'number', number, 'area_sqft', area_sqft, 'length_ft',
length_ft, 'breadth_ft', breadth_ft` alongside the existing `'svg_id', svg_id, 'status',
status`. Update the `comment on function` to name the new fields explicitly (mirroring how
it already names what's withheld). No other statement in this migration.

**B. `apps/map/src/lib/db/types.ts`:** `PublicColonyResult`'s `plots` array item type gains
`block: string; number: string; area_sqft: number; length_ft: number; breadth_ft: number` —
same field types `PlotRow`/`PlotInsert` already use for these columns, not re-derived.

**C. `apps/map/src/components/map/plotPicker.ts` or a new small file:** extract the
coordinate-resolution glue this plan needs as a **pure, directly unit-testable** function —
e.g. `resolveClickedPlot(model: ColonyModel, view: ViewState, viewport: Viewport, px: number,
py: number): PlotShape | null`, composed of `screenToWorld` then `pickPlotAt`, nothing else.
This is the "cheap to test, most damaging to get wrong" pure layer — write its test first,
before wiring any DOM click listener to it.

**D. `apps/map/src/components/map/renderColonyPreview.ts`:** add an optional 4th parameter,
`onPlotClick?: (plot: PlotShape) => void`. When provided, attach one `"click"` listener to
`canvas` (added once, not per-repaint) that reads the **latest** `view`/`viewport` computed
by the most recent `paint()` call (captured in a closure variable `paint()` updates each
time it runs — the canvas can, in principle, be resized/repainted more than once, and a
stale `view` would silently mispick), converts the click's canvas-relative pixel coordinate
via `resolveClickedPlot` (task C), and calls `onPlotClick(plot)` if a plot was hit — does
nothing if the click missed every plot (task E's caller decides what "nothing" means, e.g.
dismissing an open panel). When `onPlotClick` is omitted, **no listener is attached at
all** — `ColonyUploadScreen.tsx`'s call site (`renderColonyPreview(container, stage.svg)`,
unchanged) must be provably identical in behavior to before this plan, not just "the
listener is attached but never fires."

**E. `apps/map/src/features/public-colony/PublicColonyView.tsx`:** add local state for the
currently-selected plot's dimension fields (or `null`). Pass `onPlotClick` to
`renderColonyPreview` (task D) — on a hit, resolve the clicked plot's `svg_id` against
`result.plots` (already carries the new fields per task B/A) and set that plot's `block`/
`number`/`area_sqft`/`length_ft`/`breadth_ft` into state; on a miss (`onPlotClick` never
fires, since task D only calls it on a hit — so "tapped elsewhere" needs its own signal, see
Pinned constraints) clear the selection. Render a small, dismissible panel — reusing
`formatPlotLabel`'s exact heading shape and the exact `<dt>Length</dt><dd>{…} ft</dd>` /
`<dt>Breadth</dt>` / `<dt>Area</dt><dd>{…} sq ft</dd>` structure `PlotDetailContent.tsx`
already uses, for a visitor who has never seen the authenticated app to get the identical
wording a family member would. **No owner name, no status-change actions, nothing else from
the authenticated `PlotDetailContent`/`PlotDetailSheet` flow** — this panel shows dimensions
only, matching the plan's own scope.

**F. `apps/map/src/styles/public-colony.css`:** styling for the new dismissible panel,
following this file's existing conventions (already has `.public-colony-overlay`/
`.public-colony-message` etc. from docs/plans/22.md).

**G. Tests:**
- `resolveClickedPlot` (task C): pure unit tests — a click inside a known plot's polygon
  resolves to it; a click outside every plot resolves to `null`; a click inside plot A's
  bbox but outside its actual ring (a concave/non-rectangular case, if the shared fixture
  has one, else a synthetic model) still resolves correctly, proving this isn't just a bbox
  check.
- `get_public_colony` (`apps/map/src/lib/colony/publicColony.test.ts`, extending the
  existing live-integration suite): the "returns colony + plot statuses... with no PII/
  money column anywhere" test's assertion now also checks the new fields are present with
  the expected values, **and** the existing forbidden-column-name loop (`owner_name`,
  `owner_phone`, `broker_name`, `rate_paise`, `booking_amount_paise`, `booking_date`,
  `registry_date`, `notes`, `updated_by`, `org_id`, `version`) still passes unchanged — this
  is the acceptance-critical proof that adding five fields didn't loosen the column list
  discipline.
- `PublicColonyView.tsx`: a component test proving that, given a `renderColonyPreview`
  click resolving to a known plot, the panel renders that plot's `formatPlotLabel` heading
  and the three dimension fields in the established wording; and that no panel renders
  before any click. If simulating a real coordinate-accurate click through the full canvas
  pipeline proves impractical under jsdom's zero-layout `getBoundingClientRect` (the same
  constraint `renderColonyPreview.ts`'s own header comment already notes for pixel
  assertions), it is acceptable to test this component's reaction to the `onPlotClick`
  callback directly rather than through a synthetic pixel-perfect click — but the
  **coordinate math itself** (task C) must still be covered by real unit tests, not skipped
  entirely.
- **Not achievable from Claude, flag explicitly rather than claim done:** the actual
  click-to-see-dimensions UX, on a real device, through a real browser, against a real
  deployed public link — this repo's own established pattern (every prior canvas/visual
  session in PROGRESS.md) is that Claude has no way to judge this and it needs the owner's
  own pass once deployed.

## 3. Pinned constraints

- **The RPC's column list stays explicit and hand-written.** Never `select *`/
  `to_jsonb(plots)` for `get_public_colony`, even after this addition — grep for every
  PII/money column name (task G's list) across the new migration file as part of `/review`.
- **`renderColonyPreview`'s upload-confirmation call site must be provably unaffected.**
  `ColonyUploadScreen.tsx`'s call (`renderColonyPreview(container, stage.svg)`, two args)
  stays exactly as-is; the new 4th parameter is optional and, when omitted, attaches no
  listener at all — this is invariant 2/D-025's regression check, same posture docs/
  plans/22.md's own task E already established for the `statuses` parameter before this one.
- **"Tapped elsewhere clears the selection" needs an explicit signal, not an assumption.**
  Task D's `onPlotClick` only fires on a hit (matching its name) — task E's build must
  decide how a miss is communicated (e.g. `onPlotClick` becomes `(plot: PlotShape | null) =>
  void` and is called on every click, hit or miss; or a second optional callback). Pin
  whichever shape is chosen in the code's own comment, since this is exactly the kind of
  small interface decision a later session could silently get backwards.
- **No selection highlight is drawn on the canvas itself.** `drawColony`'s `selectedId`
  stays `null` for this preview (matching the render this plan starts from) — only the
  floating panel changes. Redrawing with a live selection state would mean turning this
  "paint once" function into a live re-render loop, a much bigger change than this plan's
  scope; not undertaken here.
- **No new grants, no RLS change.** This migration is a pure return-shape change to an
  existing `security definer` function — `get_public_colony`'s `revoke`/`grant execute on
  ... to anon, authenticated` from M17 is untouched and correct as-is.

## 6. Failure modes

Walking `spec/00-rules.md`'s five, since this plan changes a read RPC's return shape and
adds client-side interactivity, not a write path:

- **Partial writes.** N/A — `get_public_colony` is read-only; this plan adds no new write
  statement anywhere.
- **Idempotency.** N/A — a `create or replace function` migration is the normal one-time-
  forward case, same as every prior migration here.
- **Concurrency.** N/A — no new write, no new lock, no race window beyond Postgres's normal
  MVCC snapshot read `get_public_colony` already relies on.
- **Orphans.** N/A — no new table, no new column that could hold an orphaned row.
- **Dead computation.** The new RPC fields must actually be read by `PublicColonyView.tsx`'s
  panel (task E) — if `/review` finds a field returned by task A but never displayed, that
  is a real finding, not a "for later" addition; only add what task E's panel actually shows.
