# Plan 33 — Backdrop image upload lives on the colony-upload picking screen

## 1. Context already true

- **The owner's ask, stated repeatedly across sessions and again this session:** the
  backdrop JPEG upload should sit on the same screen as `colony.json`/`colony.svg`, below
  those two inputs, uploaded in the same action — not a separate screen reached after the
  fact. This has not been built despite plans 29–32 all touching "backdrop."
- **What plans 29–32 actually built, and what still stands unchanged:**
  - `apps/map/src/lib/colony/colonyBackdrop.ts` exports `uploadColonyBackdropImage(client,
    colonyId, {bytes, imageWidth, imageHeight})`, `isJpegBuffer(bytes)`, and
    `applyManifestBackdrop(client, colonyId, backdrop)` (D-049) — all reusable as-is, no
    backend/RLS/storage change needed (bucket `colony-backdrops`, grants, and
    `colonies.backdrop_*` columns already exist per plans 29/30).
  - `ColonyUploadScreen.tsx`'s `upload()` already calls `createColonyFromManifest` then
    `applyManifestBackdrop(client, result.colonyId, manifest.colony.backdrop)`
    unconditionally, then transitions to `{kind: "backdrop", colonyId, intro}`, which
    renders `ColonyBackdropScreen.tsx` as a full-panel replacement (docs/plans/31.md).
  - `ColonyBackdropScreen.tsx` (`apps/map/src/features/colony-upload/`) has its own JPEG
    file input, `readImageDimensions()` (paint-immediately/decode-async), and manual
    x/y/scale/rotate/darken/attribution fields, calling `uploadColonyBackdropImage`
    directly on submit.
  - `colony.json`'s optional `colony.backdrop` block (D-049,
    `contract/colony.schema.json`) is authoritative for **alignment** on every
    create/replace already — this plan does not touch that path or its test coverage
    (`ColonyUploadScreen.test.tsx`'s "applies colony.json's backdrop block..." and "never
    calls update()..." tests must keep passing unchanged).
- **What is missing, and the only thing this plan builds:** the backdrop **image file**
  itself has no input anywhere on `ColonyUploadStageView.tsx`'s `"picking"` stage. It can
  currently only be attached via the separate post-upload `ColonyBackdropScreen` step.
- File line counts before this change (invariant 7's 250-line cap, `.claude/hooks/
  filesize.sh`): `ColonyUploadScreen.tsx` 227, `ColonyUploadStageView.tsx` 184,
  `colonyBackdrop.ts` 141, `ColonyBackdropScreen.tsx` 211. `ColonyUploadScreen.tsx` has
  only 23 lines of headroom — the image-upload branch and intro-message composition must
  be kept out of it (see §3).

## 2. The exact task

1. **`apps/map/src/lib/colony/colonyBackdrop.ts`** — add two exports, both pure/reusable,
   so no logic is duplicated between the new inline picker and the existing
   `ColonyBackdropScreen.tsx`:
   - `readImageDimensions(file: File): Promise<{ width: number; height: number }>` — move
     this verbatim out of `ColonyBackdropScreen.tsx` (same implementation, same object-URL
     create/revoke pattern).
   - `readBackdropImageFile(file: File): Promise<{ bytes: Uint8Array; imageWidth: number;
     imageHeight: number }>` — a new helper that does the "read first 3 bytes, check
     `isJpegBuffer`, read full bytes, call `readImageDimensions`" sequence exactly as
     `ColonyBackdropScreen.tsx`'s `handleUpload` does today, throwing `new Error("That
     file is not a JPEG.")` on a bad magic number so callers have one `try`/`catch` path
     instead of a `{message, isError}` result shape to unpack.
2. **`apps/map/src/features/colony-upload/ColonyBackdropScreen.tsx`** — update
   `handleUpload` to call the new `readBackdropImageFile` instead of its inline
   JPEG-check/dimension-read, deleting the now-duplicated logic (net line reduction).
3. **`apps/map/src/features/colony-upload/ColonyUploadStageView.tsx`** — add a third,
   optional file input to the `"picking"` stage, directly below the `colony.svg` input:
   ```
   <label className="colony-upload-field">
     Backdrop image (JPEG, optional)
     <input type="file" accept="image/jpeg" aria-label="Choose backdrop image"
            onChange={(event) => onBackdropFile(event.target.files?.[0] ?? null)} />
   </label>
   ```
   Add `backdropFile: File | null` and `onBackdropFile: (file: File | null) => void` to
   `Props`. The `Continue` button's `disabled` condition is unchanged (`!jsonFile ||
   !svgFile`) — the backdrop file must never gate `Continue` or `Upload`.
4. **`apps/map/src/features/colony-upload/ColonyUploadScreen.tsx`**:
   - Add `const [backdropFile, setBackdropFile] = useState<File | null>(null);`, pass
     `backdropFile`/`onBackdropFile={setBackdropFile}` through to
     `ColonyUploadStageView`.
   - In `upload()`, after the existing `applyManifestBackdrop` call and before computing
     `intro`, add: if `backdropFile` is set, call `readBackdropImageFile` then
     `uploadColonyBackdropImage(client, result.colonyId, {...})` inside its own
     `try`/`catch`, producing an `imageResult: { ok: boolean; message?: string } | null`
     — mirroring `applyManifestBackdrop`'s own non-throwing-to-the-caller shape (a failed
     image upload must never fail the whole `upload()` promise or revert the already-
     created colony; see §6 partial-writes).
   - Move the `intro` string composition (currently three ternary branches over
     `backdropResult` alone) into a new exported pure function in `colonyBackdrop.ts` —
     e.g. `composeBackdropIntro({ colonyId, backdropResult, imageResult }): string` —
     so `ColonyUploadScreen.tsx` stays a thin caller instead of growing a fourth
     inline branch combination (json-alignment × image-upload, 2×2 plus the "neither"
     case = up to 4 distinct sentences). This is what keeps `ColonyUploadScreen.tsx`
     under the 250-line cap (§1's 23-line headroom is not enough for the branch logic
     inline).
5. **`apps/map/src/features/colony-upload/ColonyUploadScreen.test.tsx`** — add tests (see
   §5) for: an inline backdrop file being uploaded as part of `upload()`; Continue/Upload
   never gated by its absence; a failed image upload not blocking the create/replace or
   the transition to the backdrop stage.
6. **Owner amendment, mid-build: delete `ColonyBackdropScreen.tsx` and the `"backdrop"`
   stage entirely — no fallback manual-editing screen kept.** The owner's repeated
   complaint was specifically that a *second, separate* upload/editing screen existed at
   all; keeping it reachable after upload (as originally planned in §4's non-goals)
   reproduces the exact thing being rejected. Supersedes this plan's original step 6 and
   part of §4:
   - Delete `apps/map/src/features/colony-upload/ColonyBackdropScreen.tsx`.
   - Delete its test file `apps/map/src/features/colony-upload/ColonyBackdropScreen.test.tsx`
     if one exists (check first — grep confirmed no such file exists at plan-writing time;
     only `ColonyUploadScreen.test.tsx` covers this area).
   - `ColonyUploadScreen.tsx`: remove the `{kind: "backdrop"}` stage entirely — both the
     `fetchColonyById`-driven `backdropColony` state/effect (no longer needed once nothing
     downstream reads a full `ColonyRow`) and the branch that renders
     `ColonyBackdropScreen`. On a successful `upload()`, go straight to a new terminal
     stage (e.g. `{kind: "done", colonyId, message}`) that shows the composed summary
     (colony live + whichever of alignment/image applied) and a single close action —
     reusing the existing `colony-upload-overlay`/`colony-upload-panel` shell already in
     this file, not a new component.
   - `ColonyUploadStageView.tsx`'s `Stage`/`StageViewStage` types: replace the `"backdrop"`
     variant with `"done"` (or fold the done-rendering directly into
     `ColonyUploadScreen.tsx` if that keeps both files smaller — either is acceptable, pick
     whichever keeps both under the 250-line cap).
   - `fetchColonyById` (`apps/map/src/lib/db/colonies.ts`): leave the function itself
     alone (it may have other callers — check with a grep before deleting it; do not
     delete a shared `lib/db` function as a side effect of this UI change unless confirmed
     unused elsewhere).

## 3. Pinned constraints

- **`uploadColonyBackdropImage`'s call shape does not change**: `(client, colonyId,
  {bytes: Uint8Array, imageWidth: number, imageHeight: number})`. Do not add a fourth
  argument or change the storage path convention (`${colonyId}.jpg`, upsert:true,
  content-type `image/jpeg`) — untouched code in `colonyBackdrop.ts` already owns this.
- **The backdrop image upload must never block or roll back colony creation/replace.**
  `createColonyFromManifest` succeeding is the one irreversible, high-value action in this
  flow (it writes `colonies`/`plots` rows). If `readBackdropImageFile` or
  `uploadColonyBackdropImage` throws, the user must still land on the `"backdrop"` stage
  with a colony that exists — exactly the precedent `applyManifestBackdrop`'s
  `{applied: true, ok: false, message}` result already set for a bad manifest-driven
  alignment. Do not wrap the image-upload call in a way that lets its rejection propagate
  into `upload()`'s outer `.catch()` (that branch sets `{kind: "failed", ...}`, which would
  incorrectly tell the user the whole upload failed).
- **`isJpegBuffer` stays the only format check** — do not add file-extension or
  `File.type` MIME sniffing as a second gate; the existing admin-portal/pipeline
  convention (magic-number-only) is intentional (`colonyBackdrop.ts`'s own comment: "this
  project only ever ships JPEG backdrops").
- **`colony.json`'s `backdrop` block remains authoritative for alignment, unconditionally,
  on every create/replace** (D-049) — this plan adds the **image**, not a second way to
  set alignment. Do not let the new inline file input write anything to
  `backdrop_transform_*`/`backdrop_darken_alpha`/`backdrop_enabled_on_*`/
  `backdrop_attribution` — those columns are untouched by `uploadColonyBackdropImage`
  today (confirmed: it only ever sets `backdrop_storage_path`/`backdrop_image_width`/
  `backdrop_image_height`) and must stay that way.
- **250-line cap, both touched files** (`.claude/hooks/filesize.sh`, invariant 7):
  `ColonyUploadScreen.tsx` (227 lines before this change) and `ColonyUploadStageView.tsx`
  (184 lines before this change) must both stay ≤ 250 after the diff. Use
  `composeBackdropIntro`'s extraction (§2.4) to keep `ColonyUploadScreen.tsx` under the
  cap — do not inline the 2×2 branch logic.
- **`ColonyBackdropScreen.tsx` is deleted, not moved** (owner amendment, §2 step 6) — grep
  for any other importer before deleting (plan 31 already made `colony-upload/` its only
  location, but confirm nothing else picked up a reference since).

## 4. Non-goals

- No change to `tools/pipeline`, `contract/colony.schema.json`, or any migration —
  colony.json's `backdrop` declaration and the storage bucket/RLS/columns are already
  built (plans 31/32) and out of scope here.
- **No manual alignment-editing UI rebuilt anywhere in `apps/map`.** Per the owner's
  amendment (§2 step 6), the only supported way to set/change x/y/scale/rotate/darken/
  attribution is `colony.json`'s `backdrop` block on a replace (D-049) — there is
  deliberately no in-app form for it anymore after this plan. If a colony needs its
  alignment tweaked, the fix is: edit `tools/pipeline/colonies/<id>.json`, re-export, and
  re-upload as a replace. Do not add a new editing screen to compensate.
- No new client-side image resizing/compression/re-encoding — the file picked is uploaded
  byte-for-byte, same as the deleted screen did.
- No change to `admin-portal/`'s own, separate backdrop upload path (untouched by plans
  29–32's UI moves and untouched here) — out of scope, a different app entirely, not
  reachable by ordinary users.

## 6. Failure modes (spec/00-rules.md checklist)

- **Partial writes**: the one real risk this plan introduces. `createColonyFromManifest`
  (writes `colonies`/`plots`) and `uploadColonyBackdropImage` (writes a storage object +
  three `colonies` columns) are two separate, non-transactional operations, same as
  `applyManifestBackdrop` already is. Mitigation: never let the image-upload failure
  surface as an overall upload failure (§3) — the colony row is the source of truth and
  always exists once `result.ok` is true; a missing/failed image is a re-attachable gap
  (via `ColonyBackdropScreen.tsx`, still reachable), not a corrupt state.
- **Idempotency**: `uploadColonyBackdropImage`'s `upsert: true` at a fixed
  `${colonyId}.jpg` path means re-running this exact upload with the same file is already
  idempotent — unchanged by this plan.
- **Concurrency**: no new concurrent-write surface — this plan adds one more caller of an
  existing function, not a new write path or a new race between two writers.
- **Orphans**: none — a colony created without a backdrop image today is already a valid,
  supported state (backdrop is optional colony-wide); this plan does not change that.
- **Dead computation**: `ColonyBackdropScreen.tsx`'s manual image-upload UI stays live and
  load-bearing (replacing an image later, or attaching one to a colony uploaded without
  one) — nothing becomes dead code by this change other than the duplicated
  JPEG-check/dimension-read logic this plan explicitly deletes in favor of the shared
  helper.
