# Plan 20: Per-colony, owner-drawn click-to-focus zoom reference

Owner-reported bug (2026-08-29 conversation): clicking a plot flies to a visibly different
zoom level in different colonies. Root cause confirmed by reading both live manifests
(`tools/pipeline/out/shree-vatika-2/colony.json`, `tools/pipeline/out/jai-dev-residency/
colony.json`) — Shree Vatika 2 has `scale.px_per_ft = 2.6667`, Jai Dev Residency has
`scale.px_per_ft = 0.451`, a ~5.9x difference, because `pipeline/export/normalise.py`
normalises every colony's SVG to a fixed viewBox width of 1000 units regardless of the
colony's real physical footprint (D-110). `SELECT_ZOOM = 3.4` (`apps/map/src/components/
map/view.ts:40`) is a single fixed absolute Leaflet zoom applied identically to every
colony, so the same code constant produces ~28.1 screen-px/real-ft on Shree Vatika vs.
~4.8 screen-px/real-ft on Jai Dev Residency at selection time.

Owner explicitly rejected deriving the fix from site-wide `px_per_ft` (a colony can have a
huge site but small individual plots, or vice versa — site scale and "how much should fill
the screen on selection" are different judgements) and instead wants to **draw a reference
rectangle by hand in AutoCAD**, sized to whatever real-world area should fill the screen on
selection for that specific colony, with the pipeline mechanically measuring it. This
mirrors the existing `COL-NORTH`/`COL-SITE` pattern (D-118: geometry drawn in AutoCAD encodes
human judgement, the pipeline only transforms it).

Owner explicitly confirmed scope: **only the click-to-focus zoom** (`SELECT_ZOOM`). `maxZoom`
(`4`, `useColonyCanvas.ts:127`) is explicitly out of scope — "i have no issues with max
zoom." Do not touch, raise, or resize it.

## 1. Context already true

- **`SELECT_ZOOM = 3.4`** (`apps/map/src/components/map/view.ts:40`) is consumed only by the
  fly-to-plot effect in `apps/map/src/components/map/useColonyCanvas.ts:253-275`. That effect
  calls `map.project(target, SELECT_ZOOM)` (line 270), `map.unproject(centerPoint,
  SELECT_ZOOM)` (line 272), and `map.setView(center, SELECT_ZOOM, {animate: true})` (line
  274) — three call sites, all needing the same zoom value.
- **`L.CRS.Simple` binds SVG viewBox units 1:1 to Leaflet lat/lng units** (`view.ts`'s own
  header comment, `leafletViewState`). Leaflet zoom `Z` means `screen-px-per-SVG-unit =
  2^Z`. `fitScale()` (`view.ts:42-45`) already computes an analogous raw scale (CSS px per
  SVG unit, not a zoom number) as `min(viewport.width / model.width, viewport.height /
  model.height)` for the whole-colony initial fit — the new per-selection scale is the same
  shape, applied to a reference rectangle instead of the whole colony, then converted to a
  zoom via `log2`.
- **The manifest's `scale.px_per_ft` field exists and is schema-required today
  (`contract/colony.schema.json`'s `colony.scale.px_per_ft`) but nothing in `apps/map` reads
  it** — confirmed by `apps/map/src/lib/db/types.ts:102-107`'s own comment: "confirmed by
  grep that nothing else, e.g. viewbox/scale/north_deg/features/centroid/confidence, is used
  anywhere in this app." Only `colonies.svg` is persisted from the manifest into the `colonies`
  table at upload (`apps/map/supabase/migrations/20260817000000_m15_colony_upload.sql`) — this
  plan is the first time a second manifest field needs to survive into the database.
- **`pipeline/extract/dxf.py`'s existing `COL-NORTH` handling is the exact cardinality
  pattern to mirror**: `_NORTH_LAYER = "COL-NORTH"`, 0 or 1 entity allowed, `len(north_lines)
  > 1` raises (`dxf.py:93-94`). `COL-SITE` is the mirror for "closed LWPOLYLINE" validation
  (`_read_ring`, `dxf.py:103-114`, reused as-is — no new geometry-reading code needed).
- **`pipeline/export/normalise.py`'s `Transform`** (`min_x, min_y, max_y, scale, height_px`)
  is already computed once per export in `orchestrate_export` (`pipeline/export/run.py:66`)
  and is exactly what's needed to convert the new rectangle's real-drawing-unit extent into
  SVG viewBox px: `extent_px = (max_x - min_x_of_ring) * t.scale`. `apply_transform` itself is
  not reusable here (it maps one point, including translation; we need a translation-
  invariant *extent*), so this is a new small pure function, not a call to the existing one.
- **`pipeline/export/manifest.py::build_manifest`**'s exact signature is `(config, t, plots,
  features, north_deg, facings, corners)` (`manifest.py:32-40`) and returns the dict with
  `colony`/`plots`/`features` keys (`manifest.py:74-87`). `colony.scale` is already written at
  `manifest.py:79` — the new field is a sibling key on the same `colony` dict.
- **`orchestrate_export`** (`pipeline/export/run.py:33-79`) is the single call site to extend:
  it already destructures `result` (a `DxfIngestResult`) and calls `compute_transform(site)`
  at line 66, immediately before `build_manifest(...)` at line 67.
- **The full app-side thread from manifest to render**, confirmed by reading each hop:
  `parseColonyManifest.ts` validates the raw uploaded JSON against the real schema file via
  Ajv (`ajv.compile(colonySchema)`, `parseColonyManifest.ts:18-20`) — schema-valid is
  sufficient, no separate TS re-validation. `createColonyFromManifest.ts` (`apps/map/src/lib/
  colony/createColonyFromManifest.ts:7-30`) reads only a named subset of `manifest.colony`/
  `manifest.plots` and forwards it to `callCreateColonyFromManifest` (`apps/map/src/lib/db/
  colonies.ts:44-73`), which calls `.rpc("create_colony_from_manifest", {...})` — the **only**
  place that RPC name may appear (NAVIGATION.md's `.rpc`-only-in-`lib/db` rule). The RPC
  (`20260817000000_m15_colony_upload.sql:14-120`) inserts/updates the `colonies` row. Reads
  come back through `fetchColonyById`/`fetchVerifiedColonies` (`apps/map/src/lib/db/
  colonies.ts:18-37`), both already `select("*")` — a new column needs **no query change** on
  the read side, only a `ColonyRow`/`ColonyInsert` type update (`apps/map/src/lib/db/
  types.ts:16-33`). `App.tsx:234` passes `selectedColony.svg` into `<ColonyMap
  colonySvg={...}>`; `ColonyMap.tsx:54-58` forwards it into `useColonyCanvas({...})`. The new
  value follows the identical path as `colonySvg` at each of these three hops.
- **`usePlotDimensions`/`dimensionsRef`** (`useColonyCanvas.ts:70,278`) is a *separate, async,
  per-selection* fetch (`usePlotDimensions.ts`) and is explicitly **not** the mechanism for
  this — it isn't guaranteed populated by the time the fly-to effect runs on the same
  `selectedId` change, and re-deriving a per-colony-constant value on every click would be
  both wrong (adds latency) and redundant (the value never changes per colony). The reference
  rectangle's extent must be fetched once at colony load, like `colonySvg` itself, not
  per-plot-selection like `dimensionsRef`.
- **Decisions this plan rests on and does not revisit**: D-110 (fixed viewBox width 1000,
  the actual root cause of the inconsistency — kept, not reverted), D-118 (AutoCAD geometry
  encodes judgement; pipeline only measures), D-025 (upload screen is the only onboarding
  path — the new field flows through the existing upload RPC, no new write path).

## 2. The exact task

area that should fill the screen when a plot in this colony is selected. Owner's framing
judgement, not derived." Add a short paragraph next to the existing `COL-NORTH` "if absent"
paragraph: absent means the app falls back to today's fixed behaviour (Non-goal 2 below) for
that colony.

**B. `tools/pipeline/pipeline/extract/types.py`** — add `zoom_ref: Ring | None` field to
`DxfIngestResult` (after `north_deg`, before `config`).

**C. `tools/pipeline/pipeline/extract/dxf.py`** — add `_ZOOM_REF_LAYER = "COL-ZOOM-REF"`
constant. In `ingest_dxf`'s entity loop, collect matching entities into a
`zoom_ref_rings: list[Ring]` using the existing `_read_ring` (same closed-LWPOLYLINE
validation as `COL-SITE`/`COL-PLOT`/etc. — add `"COL-ZOOM-REF"` to a rings-that-need-
`_read_ring` set, or branch it explicitly next to the `COL-NORTH` branch; either is fine, the
plan doesn't pin the branch shape). After the loop, raise `DxfConformanceError(f"COL-ZOOM-REF
has {len(zoom_ref_rings)} entities, expected 0 or 1")` if more than one. Pass
`zoom_ref_rings[0] if zoom_ref_rings else None` into the returned `DxfIngestResult`.

**D. `tools/pipeline/pipeline/export/normalise.py`** — add a new pure function:
```python
def ring_extent_px(t: Transform, ring: Ring) -> tuple[float, float]:
    """Width/height of ring's bounding box, in SVG viewBox px — translation-invariant,
    unlike apply_transform (which maps one point). Assumes ring is axis-aligned to the
    DXF's own X/Y axes, the same assumption the rest of this pipeline makes everywhere
    (no rotation is ever applied, only translate + Y-flip + uniform scale)."""
    xs = [p[0] for p in ring.points]
    ys = [p[1] for p in ring.points]
    return (max(xs) - min(xs)) * t.scale, (max(ys) - min(ys)) * t.scale
```

**E. `tools/pipeline/pipeline/export/manifest.py`** — add optional parameter
`zoom_ref: Ring | None = None` to `build_manifest`'s signature (after `corners`). When not

alongside the existing `Transform, apply_transform` import) and add to the returned
`colony` dict: `"select_zoom": {"ref_width_px": round(width_px, 2), "ref_height_px":
round(height_px, 2)}`. When `zoom_ref is None`, omit the `select_zoom` key entirely (not
`null` — the schema change in step F must make it optional, not nullable).

```typescript
export function selectZoomFor(viewport: Viewport, refWidthPx: number, refHeightPx: number): number {
  const scale = Math.min(viewport.width / refWidthPx, viewport.height / refHeightPx);
  return Math.log2(scale);
}
```

## 3. Pinned constraints

- **The clamp in step P is not optional.** `map.project`/`map.unproject` apply the zoom value
  they're given *unclamped*; `map.setView` clamps to `[minZoom, maxZoom]` when actually
  rendering. Today's fixed `SELECT_ZOOM = 3.4` is safely under `maxZoom = 4` by construction
  (`view.ts:33`'s own comment says so), so this mismatch has never mattered — but a computed,
  owner-chosen `rawZoom` has no such guarantee. If the pan-offset math (`project`/`unproject`)
  runs at an unclamped zoom while `setView` renders at a clamped one, `SELECT_VERTICAL_ANCHOR`
  positioning silently drifts off its intended 35%-from-top anchor. Clamp once, before all
  three call sites, using the same `zoom` value in all three — never clamp only the final
  `setView` call.
- **A colony with no `COL-ZOOM-REF` rectangle must render pixel-for-pixel identically to
  today**, both in the pipeline's manifest output (no `select_zoom` key at all, not `null`)
  and in the app's fly-to behaviour (falls through to the exact existing `SELECT_ZOOM =
  3.4` constant). Shree Vatika 2 and Jai Dev Residency must not visibly change until someone
  deliberately re-exports them with the new rectangle drawn.
- **`create_colony_from_manifest`'s signature change requires an explicit `drop function`
  first** (step J) — `create or replace function` with new parameters creates a second
  overload rather than replacing the 7-argument original, which would leave the old signature
  live and callable, silently bypassing the new columns on any caller still using it.
- **The two new `colonies` columns are nullable with no backfill and no `not null`
  constraint, permanently** — unlike `svg`'s "every writer supplies it, nullable only at the
  column level" nullability, absence here is a legitimate steady-state (a colony owner may
  simply never draw the rectangle), not a migration-can't-backfill artifact. Do not add a
  `not null` constraint or a non-null default.
- **`ring_extent_px` assumes the reference rectangle is axis-aligned to the DXF's own X/Y
  axes** — consistent with every other geometric assumption already made throughout this
  pipeline (no rotation is ever applied to anything, per `normalise.py`'s own transform:
  translate + Y-flip + uniform scale, no rotation term). Do not add rotation-correcting logic
  (e.g. `shapely`'s minimum-rotated-rectangle, as `manifest.py::_rect_sides_ft` uses for
  plots) — that would silently accept a rotated rectangle and produce a wrong width/height, a
  worse failure than requiring the rectangle be drawn axis-aligned like everything else here.
- **`select_zoom` is optional, never nullable, in the schema** (step F) — a manifest either
  has the full `{ref_width_px, ref_height_px}` object or omits the key. Do not emit `"select_
  zoom": null` or `{"ref_width_px": null, ...}` from the pipeline.
- **QA sanity band (step I): `ref_width_px <= viewbox[2]` and `ref_height_px <= viewbox[3]`**,
  strictly — this is the one new business-judgement number this plan introduces, and it must
  block export, not warn, per tier-1.md's "Export is the last gate."
- **Reuse, do not reimplement**: `_read_ring` (`dxf.py`) for the new layer's geometry
  validation, `Transform`/`compute_transform` (`normalise.py`) for the scale factor already
  computed once per export, `fitScale`'s `min(...)` shape (`view.ts:44`) for the new
  `selectZoomFor`'s ratio math, and `map.getSize()` (`useColonyCanvas.ts:268`, already called
  in the same effect for `SELECT_VERTICAL_ANCHOR` positioning) for the viewport passed to
  `selectZoomFor` — do not add a second `ResizeObserver` or viewport-measuring path.

## 4. Non-goals

- **`maxZoom`/`minZoom`** (`useColonyCanvas.ts:126-127`) — explicitly out of scope per the
  owner ("i have no issues with max zoom"). A colony whose computed `rawZoom` exceeds
  `maxZoom` gets clamped and lands somewhat less zoomed-in than the reference rectangle would
  imply; that is accepted behaviour for this plan, not a bug to chase.
  Do not raise, lower, or otherwise touch either constant.
- **Deriving the reference rectangle automatically** (from `px_per_ft`, median plot size, or
  any other computed heuristic) — explicitly rejected by the owner in favour of hand-drawn
  geometry. Do not add a fallback heuristic beyond "use `SELECT_ZOOM`" for a colony with no
  rectangle.
- **Re-exporting or re-uploading Shree Vatika 2 or Jai Dev Residency** — out of scope for this
  plan. Both keep their current (inconsistent) zoom behaviour until the owner separately
  draws `COL-ZOOM-REF` on each DXF and re-runs the export/upload flow themselves.
- **The `COL-ZOOM-REF` rectangle rendering visually anywhere** — it is metadata only, never a
  `<path>`/CSS class in `colony.svg`. Do not add it to `contract/SPEC.md`'s `colony.svg` class
  table or to `pipeline/export/svg.py`.
- **`fitView`/`fitScale`'s whole-colony initial-fit behaviour** (`view.ts:42-49`) — unrelated
  to plot selection, not touched by this plan.
- **The Bibrod/Bharatkshetra colonies currently in progress** (raw survey DXFs, not yet
  normalised) — this plan's `COL-ZOOM-REF` layer is available to them once they reach
  export, but drawing it on those DXFs is a separate, later, owner-driven step, not part of
  this plan's acceptance criteria.

## Addendum (mid-build, 2026-08-29): reference rectangle arrives as a scaled block insert

Owner refined the authoring workflow while this plan was being built: rather than drawing a
fresh rectangle per colony, they define a single 9:16-aspect-ratio block once, then `INSERT`
+ scale a copy of it onto `COL-ZOOM-REF` per colony. This does not change the manifest shape,
`ring_extent_px`, `build_manifest`, the schema, the migration, or anything app-side in steps
D through P — `ring_extent_px` already measures whatever width/height the placed rectangle
ends up at, regardless of how that geometry got there. It only changes step C's DXF-reading
requirement: `COL-ZOOM-REF` may now hold either a plain closed `LWPOLYLINE` (as originally
planned) **or** an `INSERT` referencing a block whose definition contains exactly one closed
`LWPOLYLINE`, scaled/positioned by the INSERT's own transform.

Implemented as `_read_zoom_ref()` in `dxf.py`, replacing the direct `_read_ring()` call for
this layer: dispatches on `entity.dxftype()`, using `entity.virtual_entities()` (ezdxf's
insert-resolution — confirmed by direct test to correctly apply the INSERT's position and

## 6. Failure modes

This plan writes state (a new migration touching the `colonies` table and
`create_colony_from_manifest`), so `spec/00-rules.md`'s checklist applies:

- **Partial writes**: the new columns are set in the same `insert`/`update` statement as
  every other colony-level field already written by `create_colony_from_manifest` (step J) —
  no separate statement, so there is no window where a colony row exists with the SVG/plots
  written but the zoom-reference columns not, or vice versa. Both branches (insert and
  replace) must set both new columns from the two new parameters.
- **Idempotency**: re-running the same export (`orchestrate_export`) with the same DXF is
  already covered by the existing `test_two_clean_runs_are_byte_identical`/
  `test_orchestrate_export_is_idempotent_including_tree_positions` tests — `ring_extent_px`
  is a pure function of already-idempotent inputs (`Transform`, `Ring.points`), so no new
  source of nondeterminism is introduced. Re-uploading the same manifest through `create_
  colony_from_manifest` with `p_replace = true` must produce the same two column values as
  the first upload (covered by extending the existing "replace" test in step-5's acceptance
  criteria, not a new test category).
- **Concurrency**: not applicable — these two columns are written only by the single-writer
  upload/replace path (D-025), never touched by a plot-status transition
  (`applyPlotTransition()`), so there is no concurrent-writer scenario to protect against
  (tier-1.md's "Matching is identity"/"State transitions" rules govern a different write
  path entirely).
- **Orphans**: not applicable — these columns live on the `colonies` row itself, not on a
  child row that could be orphaned by a parent delete; there is no `plots`/`plot_history`
  interaction at all (unlike the existing `would_orphan_history` check, which this plan does
  not touch or need to touch).
- **Dead computation**: `ring_extent_px`'s result is dropped entirely (not written to the
  manifest) when the DXF has no `COL-ZOOM-REF` ring — this is correct short-circuiting, not
  dead computation, since the function is simply never called in that case (step E: `zoom_ref
  is None` skips the call). Confirm at review time that `selectZoomFor` (app side) is actually
  read by the fly-to effect and not just computed and discarded — the same class of bug
  `contract/SPEC.md:37`'s `data-label-height` history warns about.
