# D-123: `tools/pipeline` propagates a hand-declared `backdrop` through re-exports, never derives one

**Status:** accepted
**Date:** 2026-09-13

## Decision

`pipeline/extract/types.py`'s `ColonyConfig` (frozen dataclass, one per
`tools/pipeline/colonies/<id>.json`) gains one new trailing field:
`backdrop: dict[str, Any] | None = None` — defaulted so the 7 existing call sites that
construct `ColonyConfig(...)` directly (`pipeline/extract/dxf.py` itself, plus 6 test
files) keep working unchanged.

`pipeline/extract/dxf.py::load_colony_config()` reads it optionally —
`backdrop=data.get("backdrop")`, not `data["backdrop"]`, since unlike every other field
here this one has no `except KeyError` requiring it.

`pipeline/export/manifest.py::build_manifest()` copies it into the exported manifest
verbatim, immediately after the existing `select_zoom` block:

```python
if config.backdrop is not None:
    colony_out["backdrop"] = config.backdrop
```

No reshaping, no validation beyond what `pipeline/export/qa.py::run_qa()` already does —
its first check is schema validation against the real `contract/colony.schema.json`, so a
malformed `backdrop` dict surfaces as a normal QA failure once it reaches the exported
manifest, the same posture `select_zoom` already has.

The shared golden fixture (`tools/pipeline/colonies/shree-vatika-2.json`) is **not** given
a `backdrop` key — CLAUDE.md's "one shared colony, deliberately" rule means the golden
export must stay byte-identical; new tests (`tests/test_export_backdrop.py`) use their own
temp config instead.

## Why

Owner follow-up (2026-09-13, same session as D-049): "also make changes in pipeline which
creates json to enter map details and everything to enter the required values in json." —
raised immediately after the JSON-is-authoritative decision (D-049), directly answering the
exact problem D-049's own decision file and the original `## Deferred` entry both named as
unsolved: a `backdrop` block hand-added to a real colony's exported `colony.json` was
silently discarded the next time `make export` regenerated that file, since
`build_manifest()` never emitted the key — invariant 6 ("no pipeline stage may hold a
correction a rerun would silently discard").

The fix follows `select_zoom`'s own precedent exactly, but with one structural difference:
`select_zoom` is *derived* from a `COL-ZOOM-REF` rectangle the DXF actually contains, so it
travels through `ingest_dxf()`'s geometry pipeline as a `Ring | None` parameter to
`build_manifest()`. A backdrop is a manually aligned aerial photo — there is no DXF entity
to derive it from, ever — so it cannot follow that path. `ColonyConfig` (the hand-maintained
`colonies/<id>.json` input file, read once per export and never regenerated by one) is the
correct home instead: it is already exactly the kind of value this file carries (`id`,
`name`, `blocks`, `north_deg`, `source` — none of these come from the DXF either). This
turns an accepted, permanent hand-maintenance burden on the *output* file into a one-time
declaration in the *input* file that every future export carries forward automatically.

## Rejected alternatives

- **Deriving `backdrop` from some DXF entity, mirroring `select_zoom`'s `COL-ZOOM-REF`
  pattern exactly.** Not possible even in principle — a backdrop is an externally sourced
  aerial-style raster manually aligned against the rendered map, not a rectangle or any
  other entity a CAD operator would ever place in the drawing. `docs/cad-layer-standard.md`
  correctly has no layer for it.
- **A generic "extra fields" passthrough on `ColonyConfig`** (e.g. an open
  `dict[str, Any]` bucket for any future hand-declared manifest addition), instead of one
  named `backdrop` field. Rejected as unrequested scope: the ask was specifically about
  backdrop, `select_zoom`'s own precedent is a named field not a generic bucket, and a
  generic passthrough would bypass `ColonyConfig`'s own typed-field discipline for every
  future addition, not just this one.
- **Validating `backdrop`'s shape inside `load_colony_config()`** before it ever reaches
  `build_manifest()`. Rejected as redundant — `run_qa()`'s existing first check already
  validates the complete exported manifest against `contract/colony.schema.json`, the same
  schema this value must conform to either way; a second, pipeline-local validation would be
  a second place to keep in sync with the schema for no additional safety.
